# 知识层样板（通用模板）

本样板示意本项目设计中"知识层"这一角色的形态，内容参考一个现行知识层实例的结构与约定、去除其专属信息后通用化而成。任何符合下列结构与契约的知识库实例都可充任知识层；实例托管在何处、私有还是公开，均属部署选择，不写入设计文档。

## 角色与定位

- 知识层收纳**经人确认**的知识，是本系统权威等级的最高层（approved）；只承载知识，**不承载各 agent 的经验记忆与会话记忆**（那是经验层的地盘）。
- 内容按 Karpathy LLM Wiki 方式组织：原始资料只读不改，知识页由维护人（人或被指定的 agent）编译维护。
- **远端仓是共享真相源**；各 agent 机器上的本地副本只是工作副本，按同步规范与远端对齐。

## 结构

```
knowledge-base/
├── README.md            总索引与专题总表
├── WIKI_RULES.md        维护规则（版本化修订；与所用 LLM Wiki 技能配套，冲突时以本文件为准）
├── AGENTS.md            外部 agent 入口（先读顺序、交稿方式）；贡献者与权限名单另册维护
├── raw/<专题>/          原始资料，只读不改
│   ├── images/          配图
│   └── sources/         抓取的原始数据（如帖子 json、网页存档）
├── wiki/<专题>/         知识页（一层专题目录，不再下分）
│   ├── topic-overview.md 每专题一页：目的、收录范围、收与不收与合并的判断方法
│   ├── index.md         全量索引（全专题共用，每专题一节）
│   └── log.md           操作日志（全专题共用，只追加不改旧记录）
├── inbox/               投稿区（含投稿模板）
└── tools/               补充体检脚本
```

**专题制**：专题按**问题域**划分（不按来源或形式）；每个专题有一页 `topic-overview.md` 写清目的与收录判断；新建专题须经所有者同意，并同步更新总表与 `index.md`。通用专题兼作孵化区：同一主题攒够量或成为常设项目、经所有者同意后独立成专题，raw 与 wiki 整体迁移、引用一次改净、log 记一笔。

**raw 存档原则**：必须保存**原文全文、配图与抓取数据**——多方共用的库不能依赖原链接长期有效，知识页要能靠原文复核与重整。文件名建议 `YYYY-MM-DD_作者_短标题` 式（保序、标源）。文档内引用一律相对路径，不写任何机器的绝对路径。

## 写角色：维护人是角色，不是某个固定的 agent

- 维护人由所有者**点名指定**，在被点名范围内负责收录、体检与推送；改派时角色随之转移，交接在 `log.md` 记一笔。
- **同一时刻只有一个写入者**；非维护人对 `raw/` 与 `wiki/` 只读，参与方式是投稿（见下）。
- 升级路径（留档、不提前启用）：当各 agent 开始无人点名自主高频写入时，单写者角色制改为分支＋合并（PR）制。

## 写入纪律

1. **先同步再动手**：先拉取远端对齐，确认工作区干净；不干净先弄清是谁的改动，不覆盖。
2. **一次只收一篇资料，收完提交一次**；提交署名写清执行者（作者名＋`Agent: <标识>`）。
3. **提交后及时推送**；推送被拒说明有人先推，重新对齐检查冲突再推，**绝不强推覆盖他人提交**。
4. 投稿被收录后，从 `inbox/` 删除或移入对应 `raw/<专题>/`，并在 `log.md` 记一笔。

**inbox 投稿格式**：文件名 `YYYY-MM-DD_提交者_专题_短标题.md`；内容写清来源链接、建议专题、想补充的点；投稿者不直接改 `raw/`、`wiki/`、`index.md`、`log.md`。

**记忆回写通道**：各 agent 把自己记忆中的结论汇总进知识层时走 inbox，且**只投所有者确认过的结论**；文件必写四项——**类型**（决定｜偏好｜事实｜教训）、**项目**、**来源**（所有者原话或文件链接）、**日期**。私人记忆、会话记忆、agent 自己的猜测、无来源的自动生成内容，一律不投。"所有者确认过"指所有者确认的是投稿中的这一版文本，投稿须附确认记录（确认人、时间、确认的文本）；确认后再改写的文本须重新确认。维护人收录时先把投稿原样存入 `raw/` 再整理成页，冲突按下方 Status 规则处理。

## 来源强度与状态块

- 「关键结论」（数字、排名、归属、因果，以及会被拿来指导决策的结论）只有一个来源支撑时，句末标注「（单一来源）」。
- 来源冲突或与原始出处对不上：用 `> **Status: Disputed**` 块写清双方说法与出处，交所有者裁定。
- 已被新来源推翻：旧页原说法下加 `> **Status: Outdated**（日期）` 块，写明被哪条来源推翻并链接新页；**旧说法保留，不悄悄改写**。
- 已对过原始出处的，在 raw 存档中写「核对」注记，知识页可不再加标注。

## 体检与过时提醒

- 每次收录后（及所有者要求时）运行体检：出处校验（承重事实须能在 raw 中找到出处）、未被引用的 raw、空章节、同名文件歧义、内部链接与索引一致性；结果追加到 `log.md`。只修真正的问题，事实类问题不自动改。
- **过时提醒**：每个知识页元信息带**类别**与**最近确认**日期——类别参考期限：工具类 30 天、做法类 90 天、原则类不设期限。有新来源印证才更新「最近确认」；超期未确认的页列入"待复核"（只是提醒复查，不代表说法错了）；被推翻的走 Outdated 块。

## 同步、迁移与搬家

- **首次上仓/整仓迁移前必须过适配检查单**：① 剥离本机绝对路径与本机专属命令；② 清除只在旧环境成立的表述（如"只在本机使用"）；③ 备份包、锁文件、缓存等不入仓，凭证永不入仓；④ 引用自检——仓外引用要么一并入仓，要么删去死引用；⑤ 历史去留明示（整仓迁移默认带全部 git 历史，历史即 provenance；干净起步须所有者批准并记 log）。
- 禁止事项：强推覆盖远端历史；整机目录无筛选打包上仓；在本地与远端双线分叉演进。
- 搬家：整仓克隆到新环境 → 按检查单复查 → 更新 README 与规则中涉及环境的表述 → log 记明迁移日期与新址；旧址只读保留。

## 结论写回

所有者拍板的协作结论以页面形式写回对应专题：决定原文摘录存入 `raw/`（注明出处与确认日期），再写知识页并注明「所有者 YYYY-MM-DD 确认」——决定同样受出处校验约束。决定变更时走 Outdated/更新最近确认流程。

## 与经验层的接口契约

- **晋升（单向向上）**：经验层候选 → **所有者确认（绑定被确认文本的版本，记录确认人、时间）** → 知识层 `inbox/` → 维护人收录整理 → 入 `wiki/` 并记 log；晋升条目保留其经验层出处与确认记录（provenance 信封随行）。人确认在投稿之前完成，维护人的收录是整理而非确认。
- **召回（只读向下）**：经验层与其他 agent 只读检索知识层（文件直读，或经 MCP/HTTP 读接口）；召回结果带权威标注 `approved` 与来源条目链接。
- **无共享运行时**：知识层不依赖经验层的进程与存储引擎；任一层替换实现不影响另一层的数据。
- **准入分工**：知识层的"人确认"由所有者在投稿前完成、inbox 只收带确认记录的结论来保证；维护人（人或 agent）负责收录整理，不能代为确认，整理时不得引入未确认的新结论。知识层不依赖经验层的任何过滤承诺。
