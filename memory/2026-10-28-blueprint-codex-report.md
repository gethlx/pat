## 结论与评审范围

五项修改的方向都成立，但不同意“照这五条补完即可冻结”。逐项判断为：**M1 需修改、M2 同意、M3 需修改、M4 同意、M5 需修改**。此外，还有三处影响实施的重大边界需要补齐。

这些问题不要求重选 Hy-Memory，也不推翻“经验层只分加工、不分存储”的路线。补齐后，可以冻结为 **v0.1 设计与实施基线**；运行效果仍须在后续阶段验证。

## 五项修改的逐条判断

| 项目 | 判断 | 核心意见 |
|---|---|---|
| M1 并发冲突、召回机制、导入权威等级 | 需修改 | 缺口成立；区分重复写入与语义冲突，明确可保证的召回范围，区分原始输入与加工输出 |
| M2 阶段完成标准与最小评测前移 | 同意 | 用真实闭环和产物证据验收；运行统计另须定义口径 |
| M3 镜像还原演练 | 需修改 | 还原不能只比条数，还须保留来源、权威、状态与必要历史 |
| M4 失效引用与知识层指针 | 同意 | 修正为现有相对链接与角色化描述，样板歧义另行统一 |
| M5 contracts 对接 | 需修改 | 补文件原生约定；区分内部规则与跨线契约，不将未来对接变成一期依赖 |

### M1：补并发冲突、召回机制及导入权威等级——需修改

缺口判断正确。[需求基准](requirements-baseline.md) §6 已要求冲突可见、不能仅靠模型自觉召回；蓝图目前只有检索留痕和可回滚的原则，尚未说明如何落实。

建议将原报告的表述收窄为：

- **冲突不必一律交人。** 重复导入、重试写入应自动去重；版本冲突可以拒绝写入并重试。只有无法自动解决的内容冲突才保留双方、交人裁定。底线是不能静默覆盖。
- **召回保证须定义可验证的范围。** 可以保证接入层执行检索、注入结果并留下记录，不能保证模型一定理解或采纳。会话开局注入也不能覆盖会话中途新增的任务，须说明触发时机和不支持的接入方式。
- **原始导入素材默认 `raw`，同意。** 模型加工后的推断应标为 `inferred`，不能把原始输入与加工输出都永久归为 `raw`。

### M2：阶段完成标准与最小评测前移——同意

这是五条中最直接、最有必要的一条。阶段二必须拿出薄、厚两条管线各自的真实闭环证据，包括写入后被另一厂商 Agent 召回；最小回归集也应在此时建立。

实施规格还须明确两点：

- 回归集不能替代运行记录。驳回率、跨场景失败、零召回时长，需要相应的统计窗口、样本口径和检索记录。
- “90 天零召回”是后续观察信号，不能要求阶段二先运行 90 天才通过；当前阶段应验证记录机制可用。

这符合“蓝图先行、测试验证依赖假设”的既定决定，不构成重开底座选型。

### M3：镜像必须做还原演练——需修改

同意放入阶段二验收，但“恢复到可召回状态并比对条数”太弱。条数一致，仍可能丢失批准状态、来源和版本历史，甚至把已驳回条目重新当作有效记忆。

最低验收应包括：在独立位置恢复，核对内容完整性、稳定标识、来源、权威等级、有效状态及必要历史，并用代表性查询验证召回。引用的原始材料也必须可定位，不能恢复出一批失效链接。索引可以重建，不要求向量逐字节相同。

此外，**定期 Git 镜像不能单独保证每次改写都有历史**：两次导出之间可能发生多次覆盖。蓝图须明确完整版本历史由主存储还是独立变更记录承担。

冻结前写清这些标准即可；实际演练属于阶段二，不必倒置为设计冻结的前置运行要求。

### M4：修正旧引用与知识层指针——同意

蓝图文首四个旧文件名确实需要改为现有相对链接；知识层框中的具体规则版本也应改为角色与接口描述，符合不暴露、不中途绑定在用私人知识库的决定。

这是明确的文档修正。不过，指向样板不代表样板自身已经没有歧义，其中的人工确认顺序还需要统一，见下文重大遗漏 B2。

### M5：明确与 contracts 的对接——需修改

统一跨线契约的权威来源是对的，但需要两项调整：

- 原报告只列了来源信封、权威词表、读接口，遗漏了[契约区](../contracts/README.md)已经列出的**文件原生约定**，它直接关系到 M3 的迁移与还原。
- 区分记忆线内部的数据规则和未来两线共享的接口契约，不能把全部内部事件模型都变成等待另一条线定稿的事项。

阶段一提交契约提案可以接受；但[需求基准](requirements-baseline.md) §8 明确将 PAT 对接暂时挂起，不能因此要求一期完成跨线服务或等待全部契约冻结。当前内部规则应清楚，未来共享部分通过契约区协商。

## 原报告之外的三处重大遗漏

### B1：统一存储的权威归属与写入路径尚未落定

蓝图既写了统一存储，又把 MemHub 应用与 SDK 的分工列为“不阻塞冻结”的未决项。可以暂缓具体接法，但不能暂缓“最终以哪份记录为准、哪些入口可以修改它”。否则 MemHub、厚管线、人工编辑和 Markdown 镜像可能各自成为一份事实来源。

冻结前应明确：唯一权威记录、所有写入必须遵守的治理规则，以及索引、镜像、Skill 属于可重建的派生产物。具体 SDK 能否满足这些约束，在阶段一验证。

原报告 S2 的安全导入也应提升为首次真实导入前的必要条件。重复导入不得重复造记忆，失败不得破坏已有数据。蓝图“零产物成功即报警”也要区分合法去重后的零新增与异常漏写。

### B2：人工批准如何约束后续改写，尚未闭合

蓝图规定先人工确认再进入知识层，但[知识层样板](knowledge-layer-sample-spec.md)一处要求 inbox 只接收已确认结论，另一处又把人工确认放在收编时；维护者还允许是 Agent。这会导致“机器收编是否等于人确认”的不同实现。

因此，原报告的 S1 不应只是建议项。至少须明确：

- 人确认的是哪一版最终文本，确认人和时间如何留存。
- evolve 改写后不能自动继承旧文本的批准。
- 条目撤回、失效或被替代后，召回与已导出的 Skill 如何更新。

这不要求所有低权威加工都人工审批，只要求**自动加工不能悄悄获得或继承人工权威**。

### B3：真实记忆数据的存放与读取边界缺失

蓝图计划采集会话、命令、编辑和敏感动作，并导出到自有 Git，但没有明确运行数据仓与 PAT 设计仓的隔离，也没有规定各接入 Agent 可以读取哪些范围。

至少应声明：真实会话及行为日志进入独立私有数据存储；凭证不进入持久记忆和镜像；跨项目读取与外部模型加工有明确允许范围。当前只给外部评估器规定脱敏投影，还没有覆盖厚管线写入模型等数据出口。

个人系统用简单的范围配置就可以，不需要建设企业权限平台，但这个边界必须先定。

## 冻结条件与后续验证边界

**仅完成原报告原文的五项，还不能冻结。** 将 M1、M3、M5 按上述方式修正，落实 M2、M4，并补齐 B1—B3 后，可以冻结 v0.1，进入阶段一验证。

冻结所需的是成文的权威边界、治理约束和阶段验收标准，无需等全部系统建成，也无需重新选型。具体 SDK 接法在阶段一查实；真实跨厂商闭环、薄厚管线、冲突处理和镜像还原等能力在相应阶段拿出执行证据。后续验证失败应阻止相应阶段宣告完成，并触发局部修订。

本报告只形成评审意见；是否采纳、如何修订以及最终冻结，由用户裁定。
