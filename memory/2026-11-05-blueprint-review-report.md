## 结论

**v0.2 的方向可以保留，当前正文尚不能冻结为可执行蓝图。** 五条新增修订中，常设 Raw-RAG 对照与证据链题可以采纳，其余四条需要改写边界。最重要的缺口是“原始事件可重建一切”尚未落实为可靠的数据责任，以及原始检索、机器推导、人工批准三者的关系仍有歧义。

建议按本稿修成下一版草稿。原始记录与批准记录的归属、最低治理条件、公平对照和阶段完成标准写清，并处理文档冲突后，可以由用户冻结为**设计与实施基线**。实际保存、恢复与跨厂商召回能力分别在阶段一、二取得运行证据。阶段二仍须交付真实的厚管线最小闭环。

本评审采用项目冻结需求和用户裁定确定目标，采用当前蓝图判断缺口，采用固定版本源码与论文检查实现假设。知识层治理参考用于补充问题线索，入仓版以通用样板和公开来源表述，不携带实例专属信息。此次做了文档与源码核查，未运行 Hy、MemHub 或完整记忆链路。

已覆盖原文保存、薄厚管线、批准晋升、检索恢复、跨厂商读写、读取范围和审计要求。尚未系统评审通道消息路由、身份与会话映射、任务分工与交接、跨通道审批、长任务恢复、并发调度，以及记忆、任务状态、消息与审计之间的整体权威划分。上述事项需要以整体线执行蓝图和实际接入状态另行评审。

“MemHub 已有厚功能”可以支持沿用现成产品，却不足以证明 PAT 所需的原文保全、批准治理、共享范围与恢复能力已经具备。蓝图中“只亏数周工时”的估算也没有工作量或运行数据依据，建议改为待度量的集成、维护、推理和人工审核成本。

## 二、冻结前应修正的五组问题

### R1　原始记录的保全责任必须独立于加工是否成功

**位置**为蓝图第 35、37、43、58、75—76 行。这是数据主权与可恢复性的阻断项。[蓝图快照](https://github.com/gethlx/pat/blob/90aaa4d3988fd7e5ae05c8fe3490d09d46ab1ba4/memory/blueprint-spec.md)

**核验事实**是 Hy 固定提交 `45dbf46` 的消息写入路径先裁剪落库副本，assistant 默认超过 500 字符截断，tool 默认按 2048 字节保留头尾。同次提炼仍可收到完整 messages。上游测试也明确断言 lite、pro 和部分审计内容保留的是裁剪结果。本轮只阅读了这些测试，未执行它们。[裁剪函数](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/hy_memory/utils/raw_trim.py) · [写入代码](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/hy_memory/pipelines/writer.py) · [上游测试](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/tests/test_raw_trim_on_store.py)

此外，SDK 2.0.13 的变更记录说明部分提炼失败会回滚此次 raw 写入。MemHub 有自己的持久队列，能否保住特定入口的完整输入仍需查实。由此可判断，**不能仅凭 L1_RAW 的名字就把它认作 PAT 的完整原始档案**。这不代表上游所有路径都会丢失全部输入。[官方变更记录](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/CHANGELOG.md)

建议把约定 1 替换为以下文本，并在约定 2 与存储说明中引用这一处定义。

> **原始记录与重建。** 系统以用户持有、独立于加工结果的来源记录作为证据底账。来源记录保存本系统实际取得且获准保留的内容，并标明采集范围、缺失、裁剪和脱敏情况。导出物本身若是摘要，须保留其摘要性质与原始来源，不能称作完整会话。
>
> 来源记录先可靠保存，再进入 Hy 加工。加工失败、重试、归档或重建不得使已接收的来源记录丢失。Hy 的 raw、向量索引、摘要与图谱只有经过完整性核验，才能承担相应保存职责。薄厚管线共享同一套来源标识、记录归属和派生结果管理，不各自保有互相竞争的权威副本。
>
> MemHub 插件、SDK、人工编辑和恢复导入都遵守同一记录规则，各入口的写入责任须明确。镜像与 Skill 是派生交付物，不能成为绕过来源、版本和批准检查的第二条权威写入路径。
>
> 机器视图允许重算，重算结果须记录新版本。人工编辑的最终文本、批准与撤回记录、已交付 Skill 的对应版本属于必须保留的记录，不依赖模型重新生成。重建承诺覆盖原文、来源、批准、状态和必要历史的恢复，不承诺模型重跑产生逐字相同的文本。
>
> 原始事件日常只追加，纠正与状态变化另记事件。经用户授权的敏感数据清除按明确范围执行，并防止后续导入或备份恢复重新引入已清除内容。凭证在进入持久记忆前排除，保留必要的缺失说明。

**实施取舍**是先核验 MemHub 已有保存能力，能满足要求就复用。缺口可由现有导出或最小接入胶水补齐，不需要另建一套记忆引擎。具体物理目录、数据库和导出方式可在阶段一确定，但“谁承担完整原文和历史”必须在蓝图中先有明确责任。

### R2　人工批准要绑定版本，知识层不能仅凭位置自动授信

**位置**为蓝图第 48、50、53 行，以及知识层样板第 53、79—82 行。样板前文要求确认后投稿，后文却把确认放在维护人收录时，而维护人可以是 Agent。这一矛盾在 v0.2 仍然存在。[蓝图快照](https://github.com/gethlx/pat/blob/90aaa4d3988fd7e5ae05c8fe3490d09d46ab1ba4/memory/blueprint-spec.md) · [知识层样板](https://github.com/gethlx/pat/blob/90aaa4d3988fd7e5ae05c8fe3490d09d46ab1ba4/memory/knowledge-layer-sample-spec.md)

原始档案证明“某人在某时说过这句话”，不保证句子内容为真。机器生成的错误回答也是原始事件的一部分。另一边，人曾确认的知识也可能过时。因此，“可被 raw 推翻”应指原文能揭示提炼错误，不能解释成任何检索到的旧话都自动推翻当前决定。知识层通用样板中的记忆回写、Disputed 和 Outdated 机制提供了这方面的参考。[知识层通用样板](knowledge-layer-sample-spec.md)

建议将约定 4—6 中相关表述收拢为以下一处规则。

> **来源、确认与有效性。** 未经人工确认的机器提炼最高为 `inferred`，并引用实际依据的来源。原始载体标记为 `raw`，载体内的机器猜测不能因被导入而取得事实权威。`curated` 用于用户确认的经验结论，`approved` 用于按知识层准入规则接受且有对应确认依据的结论。处理等级、是否当前有效与证据是否支持结论分别判断，不以等级排序代替冲突核对。
>
> 候选门负责分诊。候选可以引用原话或包含机器草稿，但人工批准必须绑定展示给用户的最终文本版本，记录确认人、时间、范围和来源。经验候选经用户确认后进入 Wiki inbox，维护人按知识层规则整理收录。机器维护或合并操作本身不替代用户确认。
>
> evolve 或人工编辑改变已批准内容的含义时，形成待确认的新版本，不继承旧批准。旧版按原批准范围保留，是否失效另有记录。撤回、过时、争议与取代状态须进入召回结果，并更新对应 Skill 交付物。知识页不能仅凭处于 Wiki 目录就把其中全部句子自动标为已获人工批准。
>
> 原始证据与现有结论冲突时，保留双方、时间与出处，标明争议并按职责处理。检索到的历史文本作为背景证据呈现，不自动成为当前指令或新的行动授权。

这里的四级释义属于本稿建议，需要随蓝图一起确认。现有 Wiki 的整理流程继续由自身规则管理，接入层负责准确映射其已有来源和确认状态。

接入查实还应检查实际 evolve 开关与调度。固定版本 MemHub 文档包含 ultra 模式的夜间自动 evolve，蓝图的“受治理”必须落实到运行配置和写入边界，尤其要防止自动改写继承人工批准。[官方变更记录](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/CHANGELOG.md)

### R3　原文直查、真实数据镜像和审计需要明确读取边界

**位置**为蓝图第 29、54—60 行。v0.2 扩大了原文保存与查询能力，却仍只对外部候选评估器规定脱敏，没有覆盖厚管线写入模型、embedding、重排以及查询结果的外发。这直接影响真实数据第一次导入时的边界。[蓝图快照](https://github.com/gethlx/pat/blob/90aaa4d3988fd7e5ae05c8fe3490d09d46ab1ba4/memory/blueprint-spec.md)

JS／SQL 描述查询能力，MCP 描述如何向 Agent 提供工具，两者可以组合。Obelisk 展示了可用形态，尚不能证明 PAT 增加通用脚本执行面的成本和权限边界都已解决。[Obelisk 固定版本说明](https://github.com/tommy0103/obelisk/blob/1f8205b5b600516fe09ebea80d6983bcac1082b8/README.md)

建议替换镜像与查询面的相关句子，并为治理层补一条边界说明。

> **数据与访问范围。** 真实会话、行为日志和原始附件进入独立私有运行数据存储。开放格式备份覆盖来源与治理记录，Git 仅用于适合版本管理且获准同步的文本及清单。原始附件使用可迁移的文件存储并随备份校验。运行数据不写入 PAT 设计仓或未来公开仓。
>
> 接入时为每个 Agent 明确允许读取的项目和数据范围，跨项目共享须在允许范围内。过滤由查询入口执行，覆盖检索、按 ID 读原文、展开上下文和可编程查询。外部模型加工只使用该用途获准发送的内容，生成、embedding、重排和评估都按同一边界处理。
>
> **原文查询。** 正式提供按来源、会话、时间、项目和事件标识查询及展开原文的只读能力，优先通过现有 MCP／SDK 暴露。JS／SQL 可作为表达方式，但不能绕过同一读取范围、输出限额和审计，也不能取得任意文件、网络或写库权限。具体实现由阶段一核验后选择。
>
> **审计与召回呈现。** 行为审计可与记忆原料同流采集，已落盘审计记录不向被审计 Agent 开放改写接口。若实际运行权限无法阻止该 Agent 修改底账，应如实标记审计保障的局限。召回结果标明来源、版本、有效状态和当前会话关系，查询失败不得显示为无相关记忆。

这可以先用单用户的目录隔离、来源允许范围和受限接口实现。Open Duet 的 journal 权限边界与读写脱敏可作设计参照，具体效果仍要在 PAT 的真实接入环境验证。[Open Duet 固定版本记忆文档](https://github.com/Anil-matcha/open-duet/blob/3e167145881a835b790ec45f3bee6c343383058f/docs/MEMORY.md)

### R4　信赖门需要公平对照，也需要允许“尚无结论”

**位置**为蓝图第 46、65、67、79、86 行。当前说明把跨源合并认作厚管线独有能力，又只用被采用比例衡量主动浮现，会使验收偏向厚管线。[蓝图快照](https://github.com/gethlx/pat/blob/90aaa4d3988fd7e5ae05c8fe3490d09d46ab1ba4/memory/blueprint-spec.md)

Raw-RAG 本身包含检索、重排和 reader。论文仅支持其受测离线任务中的比较，未证明 PAT 的厚管线一定胜或一定败，也未证明跨源推理必须在写入时完成。论文还明确说明，残余差距不能全部归因于提炼信息损失。[Raw-RAG 原文 §5.3、§6.1](https://arxiv.org/html/2610.30755v1#S5.SS3)

**本评审的推断**是，对原始证据检索后由同一个 reader 组合多来源内容，足以构成跨源任务的合理对照。主动浮现则可让两边使用同一事件或定时触发，再比较检索原文和利用预提炼记忆的效果。裸检索器不会自己调度，预提炼记忆本身也不等于调度机制。

还有一个实质混杂因素。固定版本 Hy 的提炼输入可能比其已保存 raw 更完整，默认 raw 搜索又可能只含 active，排除已处理为 shadow 的记录。直接拿产品模式分数比较，可能把输入缺失算成算法差异。[写入路径](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/hy_memory/pipelines/writer.py) · [SDK 2.0.14 与 MemHub 1.0.6 变更记录](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/CHANGELOG.md)

建议替换对冲四及未决项 5。

> **厚功能信赖门。** 阶段二完成厚管线最小闭环，并对拟默认启用的功能做对应任务的对照。Raw 对照使用同一批获准来源、同一时间截面、同一 reader 和可比预算，通过检索、重排和必要上下文展开完成任务。主动浮现两边采用相同触发条件与观察窗口。若生产方案同时用 raw 与厚记忆，比较完整方案和移除该厚功能的版本。
>
> 第一轮对照前锁定题集、判分依据、资源预算、最低收益和不可退化项。输入截断、状态过滤和历史时间范围须对齐。按功能记录胜出、未胜出或证据不足，不用一个总分替代全部结论。只有达到事先约定收益且满足底线的功能进入默认依赖，其余保持实验可选或关闭。
>
> 问答和跨源任务同时检查答案正确性与证据支持。主动浮现同时报告建议数量、被采用数量、错误或打扰、漏掉的有效机会和实际覆盖，不能只报采用比例。每轮记录写入及查询成本、延迟与人工审核负担。小样本或结果波动不足以判断时，保留“证据不足”，扩大观察后再决定。

收益可以体现为质量提升，也可以是在预先约定的质量容差内显著降低成本或延迟。具体数值由阶段一根据实际任务确定并在首次比较前锁定，本稿不虚构收益阈值。

对修订说明②的三条理由分别判断如下。

| 原理由 | 判断 |
|---|---|
| Raw 在结构上做不到主动浮现与跨源合并 | **不同意该绝对表述。** 触发机制与推理发生在写入还是查询时，是不同维度，应分别验证。 |
| MemHub 提供现成厚管线，因此建造成本论据不成立 | **需修改。** 可省去从零实现引擎，接入、治理、运行和维护成本仍存在。 |
| 改里程碑会使厚管线被无限推迟 | **同意保留防拖延约束。** 用户已有明确裁定，阶段二仍必须交付真实厚管线闭环。 |

### R5　治理底线和最小评测不能等到阶段三、四才出现

**位置**为蓝图第 37、44、55—57、64—67 行。阶段二已接收真实数据，阶段三才写轨迹与看门狗自动化，容易让实现者把最低留痕、冲突处理和告警也一并后移。阶段二要求“测过”，阶段四才写“评测集上线”，同样存在职责空档。[蓝图快照](https://github.com/gethlx/pat/blob/90aaa4d3988fd7e5ae05c8fe3490d09d46ab1ba4/memory/blueprint-spec.md)

失败看门狗还存在明确误报风险。合法重复导入、模型判定无可提炼内容，都可能成功且零新增。上游已区分正常无变化和模型失败，蓝图应检查输入去向，而非把零产出一律当失败。[官方变更记录](https://github.com/Tencent-Hunyuan/Hy-Memory/blob/45dbf46545fc55fc7e331c09523b740cd1e7a944/CHANGELOG.md)

建议在约定 2、6 补充以下最小规则。

> 同一来源事件具有稳定身份。重复导入或失败重试不重复造记忆，SDK 每次尝试的请求标识与来源事件标识分开记录。写入版本冲突须拒绝并重试，无法自动解决的语义冲突保留双方并交人处理。内容相同但来自不同会话的事件不能仅凭正文相同合成一个来源。
>
> 每批处理说明已接收、已持久化、待处理、合法跳过、隔离和失败的输入去向，并能回指原事件。零新增须有可检查的去重或无变化理由。捕获中断、存储未确认和模型失败分别显露，不误报成功。
>
> 支持的接入端在新任务开始及关键上下文变化时执行检索并记录返回、注入、无匹配或失败。无法强制触发的入口标注为尽力支持。召回证据只证明检索与注入发生，不证明模型理解或采纳。
>
> 驳回率、失败数与零召回时长记录样本数、窗口、覆盖范围和原因。它们触发诊断与评估，不直接证明需要升厚或降薄。零召回可能来自采集、权限、过滤或检索故障，排除这些原因后再判断条目价值。

构建顺序建议替换为下表。

| 阶段 | 最小交付与完成条件 |
|---|---|
| 一　设计冻结与接入查实 | 冻结已明确的边界。锁定 Hy SDK 与 MemHub 各自版本、模式、模型及关键配置，区分发行版和主分支。查清完整来源保存、所有写入口、raw 状态过滤与导出能力，用少量可检查样例定位差异。说明差异的补齐方法和下阶段范围，形成阶段二的最小题集与评测口径。 |
| 二　薄厚真实闭环 | 薄管线 Coding 与厚管线 Chat 均有真实输入、保存、召回证据，至少由两个不同厂商 Agent 完成写入与读取交接。原始记录、最小批准流程、幂等、冲突可见、范围过滤、必要审计和失败显露同时可用。完成 Raw 对照和独立恢复演练，记录各厚功能是否进入默认依赖。 |
| 三　覆盖与自动化 | 扩展 web 导出 ETL，按实际取得内容说明完整性。完善候选门、晋升、衰减、轨迹和看门狗自动化。阶段二已有的最低保障继续有效，新增入口通过同类回归。 |
| 四　长期优化 | 扩充场景、长时间观察与证据链题。每次调参、模型或关键规则变化保留 Raw 对照及关键治理回归，更新收益记录。90 天观察信号在满足观察窗口后才解释。 |

阶段二的“厚管线闭环完成”和“某厚功能获准默认使用”分别记录。对照未胜出仍可完成实验性闭环，但不能宣称该功能已被实证证明有效。数据保全、批准或读取边界未通过，则相应阶段验收不通过，应局部补齐。

## 五、阶段一、二应取得的最小运行证据

以下是修订稿建议的验收用例，本轮均未执行。

| 用例 | 通过证据 |
|---|---|
| 长原文与附件 | 超过裁剪阈值的 assistant、tool 及含附件的事件，分别核对来源档案、加工副本和备份。获准保留的内容及引用完整，已有缺失如实标记。 |
| 重复、失败与中断 | 同一事件经 hook／文件同步／重试到达时不重复建记忆，来源不丢。模型失败、合法零新增、采集中断具有不同结果和可追踪输入。 |
| 批准与改写 | 批准版本 A 后 evolve 产生 B，B 不继承批准。撤回 A 后召回和 Skill 不再把 A 当作有效决定，恢复备份也保持撤回状态。 |
| 读取范围与自我引用 | 越界来源在检索、原文展开和可编程查询中均不可读。当前会话及其派生摘要不能冒充独立历史证据。历史中的指令文本不升级为现时授权。 |
| 原始证据公平对照 | 两边拥有相同时间点、来源范围和允许状态的输入，不因 raw 截断或 shadow 过滤制造差异。质量、成本、延迟及浮现覆盖按预定口径记录。 |
| 最终一致与跨厂商召回 | 一个 Agent 写入或批准后，另一个厂商 Agent 在声明的同步完成点后可读到相应版本。同步延迟或失败可见，不把旧视图误报为最新。 |
| 冲突与检索触发 | 并发版本冲突可见、语义冲突保留出处，新任务有实际检索记录。无匹配与服务故障可区分。 |
| 独立恢复 | 在独立位置恢复，核对内容、稳定 ID、来源、批准、有效状态、必要历史及原始引用，再做代表性查询。索引可重建，不能只比条数。 |
