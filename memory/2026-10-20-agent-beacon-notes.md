# 设计笔记：Asymptote-Labs/agent-beacon（2026-10-20，用户点题深读）

> 定位纠正：Beacon 本体是 **agent 遥测/安全观测平台**（端点 agent、OpenTelemetry 扩展的统一事件模型、本地 JSONL、风险检测规则库——prompt-injection／credential-access／approval-abuse 等、向 SIEM/观测平台转发、企业 Cloud 版）。"跨 harness 记忆"是其上一个 opt-in 子系统。与本项目的交集只有一块：**编程场景的跨工具经验捕获**。MIT，1.8k★，有正式 release 与 Homebrew 分发。

## 它的记忆环（原文核实）

捕获 traces（20+ harness 的完整会话：prompt、响应、工具调用、命令、编辑、审批、token）→ 产生 candidates（评估器打分或人工从 trace 写 lesson）→ **人工 review** → approve 进 project memory → 经 MCP 或**编译成 Agent Skill** 供后续 agent 复用。全程刻意 review-gated：评估器只给概率排序分类，绝不自动晋升。评估器（Jev）用 typed yes/no 问题（任务成功了吗／含可复用纠正或调试模式吗／lesson 有 trace 证据吗），门槛设计有巧思：**task_success≥0.50 是前置条件而非一票**，均值≥0.60 才成 candidate——失败任务不能靠其他项的高分被抬进记忆。评估显式批量运行、只发脱敏投影，捕获路径（hooks）里绝不调外部评估器。

## 可借鉴（落到本项目蓝图）

1. **统一事件模型先行**：先定一套跨来源的规范化事件 schema，解析器往里映射。我们输入层的 provenance 信封应升级为正式事件模型（Hy 的导入、web ETL、deja-vu 式索引共用一套）。
2. **候选制＋量化门槛**：咱们的"经验→知识晋升通道"一直缺具体机制——它的"成功前置＋阈值＋概率连同 provenance 一起存"可以直接借鉴，把人的审核负担压到高信号候选上。
3. **捕获与评估分离**：捕获便宜、本地、常开；评估显式、批量、脱敏。信任分级清晰，值得写进输入层规矩。
4. **记忆编译成 Skill 交付**：除 MCP 外的第二条复用通道——把已批准的经验编译成 harness 原生加载的 Skill。咱们接入层可补此形态。
5. **动作级轨迹**：经验原料不止对话，还有命令、编辑、审批等行为事件；编程场景的可复用教训主要藏在"做了什么"里。

## 对本项目的挑战（两条真问题）

1. **治理对象之问**：咱们的治理层只盯记忆（导入/进化任务别静默失败），Beacon 提示还有一层没设计——**agent 行为本身的观测与审计**（谁执行了 risky 命令、谁碰了凭证、谁批了什么）。fleet 里 agent 越多（Muse、box 上的 Grok 老邪、未来的 PAT agent），"我的 agent 都干了什么"越是真实治理问题。是否纳入本项目射程，待用户定；至少轨迹层可以一鱼两吃（记忆原料＋审计）。
2. **引擎重量之问**：Beacon 用端点＋JSONL 的薄层就实现了跨 harness 捕获＋审核制记忆，是"经验层需要重型认知引擎"的一个反例。边界在于：它只做编程场景的 lesson 型记忆，没有 Hy 那种语义蒸馏与分层认知。所以挑战是分场景的——逼咱们回答：**每个场景到底需要多厚的引擎？**（Coding 场景也许薄层够用，Chat/Working 才需要 Hy 的深度。）

## 不借的

企业舰队那一整套（MDM、SIEM 转发、SSO/RBAC、Cloud 默认开户引导）——与 OpenViking 同理，尺寸不对；且其 onboarding 默认推 Cloud、本地是 opt-out，与本项目主权默认相反，只可借机制、不可借默认值。

## 后续（2026-10-20，用户裁决与老邪答复）

- **挑战一（行为轨迹/审计）**：用户批准并入蓝图——治理层增设"行为轨迹"格，轨迹层一鱼两吃（记忆原料＋审计底账）。
- **挑战二（引擎厚度）**：老邪已向用户解释并入方式——经验层改为"场景×厚度"分配：原料越结构化、引擎越薄（Coding 走薄管线：捕获→候选门→审核→lesson/skill，Hy 的 Coding 演化链作升级件，写明触发条件）；原料越是自然对话、引擎越厚（Chat/Working 用 Hy 全量分层认知＋evolve）。厚薄两条管线共用事件模型、provenance、权威词表、晋升通道与治理层，只差"理解加工"一段；另配厚度升降级条款与分场景度量的回归评测。待用户确认后写入蓝图。
  - **风险面（2026-10-21，用户追问后补全，老邪原汇报只报收益）**：① 一致性税——两条管线的产物须在下游行为一致，跨管线冲突无人天然负责，"共用层"须严格成文否则名存实亡，是永久维护成本；② 分档押错——场景边界在真实数据里是糊的（对话里有代码决策、编码会话里有个人偏好），押错则薄管线攒下浅层 lesson 债，日后要重加工；③ 候选门的盲区——Beacon 的"成功前置"内含价值判断（失败任务无可晋升教训），但**失败教训恰是最贵的一类经验**，照抄会系统性滤掉试错经验；且本地近似实现的概率不校准，有 cargo cult 风险（形式像 Jev、数字不可信）；④ 薄先行 cannibalize 厚集成——"先跑薄的"极易变成永久方案，Hy 的核心价值（Chat/Working 厚管线）被无限推迟；⑤ 若厚薄连存储都分叉，"统一记忆"会在自家系统内部重新碎片化。
  - **对冲设计（若并入则必备）**：分档**只分加工深度、不分存储**——两条管线产物都写回同一事件模型与同一存储，薄管线是厚引擎的前置过滤而非平行系统；升降级触发改成可观测硬信号（如人工驳回率、跨项目召回失败计数），不凭感觉；候选门为失败任务单设问题集与标签（failure-lesson），不直接照抄成功前置。
  - **裁决（2026-10-21，用户）**：**带对冲并入**。连同挑战一（行为轨迹入治理层），两条一并写入项目蓝图草案 v0.1（`project-blueprint-draft.md`）；对冲另加一条执行纪律：厚管线（Chat）最小闭环设为蓝图阶段二的硬里程碑，不得以薄管线"够用"为由顺延。
- **评估器/Jev 实情**（多源核实）：Jev 是 TypeSafe AI（创始人 Diogo Almeida，ex-OpenAI）2026-09-15 发布的 "System One" **决策模型**——非自回归、不生成文本；输入 state＋typed 问题（Noul 是非概率／Choice 选择／Score 量表），单次并行返回**校准过的概率**（训练法 RLCD，专为概率诚实优化）；70–500ms、$0.042/百万输入 token、output 免费；纯托管 API（64k 上下文）。Beacon 的用法：把 trace 的**限量脱敏投影**＋三个是非题发给它，概率连同评估器型号与用量写入 provenance；门槛 task_success≥0.50 为前置、均值≥0.60 成 candidate；评估器不写 lesson 文本，人批时才写。对本项目可借鉴的是**模式**（类型化问题＋校准概率＋阈值逻辑）而非必须依赖该托管产品——主权场景可用其脱敏投影做法，或以本地模型近似实现。
