# 多智能体共享记忆系统 · 项目蓝图（草案 v0.1）

> 状态：**草案，待用户审定冻结**（2026-10-21）。依据：`requirements-baseline.md`（已冻结，含 2026-10-20 修订）。底座已定：混元 Hy-Memory（MemHub 现成用＋SDK 集成，不 fork）。本蓝图把此前各轮结论收拢为一张施工图：适配评估见 `projects-fit-2026-10-20.md`，社区实证见 `community-eval-2026-10-20.md`，设计借鉴见 `deepdive-hy-openviking-2026-10-20.md` 与 `design-notes-agent-beacon-2026-10-20.md`。

## 架构总览（五层）

```
┌ 接入层 ────────────────────────────────────────────────┐
│ MemHub 插件（已覆盖工具）｜ MCP/SDK 直连（自有 agent）   │
│ 记忆→Skill 编译交付 ｜ Gateway 模式（预留：封闭 agent） │
├ 知识层（已建成，不动）─────────────────────────────────┤
│ LLM Wiki（git 仓，WIKI_RULES v4）＝最高权威             │
│        ▲ 单向晋升（候选→人确认→inbox→策展）             │
├ 经验层（Hy 引擎，加工分档、存储统一）──────────────────┤
│ 厚管线：Chat/Working —— Hy 分层认知＋evolve（受治理）   │
│ 薄管线：Coding 先行 —— 捕获→候选门→审核→lesson         │
│ 统一存储与事件模型（两条管线产物同仓同格）              │
├ 输入与共存层 ──────────────────────────────────────────┤
│ MemHub 导入（本地 10 工具）｜ web 四家导出 ETL（自建）   │
│ deja-vu 式索引（未覆盖 harness 补位，可选）              │
├ 治理层（横切，全自有）─────────────────────────────────┤
│ provenance 信封＋权威词表 ｜ 行为轨迹（审计）｜ 检索轨迹  │
│ 衰减与归档 ｜ 失败看门狗 ｜ 数据镜像（开放格式入我方 git）│
└────────────────────────────────────────────────────────┘
```

## 关键设计约定

**1. 统一事件模型（输入层契约）。** 一切输入先归一成事件再入层：字段至少含 id、时间、来源（厂商／harness／会话）、行为主体、事件类型（发言／工具调用／命令／编辑／审批／…）、内容引用、provenance（原始载体与导入路径）。解析器（MemHub 导入、ETL、索引器）各自适配此模型——借 Beacon 的"schema 先行"。

**2. 经验层：只分加工、不分存储（2026-10-21 用户裁决，带对冲并入）。**
- 薄管线（Coding）：捕获→**候选门**→人工审核→lesson（以 Skill／MD 形态交付，并写回统一存储）。
- 厚管线（Chat／Working）：Hy 全量分层认知；记忆写入先用前沿大模型，混元专用 30B 模型列为后续成本优化选项，不进一期。
- Hy 的 evolve 默认收着用：进化动作必须留痕、可回滚，按治理层规矩配置，不用其默认无监督模式。
- **对冲一（防碎片化）**：两条管线产物同仓同格，薄管线定位为厚引擎的前置过滤，不是平行系统；下游召回只面对一个存储。
- **对冲二（防押错）**：厚度升降级用硬信号触发——初始参考值：薄管线 lesson 人工驳回率滚动超过 30% → 评估该场景升厚；跨场景召回失败案例累计达 10 例 → 评估升厚；厚管线某场景条目 90 天零召回 → 评估降薄。（数值是初始值，运行后按数据校准。）
- **对冲三（防拖延）**：厚管线（Chat）最小闭环是阶段二的**硬里程碑**，不得以薄管线"够用"为由顺延。

**3. 候选门规格（晋升与 lesson 共用）。** 模式借 Beacon＋Jev：类型化问题＋校准概率＋阈值，概率连同评估器身份与用量写入 provenance；评估器只分诊、不写文本，文本由人批准时产生。**修正 Beacon 的成功前置**：失败任务单设问题集（含"失败原因是否明确／教训是否可复用"），产出打 failure-lesson 标签——试错经验不被系统性过滤。实现优先本地（小模型须验证其概率可用性，不可信则退回纯人工分诊）；外部评估服务（如 Jev）只作可选项，且必须走脱敏投影。

**4. 知识层与晋升通道。** Wiki 维持最高权威与原有规则；晋升单向：经验层候选池→人确认→wiki inbox。召回侧可跨层检索，但结果须带层级与权威标注，经验不得冒充知识呈现。

**5. 治理层细则。**
- 权威词表四级：raw／inferred／curated／approved，全层通用。
- **行为轨迹（2026-10-20 用户批准并入）**：记录 agent 行为事件（命令、编辑、审批、敏感动作打标，风险分类词表借 Beacon），与记忆原料同一事件流，一鱼两吃（经验来源＋审计底账）。
- 检索轨迹：谁、何时、召回了什么，留痕备查并反哺衰减计算。
- 衰减：经验按召回曝光计龄，长期零召回者归档（可见、可恢复，不静默删除）；归档动作本身入轨迹。
- 失败看门狗：导入／进化类任务的"成功"必须附产物证据（条数、落盘校验），零产出报成功即告警——针对赛道通病"静默失败"设防。
- 数据镜像：经验层存储定期导出为开放格式（MD／JSONL）入我方 git 仓，作为主权保险与搬家通道；镜像完整性纳入看门狗检查。

**6. 接入层梯队。** 已被 MemHub 覆盖的工具走其插件；自有 agent 走 MCP／SDK 直连；已批准 lesson 可编译为 Agent Skill 交付（借 Beacon）；Gateway 代理注入只预留接口与设计注记，一期不实现（触发条件：出现只能经 API 链路接入的封闭 agent，PAT 侧概率高）。

## 构建顺序

- **阶段一**：蓝图冻结；假设查实（Hy 的 SDK 写入协议、MemHub 本地数据目录与导出形态、事件模型字段细化）——查实是为蓝图落地，不是否决程序。
- **阶段二**：薄管线（Coding）跑通＋**厚管线（Chat）最小闭环跑通（硬里程碑）**；统一存储与事件模型落地；数据镜像开跑。
- **阶段三**：web 四家 ETL；晋升通道与候选门完整形态；治理层自动化（衰减、轨迹、看门狗）。
- **阶段四**：调试优化期——分场景回归评测集（借 AML 方法论）上线，此后每次调参/改规则过评测再合入。

## 与需求基准的映射（摘要）

跨厂商（基准§1）→ 接入层梯队＋事件模型；两层分治（§2）→ 经验/知识分层＋晋升单向；慢层先行（§3）→ 全层无实时同步设计，快层仍观察；共存 ETL（§4）→ 输入层 MemHub＋自建 ETL；主权（§5）→ 数据镜像＋开放格式＋本地优先；治理底线（§6）→ 治理层五件；知识层形态（§7）→ 原样保留；PAT 预留（§8）→ Gateway 预留＋事件模型可扩展，不进一期实现。

## 未决项（不阻塞蓝图审定，阶段一查实/细化）

1. Hy 存储的实际格式与官方导出能力（决定数据镜像的实现方式）。
2. MemHub 与 SDK 的分工边界：MemHub 用到应用层为止，还是只取其导入能力、召回走 SDK。
3. 候选门本地实现的概率可信度验证方法。
4. 行为轨迹的采集范围与端点形态（哪些 harness 能采到动作级事件、采不到的如何降级为会话级）。
