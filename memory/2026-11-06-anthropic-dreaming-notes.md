# 设计笔记：Anthropic《The components of agent memory》与 dreaming（2026-11-06）

## 来源与核验

- 引入帖：@PawelHuryn 2026-11-06 帖（个人实践感想：用仓库内 .md 文件自管 agent 记忆＋自家 harness Mini Harness 新增 /dream 命令）。帖子只作线索，不作证据。
- 一手源：Anthropic 工程博客《The components of agent memory》（2026-11-06 发布），已读全文。内容为厂商自测与经验总结，样本普遍小（Pokémon 对照每模型一轮、wiki 评测 25 题），按本项目惯例只作存在性证据。
- 帖子转述校准一处：帖称"规定模型怎么写记忆有害"。原文结论分两面——预设死规则（如"只记失败"）使强模型在 CL-Bench 上大幅丢失记忆增益；但对较弱模型，明确引导（先读记忆、验证自己的理论）使分数近乎翻倍。多模型混编的系统里，这条须按模型档位分别适用，不能只记一半。

## 原文要点

**记忆的形态与写入判断**
- 记忆＝跨会话保留的笔记文件（memory notes）。写入时的显著性判断本质是"预测未来会需要什么"；强模型已能闭环：记录失败→提出理论→验证→沉淀为带依据的规则（"这条规则＋我如何知道它是对的"）。
- "更好的模型记得更少"（Pokémon Red 对照，约 10,000 步时点）：弱模型不加选择地存档（413 个文件／225 个文件夹，得 1 枚徽章），强模型只存 9 个文件＋一个 global.md（得 4 枚徽章）。判据：能从环境当场读到的状态（金钱、位置）存了纯属冗余且快速过期；只有模型自己推导出的策略、计划、已验证规则不存在于环境中、必须写下来。
- 索引层纪律：常驻注入层必须小——Claude Code 只加载 MEMORY.md 的前 200 行或 25KB 作为索引（示意"知道什么、在哪找"），细节留在下层文件。

**dreaming（离线整理）的五项职责**
1. **核错**：拿笔记回原始记录（transcript）核对，抓出写错或已漂移的条目并改写（PokéCenter 位置写反的案例：未纠错的运行三次掉回同一陷阱后放弃，纠错后直达目标）。
2. **建表示**：在原始语料之上增量构建 wiki 式互链页面（合并重复、回源核对主张）。350,000 文件语料上，128 个 dreaming 会话把 25 题得分从 13% 提到 48%（仅用 wiki）；wiki＋检索 61% ＞ 检索单独 53–54%；多文档问题上 wiki 87% 对检索 73%；wiki＋检索每题省约 20,000 token。**反例同等重要**：单文档可检索的任务上 wiki 零增益；wiki 单独用（48%）反低于检索单独用；有一次 wiki 长得比语料本身还大——抽象失败。
3. **升降级**：把笔记在记忆层级间浮动，维护常驻注入层的小体积：细节降层、留链接，重要项升入顶层。
4. **目标聚焦**：引导记忆生长的指令可由"反思失败→改指令→重建"的循环改进。事故一例：构建 wiki 时多个 agent 并发写同一张共享汇总表，互相覆盖，57 个关键事实只剩 41 个（72%）；改成"每份合同一页、单个写者、逐字引用条款而非汇总转述"后达 100%。
5. **补缺口**：跨会话找共性模式与共性错误；修断链（指向不存在页面的链接改指或补页）、补索引。

**未决问题（原文自陈）**：写入时机（当场写分心 vs 做梦写不及时）；保持记忆新鲜（把 dreaming 集中在易变信息上、频率按访问频次调）；表示层要花算力维护且会累积错误——检索作地基＋表示层作增益，是他们的当前答案。

## 对本项目的影响

**印证已定设计（不新增动作，登记备查）**
- 文件原生＋小索引常驻＋领域文件按需打开：与本项目知识层形态及分级加载约定一致；200 行／25KB 可作本项目**索引层体积上限的初始参考值**（此前蓝图只定"分级"、未定体积纪律）。
- "检索为地基、表示为缓存"：与蓝图 v0.2 约定 1（原始事件为真相源、提炼产物为视图／缓存）同构，厂商侧再添一证。
- 增益出现在跨源问题上（87% vs 73%）、单源可检索任务零增益：支持 v0.2 信赖门的做法——厚功能增量按功能分指标验，跨源合并的增量就该在跨源题上验。
- 多写者并发覆盖事故与解法（单写者＋逐字引用）：与知识层单维护人制、原文存底规则独立同构，属外部事故反向验证。

**可收零件：dreaming 整理作业（建议冻结蓝图时作治理层组件注记议入，不单独改版）**
- 本项目治理层现有衰减、归档、看门狗，但没有一个具名、定期、对原始记录干活的整理工序；Hy 的 evolve 是引擎内部机制、按蓝图本就收着用、不算我方工序。dreaming 的五项职责恰好把这道工序的规格开全，可直接落成治理层组件：定期运行（频率按信息易变性与访问频次调档）、对原始事件核错改写（改写走取代语义、不静默删除）、合并重复、修断链、维护索引层升降级与体积。
- 约束照 v0.2 现有规矩：dreaming 产物封顶 inferred；其"核错改写"不得越过原始事件（真相源只增不改，改的是视图层）；整理作业本身的动作入行为轨迹备查。

**写侧判据一条（候选门问题集候选）**
- "未来会话能否从原始记录／环境当场重新推导？能，则不值得提炼。"——原始层照单全收不受影响；此问只用于提炼与晋升侧的取舍，与候选门现有问题集同层，待阶段一细化候选门时议入。

**不采纳／边界**
- 该文是单厂商、单 agent 的记忆设计，对跨厂商共享（本项目立项问题）只字未提；其 memory 目录仍是产品内形态。Huryn 帖"不要把记忆交给实验室"的立场与本项目主权原则一致，但属立场表态、非证据。
- 引导实验的完整结论是双面的（见来源校准）：本项目接入层对不同档位模型的引导强度应分档，此点记入接入层细化备忘，不改变候选门"只分诊、不写文本"的定位。
