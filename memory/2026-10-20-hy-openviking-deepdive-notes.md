# 深扒报告：腾讯 Hy-Memory 与 OpenViking（抛开协议）

> 日期：2026-10-20。用户点题两件：① 深扒 Hy-Memory；② 确认 OpenViking 是否因协议被放弃，并抛开协议评其功能与口碑。证据标准同前（独立／亲手／带日期优先，厂商数字只作存在性证据）。

## 一、Hy-Memory 深扒：它比"观察名单"重得多

### 真实形态：三层开源（2026-10-16，Hy Memory 2.0）

| 层 | 内容 | 状态 |
|---|---|---|
| 专用模型 | **Hy-Memory-30B-A3B**（HF 开源，Apache-2.0，另有 FP8／GGUF 量化版）：专为"记忆读写"训练的模型——先用 on-policy 蒸馏教各框架的写入协议，再用归因强化学习优化"写下的记忆对未来答题的贡献"（arXiv 技术报告）。约 3B 激活参数，GGUF Q4 约 18GB，**可本地跑**（Ollama／vLLM，OpenAI 兼容接口） | 已发布 |
| 框架 | **hy-memory 2.0.4**（PyPI）：三场景管线——Chat（L0–L7 分层认知记忆）、Working（事实＋可复用经验双层）、Coding（版本演化 diff 链）。LLM 与向量端点可自选，不绑专用模型 | 已发布 |
| 应用 | **MemHub**（Mac App＋CLI，v1.0.4／cli 1.0.5，有正式 release）：local-first，授权后**导入 10 种 AI 工具的历史会话**（WorkBuddy、Cursor、Codex、Claude Code、OpenCode、OpenClaw、Qwen Code、Pi、Hermes、DeepSeek Harness），新会话持续同步汇入，插件化召回回注各工具 | 已发布 |

### 为什么它对本项目格外相关

MemHub 的形态几乎就是冻结基准 §4 的产品化：**"授权导入各工具历史＋本地数据目录＋跨应用统一召回"**——咱们设想的"导出 ETL＋本地自有层"，它以产品形态先跑出来了（管的是本地 harness 落盘，与 deja-vu 同路线但做成了完整产品＋治理：仓内有 memory_visibility 可见性体系）。另外专用记忆模型本地化意味着蒸馏环节不必依赖云端大模型，与数据主权相容。

### 证据与口碑（首周）

- **厂商成绩**（只作存在性证据）：四套基准对比 Mem0／MemOS／EverOS／OpenViking 等自报第一；专用模型在 20% 子样本上宏观均分 55.49%，称高于 Opus 5 的 54.62%——未经独立验证；但注意 55 分这个量级与 AML 受控榜首 58 分同一水平面，反而比"94.6%"那类数字可信。
- **腾讯内部已落地**：金融（自选股）、资讯（腾讯新闻）、知识管理（iWiki）、办公等业务有专项评测数据（厂商口径）。
- **独立实测已出现**：韩国 YouTuber 2026-10-19 在 M3 Max 本地安装（Ollama＋GGUF），自设 6 周跨度／8 对话／5 个陷阱／10 问的小测，**打 5／10**：主要弱点是**信息变更类问题**（旧事实更新不灵），韩语记忆被存成英文，加一行提取规则后改善。小样本，但真独立、真动手。
- **首周 bug 密度不低**（issues 原文）：`evolve()` ultra 模式永不推进（#88，745 条事实反复聚成同一簇）；Codex 导入 >2GiB 会话文件失败（#102）；历史导入被单条超长消息卡死（#68）；记忆输出语言写死简体中文（#67）、UI 仅中文（#80）；macOS App v1.0.2 无法启动（#37）；修订记忆触发唯一约束冲突（#105）。产品是真的，粗糙也是真的——v1 第一周的典型状态。

### 修正评级

从"零验证、纯观察"上调为**观察榜首位且分量加重**：形态与本项目需求的贴合度全场最高（导入＋本地＋跨工具＋专用模型），背书是混元团队＋内部生产落地。仍不进选型的原因只剩：太新（以周计）、变更类记忆弱点已被独立实测点名、evolve 等核心算法有活 bug。**观察触发点**：AML 第二轮成绩、MemHub 1.1+ 的稳定性口碑、evolve／导入类 bug 的修复速度。若三项过关，它就是决赛圈的种子。

## 二、OpenViking：协议问题确认＋抛开协议的评价

### 协议到底卡在哪

是的，放弃原因就是协议：**AGPL-3.0**。具体毒性在 §13"网络 copyleft"：自己用、内部用完全合法免费；但只要**把基于它的服务通过网络提供给别人用**，就必须向使用者提供整个组合工作的完整源代码。本项目留了自研商业化路径（冻结基准 §5），一旦将来拿它做对外产品，要么开源自己的产品，要么侵权——没有中间态。字节理论上可双许可授权，但未见公开提供。所以排除是按用户自己的基准执行的，不是"AGPL 不能用"，是"AGPL 毒死商业化选项"。同理被刷掉的还有 basic-memory（AGPL）、honcho（AGPL）、ByteRover（ELv2）。

### 抛开协议：功能评价（全场最强，没有之一）

- **统一上下文数据库**：记忆、知识 RAG、Skill 装进同一个**虚拟文件系统**（`viking://` URI、目录递归检索），不是三套拼凑。
- **分层加载 L0／L1／L2**：每目录自带摘要（~100 tokens）／概览（~2k）／全文，agent 先判相关性再读全文——其 LoCoMo 厂商评测中三种 agent 接入准确率 80–83%（原生记忆仅 24–57%），输入 token 降 34–91%（厂商数据，独立复现缺位）。
- **经验记忆有实测增益**：tau2-bench 任务成功率 +6.9／+11.9 个百分点（厂商评测）。
- **Gateway 模式**（2026-10-09，v0.5.0 Beta）：改一个 base URL 的代理注入，逐字回放保证 prompt cache 命中——接入成本全场最低的设计。独立 YouTube 拆解的评价：值得试，但 Beta、无人发布过其独立召回数据。
- **自进化**：每会话后自动压缩、抽取长期记忆、更新上下文库；检索轨迹可视化可调试。

### 口碑与健康（G 维度）

- 字节跳动火山引擎团队（TikTok 向量检索基础设施的班底），仓龄 2026-01 至今，40.4k★、3,245 forks、**295 位贡献者**、近 90 天 5 个 release、12 个作者的日级提交速度——工业级维护，全场无出其右。
- **6,400+ 个 issues** 是双刃剑：真实大规模使用的证据，也是复杂度事故面的证据——Delta 表无界增长到 9.2GB 触发 OOM（#6249）、会话列表超 1,000 条静默截断（#6326）、Gateway 静默降级（#6283）、任务成功误报（#6240）。"静默失败"通病它一样有，且因为体量大，坑都在深水区。
- 独立深度长测仍稀缺（英文覆盖以讲解型内容为主，部分疑似投放）；安装不轻（Python＋Go＋C++ 核心、需 VLM＋向量模型）——themenonlab 的定性准确："这是基础设施，不是库"。

### 定位结论

若本项目哪天明确**放弃这一层的商业化**，OpenViking 立刻是功能面第一名；在此之前，它的正确用法是**头号设计参考**——L0/L1/L2 分层加载、viking:// 文件范式、Gateway 注入模式，三样都值得抄进自研设计。协议这道门，替用户把着，不松。

## 再附（2026-10-20，用户问）：OpenViking 设计中我们没想到的可借鉴项

**真空白（3 项）**：
1. **Gateway 代理注入＋缓存保真**：在 harness 与模型 API 之间架代理，每轮自动检索记忆并拼到最新消息尾部，且注入内容逐字回放以保住 prompt cache 命中。此路径**不需要 harness 配合**（任何 API-key 客户端可用），与我们已有的 MCP／skill／ETL 三条接入路互补，是第四条路。
2. **L0／L1／L2 分层加载作为统一召回契约**：每个记忆单元与目录都带摘要（~100 tokens）／概览（~2k）／全文三级，agent 先用便宜层判相关性再决定读全文，且目录摘要向上汇总。我们 wiki 的 index.md 只是雏形；把它系统化为经验层＋知识层共同的召回协议（含 token 预算），是新东西。
3. **记忆生命周期＋检索轨迹反馈**：经验按"召回曝光"计龄、长期不用的自动归档（会遗忘的记忆系统）；同时记录每次检索轨迹（谁、何时、召回了什么）用于反哺组织与审计。我们基准只写了"沉淀"，没写衰减与轨迹——这是治理层的一个缺口。

**想过一半（2 项）**：虚拟文件系统范式（我们是真文件，它多了 URI 化寻址与目录级语义汇总，可借鉴后者）；会话结束自动进化管线（压缩→抽取→更新）作为显式契约＋可插拔压缩器接口。

**想过且有意不采（1 项）**：记忆／知识／Skill 三合一统一存储——与其内部分层相比，我们的两层分治（知识层独立 git 仓、人工策展、最高权威）是有意选择，不动。

## 再再附（2026-10-20，用户问）：OpenViking 对比混元——真创新还是过度工程？

**判断框架**：OpenViking 的设计中心是"成为全行业的通用上下文平台"（多租户、任意资源、组织级规模，字节内基础设施的延伸），通用性与拓展性是其**目标本身**；Hy 的设计中心是"一个人的多个工具共享一份本地记忆"（MemHub 是个人产品形态）。两者都有平台型冗余，但位置不同：Hy 的冗余在**模型层**（专用 30B 模型是腾讯的护城河投资，但框架可不用它——可插拔）；OpenViking 的冗余织在**核心引擎**里（虚拟 FS 引擎、VLM 内容理解管线、多租户服务端、无监督自进化），拆不掉。

**逐件判定（对本项目＋PAT 的问题尺寸：一名用户、约十个 agent、蒸馏后记忆单元以万计）**：
- 真创新且我们用得上：L0/L1/L2 分层加载的思想（但两级可能就够，三级＋目录摘要自动汇总已带规模色彩）；Gateway 接入模式（当前非刚需，对 PAT 未来接入封闭 agent 是期权）；检索轨迹＋生命周期意识（个人记忆以十年计，衰减反而是刚需，但实现可远比它简单）。
- 对我们属过度工程：虚拟 FS 背后的分布式存储引擎（我们的语料一个 git 仓装得下）；面向任意文档/媒体的 VLM 摄入管线（我们的输入是会话与已结构化的事件流，没有开放世界文档洪流）；多租户服务端与 Studio（单用户不需要）；**无监督自进化**——它解决"规模大到无法人工策展"，而我们的知识层恰恰要求人工策展与不静默变更，其自进化与我们的治理模型相冲突，是负资产。
- 公平起见，Hy 的冗余也点名：专用模型＋归因 RL 是平台下注，三场景划分带腾讯业务线烙印；但因其冗余可拔插，对采用风险的影响远小于结构性冗余。

**原则（本轮沉淀）**：选型加一条"**设计与问题同尺寸**"——过大的设计不是中性的，它会在运维重量、治理摩擦、退出成本上持续收税。OpenViking 输给 Hy 的不是设计高度，是设计尺寸：它回答的问题比我们的大两号。此判断在本项目"不商业化、PAT 届时另行选型"的前提下成立；若本项目转而要服务他人，结论需重估。
