# Hermes 执行验收证据清单（致执行方 Codex）

> 状态：待执行方回填执行报告
> 维护线：整体线
> 最后更新：2026-10-27
> 摘要：Hermes 已由 Codex 在 VPS 上完成配置（用户 2026-10-27 告知）。本清单列明验收方（老邪）按 `hermes-config-spec.md` §7 核验所需的全部证据项；执行方逐项回填结论与证据，写入执行报告后提交本仓。

## 0. 回填方式与红线

- 执行报告写入 **`platform/hermes-execution-report.md`** 并提交本仓（`main` 分支，`[platform]` 前缀）。
- 每组证据末尾给结论：**已落实 / 有偏差 / 未做**，偏差与未做必须写明理由，不许沉默跳过。
- **红线：任何密钥、令牌、SSH 凭据、Bearer key 的值不得写入报告或仓库。** 凭据只报属性（存放路径、文件权限、是否专用低额度、服务商侧上限值），不报值。
- 冒烟类证据以**文件侧证据**为准（文件路径、内容摘要、哈希、目录监视记录），不接受"会话里试过、没问题"式自述。
- 本清单对应 spec 版本：`platform/hermes-config-spec.md`（commit 932e7a76 修订版）。

## A. 部署三元组与版本

1. 部署形态（git 安装 / pip / 官方镜像）、具体版本号（镜像须给钉死的 tag）、安装通道。
2. 版本安全下限核对：实际版本 ≥ v0.21.6；且包含 CVE-2026-71963 修复提交 `f6234d0` 的核对结论与核对方法。
3. 自动升级已关闭的回读证据；升级前快照纪律的落实方式。

## B. 配置哈希与治理键回读

1. 实际生效配置文件的路径与内容哈希（SHA-256），供后续比对漂移。
2. §3.4 治理键逐项回读（给实际值，不给"已设置"）：
   - `skills.write_approval`、`memory.write_approval`
   - `curator.enabled`（须为 false）
   - `auxiliary.background_review.enabled`（须为 false）
   - `skills.creation_nudge_interval`、`memory.nudge_interval`（须为 0）
   - 会话 token / 费用预算上限的实际值（须非零）
3. §3.5 凭据项回读：
   - `auth.adopt_external_logins`（须为 false）
   - 密钥文件权限回读（须为 0600）
   - 首个接入模型是哪家（DeepSeek / Kimi）；所用 key 是否为专用、可撤销、低额度（只报属性）
4. 可选云组件逐项审计结果：Portal Tool Gateway 未启用、Honcho 未接入、无任何厂商托管服务绑定——逐项给"已确认关闭"的依据。

## C. 部署姿态回读

1. gateway 服务化：服务注册方式、开机自启与异常自拉起已启用。
2. API Server 只绑 127.0.0.1、Bearer key 必填已生效；Dashboard 未对外网开放；CORS 关闭。
3. 工具执行后端为官方 Docker 加固后端（非 local 裸跑）；宿主目录挂载情况（未挂载，或只读挂载并明示路径）。
4. 容器参数实际值：`docker_forward_env`（须为空）、`container_persistent`（须为 false）、网络分段方式、内存等资源上限值及其与 VPS 规格的关系。
5. `security.allow_private_urls` 仍为 false（未放开）。
6. 出口基线：模型 API 域名白名单的落实方式。
7. `approvals.deny` 自定义硬规则的实际内容（规则可入仓，非凭据）。
8. 本阶段范围确认：未接任何消息渠道、未建 MQTT 桥、未接数据层。

## D. 自治面清点回读

逐项给当前状态（开跑前基线应为全空 / 全关）：

1. cron 存储为空——**含暂停态任务**；
2. heartbeat 关闭；
3. 无 standing goals / recurring loops；
4. 内置插件逐个列名与状态（至少说明 disk-cleanup 一类在跑什么）；
5. 插件目录、技能目录零第三方安装；
6. 技能 / 记忆目录的变更前快照机制形态（已启用哪种）；
7. 任何备份 / 同步机制的审计状态（未审计的不得已开启）。

## E. 冒烟证据（文件侧）

1. 本地对话自检通过的记录。
2. 命令审批三态实测：批准、拒绝、超时（短超时 + fail-closed）各一次的结果；**迟到的批准未落到下一次请求**的验证结果。命令审批的人工裁定范围与模式（smart / manual 等）明示实际值。
3. Runs 审批（本体级）：审批挂起 ≥ 2 小时、不重启进程走完的结果。未做则明说未做，不许含糊。
4. 写入行为冒烟全链路：经 API 触发一次记忆或技能写入 → 只进暂存不落盘 → 待审项可见 → 批准后落盘（给文件路径与内容证据）→ 另一次写入拒绝后无残留（给目录侧证据）。
5. 服务重启后自恢复的验证结果。

## F. 外部信号在位

1. 模型服务商侧用量告警或消费上限：哪家服务商、阈值多少、已生效的依据。
2. 技能 / 记忆目录变化监视：启用了哪一种、监视范围、已生效的依据（至少其一，§7 硬要求）。

## G. 工具层观察项

`write_approval` 对 `skill_manage` 工具 `write_file` 路径的覆盖性：核实方法与结论（#142069 的 0 字节写入路径是否被审批门覆盖）。

## H. 偏差清单

与 spec 不一致的**全部**事项逐条列明：spec 要求、实际做法、偏差理由。特别包括：因版本漂移（spec 基于评审时点版本）导致的配置键名或默认值变化，以及按 §3.1 要求逐项复核的结论。没有偏差也要明写"无偏差"。
