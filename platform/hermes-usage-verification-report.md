## 2. 三个决定性发现

**发现一：落盘误报是信任红线，本轮出现三次。** T2 两次、T6 一次：Hermes 报告"已写入"、工具在容器内返回 `verified: true`，宿主机上文件根本不存在。这不是能力问题，是证据问题——**凡文件交付，今后只认宿主机文件侧核验，它关于自己是否落盘的自述一律不作数。** 这也意味着现阶段不能让它独立交付任何"写完即完"的产物。

**发现二：干预成本主要花在环境上，不是活上。** 主批次 9 次审批＋4 次纠偏。审批大多是设计内的（治理基线本就如此），但 4 次纠偏里有 3 次是环境类问题（safe-root 继承、落盘路径错配、首次未触发审批）——profile 隔离不等于进程环境隔离。也就是说"用它累不累"目前主要累在脚手架，不在任务本身；脚手架修好（独立 gateway 起步、落盘核验设为完成门槛），干预结构会明显改善。

**发现三：跨会话续作能用，但靠的不是长期记忆。** T6 第二天找回背景靠的是 `session_search` 翻原始会话；`MEMORY.md` 里的索引摘要指向的详情文件从未落盘（被 safe-root 拒写，它自己没察觉）。结论要分开记：**"换会话能续作"成立；"长期记忆的索引→详情链路可靠"未被证明、且本轮恰好实证了它会断。** 任何依赖详情文件沉淀的长期工作流，现在都不能建在这条链上。

其余单项：T4 的教训是"来源选对 ≠ 逐项核对"，版本/日期/清单型事实必须有第二观察者开原文复核；T5 的重复审批是上游行为，现阶段只能接受并计量，不写进能力承诺；费用不是问题——用户侧观察当日不足 1 元，token 累计量大主要是上下文重复计入，属效率问题、非预算风险，预付熔断继续兜底。

## 3. 处置结论

**可以接的活（证据已够）：**
- 固定语料的理解、定位与答疑（T1 级）：给它钉死版本的仓库/文档副本，问答与梳理可直接用。
- 边界明确、自带测试套件的小型代码修复（T3 级）：在隔离工作区内执行，以测试全绿＋diff 范围为交付判据。

**可以接、但必须带护栏的活：**
- 文档加工与一切文件交付：交付判据＝宿主机落盘核验通过，自述不算数。
- 联网调研：产出只作草稿；版本、日期、清单型断言须第二方核源后才可引用。
- 长任务托付：可派，但预算与耐心上预留偶发重复审批。

**暂不接的活：**
- 依赖长期记忆详情文件的跨日连续工作流（链路未闭环）。
- 任何以它自述状态为唯一完成证据的任务。

**最小放行清单（接上述活时）：** 只读语料挂载；隔离工作区读写挂载；代码类任务按需临时开工具网络、完工即关（本轮已验此流程）；每个独立 profile 用独立 gateway 起步。以上均已在本轮测试区验证，不涉及生产配置变更。

**继续保持关闭：** 仓库写权限与 git 凭据、生产工作区写入、渠道自动化与 cron、把容器内验证结果当落盘证据（此为纪律项）。

## 4. 毕业口径

本报告只完成评分，不自动把任何真实任务转给 Hermes。按任务集 §3，毕业决定由用户在本报告后裁定：建议从"可以接的活"两类里各挑一类先转真实任务试运行，其余维持测试区结论。若用户裁定推进，下一轮的改进项为：落盘核验写入任务完成门槛、调研类任务标配二次核源、观察上游是否修复重复审批与 safe-root 继承问题。

## 5. 关闭决定（2026-10-29 用户裁定）

- **阶段一正式关闭，Hermes 转维持性待机**：配置冻结于验收基线，不再追加验证轮次，不接真实任务；仅跟进 CVE 级安全更新。Hermes 专属上游遗留（providers 结构迁移、session_reset 插件、npm 锁文件等）一并冻结，不再投入。
- **毕业口径更新**：§4 的"各挑一类转真实任务试运行"建议未采纳。用户裁定不设常驻工作 profile；未来出现具体真实任务时，按测试区配方（只读语料挂载＋隔离工作区＋落盘宿主核验）临时复刻、按需升格。
- **数据留存**：本轮验收结论、执行结果与本报告构成基准数据集，作为后续底座（如阶段二候选）同题对比的标尺。
