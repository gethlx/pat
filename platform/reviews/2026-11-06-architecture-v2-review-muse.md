## 结论

**支持冻结。** v2 的定位收正（跨厂商 Agent 组织治理）、拉模式、Git 短期基座＋退出信号、宰相席位制与确定性优先、以及联合评审对过度工程化的多数砍法（交接状态机→一段文本、四份契约→一页、看门狗 Agent→cron），本评审均认同。升级报告 R1–R8 中被 v2 吸收的部分（持久任务记录、工作记忆并入任务账本）经核对属实；R7（数据可清除、离线恢复）随硬件线推迟，合理，不必现在补。

以下六条是现有评审未说透、或与本线运行史直接相关者。处理建议：1、2、3、6 为冻结前补记（均为段落级，不动架构）；4、5 为阶段一/二实施规则，记入蓝图附录即可，不值得为此再开一轮评审。

## 一、名册缺了现行协调面，两套账本是最大风险

家底盘点盘的是「本机能装的 CLI」，但用户今天实际运行的协调系统不在名册内：Muse（老邪）侧的侧聊分线、目标与跟踪账本、定时任务、worker 派活与审批卡闸门——邮件监控、wiki 投稿、赛事同步等日常流量都走这套。v2 阶段一另起「宰相府最小版」，对现行面只字未提。

风险不在席位归属，在**账本出现两份**。本线 2026-10 月底刚有实证教训：记录分片存放（侧聊呈草稿、主聊点头、发送记录在 Gmail），任一片空白都被误读为「事件未发生」，根因被用户钉死在分片本身。铁律四「只建一份」对任务账本同理适用。

**建议**：蓝图补一段现行面的定位——或定为宰相府的第一个用户入口通道（入口归入口，账本只进 Git 那一份），或明确划界哪些工作不进 v2 账本。不划界，两套系统迟早互相看不见。

## 二、执行器的动作门与预算字段，未继承既有裁定

联合评审把治理六件砍到「provenance ＋ 一个 cron」，大体成立；但有一项不是过度工程，是用户的现行裁定：dsh 侧已定的**四类不可逆动作审批门**（删除/覆盖仓外数据、对外发送、动凭据与权限、生产部署），以及对外发信「看过原文并明确点头」的铁律。v2 只写「宰相不能替你做审批」，未约束**执行器自身**的动作；任务文件七字段中也没有 scope / access / budget。

依据：采收 E13（自治边界三要素＋逐任务成本账本）源于真实成本事故；Grok Bot 又恰是「无产品级消费上限」的一家。长时拉模式任务无预算字段，等于把熔断完全押在厂商侧。

**建议**：任务文件加 `budget` 与 `access` 两字段；蓝图补一句「四类不可逆动作门全舰队沿用 dsh 裁定」。成本一行，防的事故每件都比这行字贵几个数量级，不违背「不增加管理成本」判据。

## 三、共享记忆仓的单写入者与拉模式相矛盾，拆仓一次解两题

蓝图 §4.2 写共享记忆仓「单写入者策略」，阶段三又让 Grok Bot 克隆私密仓取活回写。两个问题叠在一起：

- **暴露面**：Grok Bot 云电脑按其官方文档不构成安全边界（同账号 Bot 共享文件、浏览器会话与凭据）。把被定为「数据资产种子」的记忆仓整体克隆到最不可控的一台机器上，不可接受。
- **写权限**：多执行器回写与单写入者策略直接冲突。

**建议**：**tasks 独立成仓**。拉模式 worker 只接触 tasks 仓（领活、回结果），记忆仓不下该机器；结果由壳侧归并进事件库。如此单写入者真成立（记忆仓只有壳侧一个写入者），tasks 仓的多方并发正好用 Git 的 push 竞态乐观并发。多一个仓，每周管理成本约等于零。

## 四、claimed 缺过期回收，失联执行器会锁死任务

蓝图 §4.3 的 claimed 记 owner 与截止，但截止到期如何处理全文未写。v1 工作记忆层选乐观并发弃锁的理由写在原文里：Agent 会 stall/crash，锁会被死 Agent 永远占住——文件式领取是同一个病。升级报告 R3 管的是交接时「先确认旧执行停止」，覆盖不到首次领取后失联。

**建议**：补一行规则——截止过期由维护 cron 扫回 inbox，handoff 注明「上一任失联、状态未核」。这是 R3 在 Git 账本中的落地形态，不必另建租约系统。

## 五、事件真实性差最后一环：引用须可核验，维护脚本须抽查存在性

蓝图 §6.2 要求每条事件记「依据什么（原始引用）」，方向对。但事件由执行器自报，而 Hermes 使用验证的头号病灶正是**落盘误报**（自报已写、实际未写）。v2 验收部分已立「不信自报、要有 commit」的标准，但四件套中的 maintenance 脚本只核对条数，核不出引用真假。

**建议**：done 事件的 `artifacts` 字段改为必填，且必须指向 commit 或资产 ID；维护 cron 定期抽查引用存在性，查无此物即告警。记忆线刚为同一件事设过信赖门，整体线不必再交一遍学费。

## 六、两处文本账，冻结时一并对齐

1. **壳的路线表述矛盾**：联合评审「已定案」第 1 条为「壳自建首选」，蓝图附录待确认第 1 条与 §5.3 又建议「先用 WorkBuddy」。两说可共存（自建为终局、WorkBuddy 为验证脚手架），但蓝图正文未写明这层关系，实施时必然各执一词。冻结时用一句话钉死。
2. **三级与四级权威词表**：联合评审将四级（raw/inferred/curated/approved）收为三级（vendor/inferred/confirmed），理由成立，本评审同意。但记忆线 v0.2 的现行口径仍是四级，且「提炼产物封顶 inferred」是其信赖门的落点；两套标签将在云端服务一站汇合（蓝图 §4.4）。**映射表必须写进契约区那一页契约，并列为阶段二的前置**，不能留到实施中对齐——标签一旦写进事件库，改名即数据迁移。且须注明：vendor 是来源轴、raw 是加工轴，一份厂商导出原样存档同时占两格，映射表要留此位置。
