# Hermes 配置方案评审意见（评审方：mimo）

> 状态：已提交评审
> 维护线：评审方-mimo
> 最后更新：2026-10-21
> 摘要：对 `platform/hermes-config-spec.md` 的评审：有条件通过。三条阻断：Docker 加固后端与命令审批在上游是互斥而非并行（Container bypass）、"审批"混淆了命令审批与 Runs 审批两套机制、MemoryProvider 占槽不等于记忆权威让渡（官方明示 never replacing）。另有 CVE 自查判据、部署形态、磁盘加密可实现性等重要项与跨文档口径缺口。

评审依据：按指引 §3 顺序实读 `AGENTS.md`、`architecture-v1.md`（云端节点/数据层/协议与通道节）、`hermes-adjustments.md`、方案全文、`design-harvest.md`（A/E 组）。**外部事实核查于 2026-10-21 晚独立进行**，信源见文末附录；未上机、未运行任何 Hermes 实例——凡"上游文档说 X"均为文档级证据，不等于实测，推断处单独标注。提交前注意到 `reviews/` 内已有其他评审方文档，本文结论与事实核查独立形成，未据其修改；重合条目互为佐证。

## 1. 总体结论

**有条件通过**——治理先行的底色、默认收口与阶段切分是对的，调研依据抽验基本立得住（三桩 issue、353M 事故、v0.21.6 修复面、CVE 区间均核到原文）。但方案把两组"看上去配套、实则互斥或异物"的东西并排写了：Docker 后端会整体跳过危险命令审批；"审批"一词横跨命令审批与 Runs 审批两套机制而姿态只配了半套；记忆"占槽让渡权威"的前提与官方文档相反。**阻断项 R1–R3 修正后可执行**；R4–R9 应并入执行前修订，不挡评审通过。

### R1（阻断）Docker 加固后端与命令审批互斥

- **位置**：§3.3「工具执行走官方 Docker 加固后端……无人值守场景下命令审批保持开启」。
- **意见**：官方 Security 页明文——"Container bypass: When running in docker, singularity, modal, daytona, or vercel_sandbox backends, **dangerous command checks are skipped** because the container itself is the security boundary."即方案选定的执行档下，危险命令审批（含 Hardline 之外的整层检查）是被跳过的，"命令审批保持开启"是空转。方案把两道闸写成叠加，实际是二选一。
- **证据出处**：官方 Security 页「Container bypass」（中英文镜像同文）；三方对照表（hermes-agent-lab「Container Isolation Mode」）同证 docker/singularity/modal/daytona 档检查跳过。
- **建议改法**：§3.3 显式二选一并写明取舍：(a) 接受"容器即边界、命令审批不生效"，安全姿态改为容器参数收口（挂载/网络/env/资源）；(b) "整进程容器 + 容器内 local 后端"以保留命令审批（**推断**，须冒烟验证）。附注：`approvals.deny` 硬规则在容器档下是否仍然生效**本文未核实**，须实测或补查文档后写入。

### R2（阻断）"审批"两套机制被混作一套

- **位置**：§3.3「审批超时按 fail-closed」× §7「审批挂起数小时……可恢复并走完」× §4 映射「输出与审批回流｜3.3 + §7 冒烟」。
- **意见**：上游是两套东西。**命令审批**（tools/approval.py）：`approvals.timeout` 默认 300 秒、超时 fail-closed、**过期卡不可重开**；webhook/api_server 等无人值守面另有 `approvals.unattended_mode`（默认 deny = 危险命令即时拒绝，不挂人）。**Runs 生命周期审批**（`/v1/runs`/`/approval`）：才是 §7 "挂起数小时"的测试对象，其挂起上限、超时与持久化行为文档级未钉死（调整清单已自认）。3.3 只配了前者，映射表把两者并成一行——照此执行，冒烟会拿命令审批的默认值（300 秒）去测 Runs 挂起，结论必然混淆。
- **证据出处**：官方 Security 页「Approval Timeout」（默认 300、fail-closed、过期不可重开）与 `approvals.unattended_mode`（默认 deny；PR #98558）；方案 §7 与 `hermes-adjustments.md` 第 3 条（Runs `/approval` 一等端点、待冒烟项）。
- **建议改法**：拆成两张姿态表——命令审批（timeout 目标值、unattended_mode、与 R1 容器档的关系）与 Runs 审批（挂起上限、超时、重启持久化、入口）；§7 判据只测 Runs 路径并在判据里注明"与命令审批无关"。

### R3（阻断）占槽 ≠ 记忆权威让渡

- **位置**：§3.4「本阶段不占 MemoryProvider 槽……槽位预留给共享记忆线对接」、§4 映射「记忆不垄断｜槽位预留」；前提源头在 `hermes-adjustments.md` 第 4 条「占槽后本体记忆降为草稿/缓存语义」。
- **意见**：官方 Memory 页明文——外部记忆 provider（Mem0、Honcho 等 8 个及插件位）"run **alongside** built-in memory (**never replacing it**)"。占住槽位不会让 MEMORY.md/USER.md 退场，是两套记忆并存；"让渡权威、本体降为草稿"靠占槽做不到，须另行处置内建存储（文档给出的全关手段是 `memory.memory_enabled: false` + `memory.user_profile_enabled: false`）。映射表以"槽位预留"作为"记忆不垄断"的满足路径，是纸面满足——这可是红线需求。
- **证据出处**：官方 Memory 页「External Memory Providers」「Configuration」；`hermes memory setup` 为单 provider 配置入口。
- **建议改法**：① §3.4 与 §4 改写满足方式为"治理闸（本阶段）＋ 内建存储处置 + 外部槽对接（接入期）"，占槽只是接入通道不是权威让渡；② 此口径须回写 `hermes-adjustments.md` 第 4 条（属整体线自有文档，由整体线改）；③ 接入期方案把"内建两处存储关不关、导出/让渡格式"列为必答题，否则阶段一攒下的原生记忆被锁死在 Hermes 格式里——恰是"记忆不垄断"要防的事。

### R4（重要）CVE 自查判据应钉死锚点

- **位置**：§3.1「安装时按版本自查 CVE-2026-71963 的修复状态」、§6 安全实证。
- **意见**：可钉的判据已经存在，不必停留在"说法不一"：CVE 记录口径为**影响 0.18.2–0.21.0、修复以提交 `f6234d00`（PR #101483）标记、CVE 自身未标注修复发行版**（独立追踪库以 code_commit 为修复边界；部分二手源推断 ≥0.21.1 已修）。另一处易踩的坑：v0.21.6 发行说明中的 git 加固对象是 clean/smudge/process **filter 程序**，与 GitSpawn 的 **core.fsmonitor** 注入不是同一修复条目——"版本 ≥v0.21.6"不能自动证明 fsmonitor 修复在位。方案的 CVSS 8.6 无误（CVSS 4.0 分；3.1 分为 8.8），但建议把两个分值口径写明，免得下轮评审再吵。
- **证据出处**：cvedetails / Rapid7 / OpenCVE / mallory 的 CVE-2026-71963 条目（影响区间、fix commit、8.6=CVSS4.0/8.8=CVSS3.1）；v0.21.6 发行报道（filter 硬化条目）。
- **建议改法**：自查判据改为"部署构建包含 `f6234d00`/PR #101483，或版本 >0.21.0 且发行说明含 fsmonitor/hooksPath 修复条目"，与 R5 的部署形态绑定执行。

### R5（重要）部署形态未定，版本纪律落不了地

- **位置**：§3.1（版本与升级）、§3.2（gateway 服务化）、§3.3（"Docker 加固后端"）。
- **意见**：三个"Docker/安装"概念被揉在一起：①工具执行后端（terminal.backend=docker）是运行时沙箱档；②本体部署形态（git/pip 一键装 vs 官方镜像）决定版本自查、升级快照、"关自动升级"的落点；③镜像 tag `:stable`/`:latest` 是移动目标，与"版本自查、版本无漂移"直接冲突（除非钉具体 tag）。发行渠道还不齐：v0.21.6 的 Desktop/Termux 构建不随补丁走。方案没钉形态，执行者无从下手。
- **证据出处**：官方 Installation 页（四条安装路线、六种终端后端）；v0.21.6 发行渠道差异报道。
- **建议改法**：§3.1 钉"部署形态 + 版本/tag + 通道"三元组（例：git 安装钉 commit 或版本号；镜像钉具体 tag）；文中"工具执行后端"与"本体部署形态"分开用词。

### R6（重要）磁盘加密基线在无人值守 VPS 上不成立

- **位置**：§3.5「密钥文件权限 0600 + 整机磁盘加密」、取舍 B。
- **意见**：两个问题。①自管 FDE（如 LUKS）开机需解锁，与 §3.2「开机自启、异常自拉起」互斥——解锁钥放本机等于白加密，人工解锁则常驻不成立；②云厂商侧加密只防物理取盘，不防宿主/厂商侧与被攻破的进程，对"凭据防泄露"贡献有限。把它写成"基线"是纸面项（**推断**：运维常识与威胁模型分析，上游文档无 FDE 方案可引，故标注为推断）。顺带一句：GitSpawn 类漏洞的实际危害恰是"进程环境与 provider key 运行时外泄"，0600 与磁盘加密都管不到运行时。
- **证据出处**：CVE-2026-71963 条目"expose the full environment, including configured provider API keys"；无官方 FDE+无人值守组合方案（核查所得为否定性证据）。
- **建议改法**：B 的表述改诚实版——真实基线 = 0600 + 暴露面收窄（§3.2 已有）+ 可选的 provider 侧消费上限/低额度专用 key（一次性配置、零日常运维、直接对冲运行时外泄的爆炸半径）；磁盘加密降为可选加固，且"解锁方式与常驻的兼容性"列为前置验证项。密钥注入放迭代期，同意维持两步走。

### R7（重要）冒烟清单丢了调整清单立账的验证项

- **位置**：§7 验收清单。
- **意见**：`hermes-adjustments.md` 显式立账的两个待冒烟项之一——"write_approval 在无人值守/API 模式下的完整行为（草稿落点、审批入口）"——在 §7 消失了。§7 只剩"治理开关逐项回读"，那是配置回读，不是行为验证；文档级已知的答案（暂存于 `~/.hermes/pending/`、`/memory pending` 审批）覆盖不了 API/无人值守路径下"暂存是否真生效"。对照 E1"永不信自报成功"与 #137967（截断仍记 completed）的教训，方案的验收恰恰在复制"自报/自读即真"的错误。
- **证据出处**：`hermes-adjustments.md` 需求 4 差距④与文末「与基线相比的新发现/修正」；官方 Memory 页（pending 语义）；issue #137967。
- **建议改法**：§7 补两条——①行为冒烟：API 触发一次会写记忆/技能的操作 → 确认只进暂存不落盘 → pending 可见可审批 → 拒绝后无残留；②结果抽查项：关键写入的落盘结果以文件侧证据核对，不采信会话自述。

### R8（重要）自治面清单不全，gateway 就是调度宿主

- **位置**：§3.4 治理清单、§2 理念 5、§5。
- **意见**：理念 5 点名"维护、巡检、自动总结、定时任务"全部要有上限或关闭，但配置面只关了 curator 与 background_review。上游还有整族自治面：cron 调度器（**gateway 服务每 60 秒 tick**，零渠道阶段照样会自己醒）、loops（max_ticks 默认 100）、goals（max_turns 默认 20）、cron_mode/single_query_mode/unattended_mode 审批模式、`cron.allow_agent_scheduling`。且 #141912（2026-10-20 开，未修复，0.22.x 仍在）证明 cron 的机器注记以 USER 角色混入对话流、被记忆面当用户事实吸收——定时任务不只是"费钱"，还是记忆污染源。
- **证据出处**：官方 Security 页（cron_mode/unattended_mode/黑名单）、agentos 指南对官方 cron/delegation 文档的转述（loops/goals 上限、60s tick）；issue #141912。
- **建议改法**：§3.4 或 §5 明确"本阶段不创建任何 cron/loop/goal；相关默认值入审计清单"；理念 5 的落地清单逐项对齐上游自治面族，不留"原则点名、配置不管"的缺口。

### R9（重要）写入治理缺快照/回滚与同步面审计

- **位置**：§3.4。
- **意见**：E3 三件套是"审批门 + 版本快照可回滚 + 不静默跨机同步"，方案只落了第一件。第二件：#142069 显示 curator ledger 记 before/after hash，但事故里 0 字节技能是**人工恢复**的——ledger ≠ 回滚，方案对 memories/skills 的变更前快照无任何要求（`hermes update` 的快照只在升级时触发）。第三件：0 字节事故的放大环节是"技能目录同步到其他机器"，方案的云组件审计清单（Portal/Honcho）不含任何备份/同步机制面。
- **证据出处**：issue #142069（ledger 记录、manual restore、spread to other machines）；design-harvest E3。
- **建议改法**：§3.4 补"记忆/技能目录变更前快照纪律"（形态可由执行者定）与"任何备份/同步机制入审计清单，未审计不得开"；或显式列为迭代期项并注明当前接受单机风险。

### R10（建议）API Server 绑定口径不一

- §3.2"只绑 127.0.0.1"（同机可达）与 §3.6"API Server 内网调用"（同网可达）姿态不同；桥与 Hermes 是否同机未定。按 E5（安全与拓扑一起验），建议默认同机 + 127.0.0.1，异机则显式降级为"内网绑定 + 白名单"，两处表述统一。

### R11（建议）数据主权边界未声明

- §4"数据主权与隐私→满足"限定的是 Hermes 侧（无遥测、无强制云组件、状态本地），不含**模型 API 上行**（对话、工具输出、文件片段会发往 DeepSeek/Kimi——LLM 使用的固有面）；§3.2 的 Tailscale 与 §3.4"不绑定任何厂商托管服务"亦有张力（Tailscale 有外部协调面）。建议在 §3.5/§4 加一句主权边界声明，Tailscale 列为传输层豁免或给纯 SSH/自托管替代。

### R12（建议）桥约束缺凭据隔离与幂等两条

- 六条"薄且无状态"居首，排序对、无多余。缺：①per-adapter PAT 侧凭据隔离——§3.7 的服务端打戳按凭据认人，桥侧"每个 adapter 一组凭据"是打戳的凭据基础，应进约束；②设备事件的幂等/防重放口径（上游 webhook 自带 delivery-ID 幂等与时间戳签名，桥侧对应行为要声明）。条 1"状态只在数据层与 Agent 侧"与取舍 C 的"状态存 PAT 侧"一致，无冲突。

### R13（建议）技能供应链面无姿态
