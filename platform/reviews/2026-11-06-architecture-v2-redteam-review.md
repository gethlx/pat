## 一、逐条反驳老邪意见

### ① "名册缺现行协调面，两套账本是最大风险"——定级推翻，降为范围注记；利益专项见文末

**推翻三点：**

1. **误读名册的用途。** 家底盘点开篇即定判据："壳能不能合法、稳定地调到它"（盘点 §一）——那是**执行器名册**，不是用户全部运行面的普查。老邪（Muse 侧）没有可编程派活入口，这一点盘点对同名的 Meta Muse 已查实（盘点 §2.4：无派活 API、Gadgets 方向相反）。以"协调系统不在执行器名册内"指控"名册缺失"，是拿错了名单的定义。
2. **类比偷换。** 他引的 10 月底教训是"**同一件事**的记录分片在侧聊/主聊/Gmail 三处、任一空白被误读为未发生"。而他列举的现行面流量（邮件监控、wiki 投稿、赛事同步）与 v2 的任务域（向 Codex/Grok Bot/DSH 派活）**不是同一批任务**。不同任务域各有账本 ≠ 同一事件的账本分片。前者是常态，后者才是事故。风险只在两个任务域将来交叠时才成立——那是条件风险，不是他说的"最大风险"，全文无任何交叠实证支撑这个定级。
3. **入口其实没被排除。** 蓝图 §二图示用户入口写作"Web / Telegram / 手机 / 语音"——通道无关式表述，老邪的聊天面天然可作其中一个入口，蓝图从未说阶段一要另起入口与之竞争。他建议的两个选项（定为第一入口／明确划界）互相排斥而他不选，说明这不是一个已想清的架构问题。

**推不翻的内核：** 铁律四"只建一份"（蓝图 §一）与联合评审 §1.5"不要建两个东西"的单账本原则是真的；若将来同一任务同时经侧聊与 tasks/ 流转，分片事故会原样重演。一行范围注记（"本账本只记经协调面派发的任务；其他渠道的任务不入此账"）成本为零、值得写。

**定级：原表述存活 4/10。** 降为附录范围注记，非冻结前置。

### ② "执行器动作门与预算字段未继承裁定"——方案推翻，前提部分失实

**推翻三点：**

1. **他引的"现行裁定"不是现行裁定。** `platform/dsh-deployment-verdict.md` §5.1 白纸黑字：对外发送"用户裁定接受现状、**不设门禁**……原'保留审批'口径就此项作废"；§5.2 对 GitHub 亦裁定"**不建凭单等结构性授权机制**"，靠行为规则落实。升级报告 §一也复述了这两项裁定。老邪所谓"四类不可逆动作门全舰队沿用 dsh 裁定"，沿用的恰是被 §5 修改过的旧版——他把裁定读回了裁定之前的样子。这是读错自己引用的文件。
2. **成本意识蓝图已有设计，他没提。** 联合评审 §2.3 名册字段含 `limits`（"额度与计费口径，用于派活时避坑"）；蓝图 §三对 Grok Bot 明示"无产品级消费上限"并划线"不让它跑不可中断的关键路径"。而采收 E13 本人写定的阶段一最小落地是"服务商消费上限＋用量告警"（design-harvest E13）——平台级熔断，不逐任务设字段。他主张的 per-task `budget` 字段超出他自己引用的 E13。
3. **无执行机制的字段是装饰。** 执行器在自己登录态下跑（联合评审 §二图注："各自登录态、各自权限墙，互不代持"），壳没有拦截层；`budget` 靠执行器自报消耗——而他自己的第⑤条刚论证完"自报不可信"。字段加上，事故照旧，只是账本里多一列假数。按管理成本判据，这是负分。

**推不翻的内核：** v2 全文确实没有一句把既有治理裁定（dsh 验收 §5 的行为规则、发信铁律）以引用方式带入舰队语境；§5.1 只约束宰相（"不能替你做审批"），执行器在任务范围内自身可执行的动作确实无一字交代。一句"既有治理裁定在本架构内继续有效（见 dsh 验收结论 §5）"的补记成立——是引用，不是新设门。

**定级：原方案推翻；一句引用式补记存活。整体 3/10。**

### ③ "单写入者与拉模式矛盾，拆 tasks 仓"——矛盾系误读拼接，方案非必选

**推翻三点：**

1. **蓝图早留了口，他装没看见。** §4.3 目录约定明写"tasks/ 任务账本（**同仓或独立仓**）"——拆仓本就是蓝图自留选项。把"选项未定"说成"自相矛盾"，定性过重。
2. **"直接冲突"是拼接出来的。** §4.2 的"单写入者策略"贴在**共享记忆仓**（事件库、候选、确认结论——策展型资产）一行；而 §4.1 的 Git 性质表对任务领取明写"push 竞态即乐观并发：两人同领，一人 push 失败，重试即得"——蓝图的任务并发模型从第一天就是多方乐观并发。把记忆仓的写入策略挪到任务账本上，再宣布冲突，是误读。且仓宪章 AGENTS.md 写入规则 3 的"同一区同一时刻只有一个写入者"语境是文档协作纪律防并发覆盖，与运行时领取不是一回事。
3. **他的方案与他自己的 ① 自相冲突。** ① 刚说完账本不许分片、多一套系统就是风险；③ 又要多拆一个仓、多一套 clone/备份/同步面。且拆仓并不自动解决暴露：tasks 仓同样含 goal、handoff、artifacts 引用，照样整仓克隆到那台机器上。真正起作用的是**凭据的仓级限定**（该机只持有 tasks 仓可用的凭据），这在同仓/独立仓两种形态下都能做，且更便宜。

**推不翻的内核：** §4.2/§4.3 确实从未写明 **events/ 由谁写**——执行器直写，还是经壳归并。这一句含糊在阶段二实施时必然分叉（两种实现的数据质量完全不同）。加上记忆仓是全文自称的"资产种子"（§六），对最不可信执行器做最小权限限定，方向是对的。

**定级：问题半存活（events 写入者须在冻结时定一句），拆仓方案降为备选。5/10——六条里成色最好的一条，但仍够不上"冻结前必改"。**

### ④ "claimed 缺过期回收"——真缺口，严重度被夸大；他自己已给了正确处置

**推翻定级：** (a) claimed/ 是单用户可见的目录，`ls` 一眼可见僵尸任务，与 v1 服务里不可见的分布式锁不是一个量级——他引 v1"锁会被死 Agent 永远占住"的语境是无人值守的服务层，本处最坏结果是用户手动把文件挪回 inbox。(b) 升级报告 R3 已覆盖危险的那一半：旧执行迟到结果不得覆盖新修订、无法确认停止时不盲目重发写动作——会造成实际损害的是迟到写入，不是文件躺在 claimed/ 里。(c) 他自己的处理建议就是"记入蓝图附录即可"——即承认这不是架构问题。红队同意他的处置、不同意他的标题：这是一条实施注脚，不是一条"评审意见"。

**推不翻：** 拉模式 worker 恰是最可能无声消失的一类（厂商云、beta 无 SLA，蓝图 §三明载），过期扫回规则在阶段三开工前写进维护脚本清单，便宜且对症。

**定级：作为实施注脚 6/10；作为冻结异议 0。**

### ⑤ "done 引用可核验、维护脚本须抽查"——大半已在文本内，属重复主张

**推翻两点：**

1. **他要的东西蓝图已经写了。** §6.2 第 3 项："依据什么：原始引用（**可回查的 commit 或资产 ID**）"；§九末段："必须有产物、有 commit、有可核对的落盘"——这正是他建议的"artifacts 必须指向 commit 或资产 ID"，原文俱在。他称维护脚本"只核对条数"，出处是联合评审 §五件 4 的一句话摘要（"备份、条数核对、失败告警"）——那是四件套的梗概行，不是禁止其他核对的规格书。拿梗概当规格，再宣布缺口，属误读。
2. **他的加固方向打偏了靶心。** Hermes 落盘误报当年是怎么抓住的？dsh 验收 §2："落盘宿主机核验**内容与哈希**精确"——即验收时验内容，不是平时抽查存在性。存在性抽查只能证明"有个 commit"，证明不了活干对了；而把 artifacts 设为必填，会逼无产出型任务（查询、巡检无发现）伪造垃圾产物填字段，污染账本——用他最在乎的数据质量去换一个弱信号。再加一个 cron 抽查，按管理成本判据要先回答"每周省什么"，他没答。

**推不翻的残存：** §6.2 的要求与 §九的标准之间，执行归属确实含糊——阶段二完成标志（蓝图 §八）只写"DSH 接手能读到上一任做了什么"，未把 provenance 抽查列入验收动作。把"验收时抽查三条事件的原始引用可回查"写进阶段二完成标志，一句，可取。

**定级：3/10。主体是重复蓝图已有条款。**

### ⑥ 文本对齐两处——A 是把待裁定项说成矛盾；B 映射已有其位，前置要求过强

**A（壳路线）定性推翻：** 联合评审 §七的结构本来就是两层——"已定案"记**终局归属**（壳自建首选），"仍待你确认"记**第一版载体**（WorkBuddy 还是脚本）。蓝图 §5.3 与附 1 忠实复制了这个两层结构。终局与首步不是矛盾，是时序。而附 1 本身就是呈给用户在冻结时裁定的问题——要求"冻结前先钉死附 1"，逻辑上是循环的：冻结要裁定的正是它。当然，蓝图作为执行文档，§5.3 通篇不见"自建首选"四字、只读蓝图的人会以为 WorkBuddy 是定案——一句"终局自建，WorkBuddy 仅作第一版验证载体"补进 §5.3，成本一行，红队不反对。但这叫补注，不叫纠正矛盾。

**B（词表映射）推翻"前置"要求：** (a) 映射不是无家可归：`contracts/README.md` 预定收录契约已明列"**权威等级词表**"，变更协议现成；联合评审 §七"裁定后立即执行"已把一页契约列为产物之三。老邪说"必须写进那一页契约"——那正是既定安排，他在要求一件已经排好的事。(b) "列为阶段二前置"过序：阶段二在 v2 三级标签内部自洽运行；映射成本只在云端汇合（§4.4 信号触发）时才兑现，且事件 append-only 带 provenance，汇合时做一次标签变换是可行且唯一的必要时点。"改名即数据迁移"对任何时点都成立，它论证的是"别拖到仓很大"，而一页契约的既定交付时点（裁定后立即）远在那之前。(c) 他最有价值的一句是轴的问题：vendor 是来源轴、raw 是加工轴——属实，且记忆线四级（memory/blueprint-spec.md 约定 6）同样混轴。但他没注意到 v2 §4.3 的目录结构其实已经给出了实践映射：`proposals/`（未确认）与 `confirmed/` 之分，就是四级里 curated/approved 在三级制下的落点。两套词表的实际距离比他渲染的近。

**定级：4/10。A 降为一行补注，B 降为"按既定安排交付一页契约"，均非冻结门槛。**

## 二、为 v2 辩护：被批评处实已覆盖 / 批评者误读

1. **"宰相会成为新的成本与失控源"类担忧，蓝图先答了。** §5.1"确定性优先"：显式指定、回复任务消息、单一人选三种情形不经宰相——宰相只处理真歧义。§5.2 决策输出是 JSON Schema 约束的短结构。这是全文对管理成本判据最实的回应，六条意见无一提及。
2. **"Git 扛不住并发"是假问题，蓝图给了机制不是口号。** §4.1 表内"push 竞态即乐观并发"，§4.4 预先写死换后端信号（检索 2–3 秒／冲突每天多次／需语义检索）并承诺接口不变。预先承诺退出信号的设计纪律，在全部材料里罕见，不该被"Git 只是将就"的读法埋没。
3. **`handoff` 自由文本不是偷懒，是裁定后的取舍。** 联合评审 §四砍交接状态机的理由是管理成本，用户判据在案。老邪 ④ 实际上在要求把被砍掉的东西以 cron 形态部分请回——可以请，但要承认这是在已裁定取舍上加注脚，不是蓝图"漏了"。
4. **蓝图对 Grok Bot 的风险交代比批评者更完整。** §三专列三条硬伤及对策（短时令牌、不跑关键路径、adapter 可降级），与盘点 §2.5 一一对应。老邪 ③ 的暴露面警告，蓝图不是没看见，是已用凭据纪律回应；剩下的只是"记忆仓要不要物理隔离"的程度之争。
5. **Muse（Meta）不进执行器名册是设计而非遗漏。** 盘点 §2.4 查实 Gadgets SDK 方向相反；蓝图 §5.3 将其定位终端接口、§七给出其生态硬件的用武之地。把这一行读成"现行协调面被抹除"，混淆了两个同名对象（Meta 的 Muse 产品 vs 老邪的助理服务）。

**一处红队无法替蓝图辩护、须如实记录：** 联合评审的"四件"含 maintenance 脚本（联合评审 §五、落地顺序第 4 步），**v2 全文未收录此件**——§八五阶段无对应行，§九验收亦未提。蓝图落地时把评审的四件悄悄变三件，无说明。此缺口与老邪 ④⑤ 的关切部分同向（僵尸任务、假引用都要靠它兜底），应在冻结时补回一行：阶段一交付物含维护脚本最小版（备份＋失败告警）。

## 三、翻车场景：五阶段各在哪一步最可能翻

| 阶段 | 最可能翻车点 | 代价 | 蓝图内防线 |
|---|---|---|---|
| 一 骨架 | **前置实测从未被跑。** 联合评审 §六明说第 1 步唯一前置是 `codex exec --json --output-schema` 跑通；蓝图 §八阶段一完成标志直接假定派活跑通。若 schema 约束输出不稳定，宰相决策不可校验，阶段四的地基是沙的。次险：若实施者图省事拿 WorkBuddy 未上 PATH 的内置 CLI（盘点 §2.3）当壳的调用面，那是未文档化接口，直接撞铁律三与采收 E4。 | 低：数天工时，无数据损失 | 附 1 给了脚本路线作退路；联合评审给了 DSH headless 作第二退路。但两条退路都停在文档层，无人认领实测——这是执行问题，不是文本问题 |

## 四、共同盲点：全部材料都没提到的

逐份核过蓝图、联合评审、升级报告、盘点、记忆线蓝图、采收册、dsh 验收结论后，以下五项无一被任何材料正面处理：

1. **账本自身是注入面。** 采收 E12 只防**外部**文档/skill 的指令性文字。但 v2 的信任拓扑是：多个厂商 agent 写 events/handoff，宰相与后续执行器读它们作上下文。一个被外部内容污染的执行器（它读过的网页、它导入的 skill）可以把指令性文本写进 handoff，下一任会当作"上任交代"执行。provenance 只记"谁写的"，不验"写的是不是指令"。对一份自称"资产种子"的 append-only 库，这意味着**污染不可逆**：删，破只增不改；不删，长期投毒。全部材料无一字及此。
2. **协调与记忆平面的可用性单点在 GitHub，而镜像无人认领。** 附 2 对记忆仓轻描"数据过第三方"，建议 VPS 每日镜像——但 §八五阶段**没有任何一步交付这个镜像**。GitHub 账号一旦被锁或服务中断，派活、记账、记忆同时停摆；且"资产种子"的唯一主副本长期托管在美国厂商平台，与本项目长期的数据主权叙事之间的张力，无人正面写过。验收 §九.6 只验"删本地副本可从远端还原"，没验"远端不可用时怎么办"。
3. **治理层自身的成本从不计量，全案的成立前提因此不可证伪。** 蓝图开宗明义"不增加管理成本"（§这份蓝图解决什么），联合评审把判据定为"每周花我多少分钟"。但没有任何材料给治理层本身记账：宰相调用、用户审 proposals、处理歧义、维护名册与脚本——这些分钟数若超过它省下的人肉总线时间，系统就是负资产，且按现在的设计**永远不会有人发现**，因为没有一行要求测它。采收 E13 的逐任务成本账本记的是执行成本，不含治理开销。
4. **用户本人是单点，且被默认为无限可用。** confirmed 晋升、歧义定夺、指针更换、附录三处待确认——所有关键路径收束于一人。用户出差/生病一周，proposals 积压、歧义任务停摆、宰相指针无人能换。个人系统可以接受这个设定，但全部材料连"接受"这个动作都没做过，更没有最低限度的缺席预案（如歧义任务默认停等而非默认继续的规则）。
5. **壳所在的那台本机是凭据总汇点，无人当资产保护。** 盘点 §2.1 无意中摊开了事实：本机同时存着 Codex 的完整登录态与会话资产、WorkBuddy、Grok 应用、各家 CLI 的凭据目录。壳跑在这台机器上，等于全舰队的钥匙串挂在同一台笔记本上。§九.6 的备份验收只覆盖仓，不覆盖凭据与登录态的恢复——真丢机器时，最贵的不是 clone 仓，是逐家重建登录与信任链。全部材料无一处把"本机失陷/丢失"列为场景。
