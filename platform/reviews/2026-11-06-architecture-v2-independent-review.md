## 结论

**冻结判断：附条件可冻。** v2 的定位转向（跨厂商 Agent 组织治理）、推/拉双模、宰相席位制、Git 短期基座四项骨架判断成立，且都有家底实测或用户实测支撑，不是纸面设计。但蓝图正文存在四处文本级硬伤（自相矛盾或关键定义缺失），不改则实施第一周就会撞上；另有一批联合评审已定、却在落地为 v2 时丢失的内容（维护件、名册字段表、入口白名单），属"评审结论未完全入蓝图"的系统性问题。这是本稿与当事方意见的第一处分歧：老邪的结论是"六条补记、不动架构"即可冻结——本评审认为其中至少三处（tasks 仓落点、事件模型归属、Muse 定位矛盾）是冻结前必须先定的定义问题，不是补记。

用户已裁定事项（壳自建首选、三级权威词表、dsh 审批处置、发信须看原文点头、过度工程化以每周维护成本为判据、v2 暂不做可视化、pat 永不整体转公开）本稿不翻案，只查蓝图与之矛盾或未落实处。

## 一、逐项评审

### 1. 定位：成立

从"数据主权平台"收正为"跨厂商 Agent 组织治理"，依据充分：家底盘点证明真正的约束是各家可驱动性差异（盘点 §一），而非数据管线；数据主权降为长期副产品但要求记忆形态现在就对（v2 §六），与联合评审 §一时间尺度表一致。此定位也是五条铁律能成立的前提。保留一条提醒：定位里"治理"一词有天然膨胀倾向，蓝图以"只解决这一件事"自我设限（§这份蓝图解决什么），冻结后应以此句为范围护栏，新增需求先过此问。

### 2. 架构（三面＋双模）：骨架成立，两处硬伤

双模是全案最有价值的结构判断：拉模式把"没有入站门"从死刑改判为接入形态，且有用户在 Grok Bot 云电脑上驱动 Codex 的实测（盘点 §2.5），不是推测。协调面零暴露端口、双模共用同一账本与结果格式（v2 §三），方向正确。

硬伤一：**Muse 的定位在蓝图内部自相矛盾。** §二架构图把"Muse 云"列在"不可到达的执行器"（拉模式）一侧；§5.3 选人矩阵却明定 Muse 为"终端接口，非执行器"，盘点 §2.4 的判定也是"不进第一批名册、归终端面"。图与文必居其一，冻结前须统一。本评审倾向从矩阵与盘点：Muse 是终端面，图中应删或改注。

硬伤二：**拉模式的触发机制没有闭环。** §三写触发方式为"定时/事件/webhook"，但铁律三与 §三关键性质同时要求协调面零暴露端口——webhook 由谁发出、打到哪里，全文未答。若实际只能靠对端定时轮询，则任务延迟下限由轮询周期决定，阶段三的完成标志（"自己领走、做完、推回"）掩盖了这一延迟属性。冻结前不必定死实现，但须写明第一版触发以对端定时 routine 为准、webhook 待触发源明确后再议，避免实施时各自理解。

### 3. 宰相席位制：成立，缺三件小事

席位制（指针、只出决策、不扩权、确定性优先）是对"不存在永久核心 agent"这一用户纠正的正确工程化，Codex 首任的理由（`--output-schema` 实测，盘点 §2.1）扎实。三件缺失：

- **决策不入账。** §5.2 定了决策的输出形态（短 JSON），但没定决策本身是否作为事件入记忆面。派活决策是治理动作，日后追责、复盘、换宰相后理解历史，都需要它。provenance 三样（§6.2）只约束记忆条目，未覆盖决策。
- **宰相不可用时无降级路径。** 指针指向的 agent 额度耗尽、输出不合 schema、或干脆超时，壳怎么办——回退兜底指针（DSH）还是停摆待人？阶段四验收（§九第 5 条）只验"换指针后照常"，不验"宰相失联"。
- **指针枚举与正文打架。** §5.1 指针取值含 `grokbot`，§5.3 与 §三却明定 Grok Bot"不推荐当宰相（黑箱路由）"。枚举应与定位一致，或注明该值为保留禁用项。

另有一处与铁律的张力须写明（详见 §二线索 ⑥）：铁律二要求壳不含模型特权，而 §5.3 称 WorkBuddy（本身是多模型 agent 产品）为"宰相府的现成实现"——用一个 agent 产品当壳，与铁律二是结构性紧张关系，蓝图至少须用一句话交代为何第一版可接受、何时必须替换。

### 4. 记忆面：方向成立，两个跨线问题未解

三级权威（vendor/inferred/confirmed）是用户已裁定口径，本稿不议其档位本身；§6.2 三样必记、§6.3 晋升单向，与记忆线约定 5、6 同向。但有两问：

- **事件模型双头。** v2 铁律四宣称"只建一份 append-only 事件库"，§4.3 的事件是按日 JSONL、字段未定；记忆线蓝图约定 1、2 另有一套"原始事件为真相源＋统一事件模型（字段已列：id、时间、来源、行为主体、类型、内容引用、provenance）"。两条线各有一份"唯一的"事件库定义，字段口径不同。§4.4 称云端服务是"同一条路的下一站"，但若阶段二两线各按自己的模型落事件，下一站面对的是两套历史数据，不是一套。此为全案最深的一处跨线不一致，老邪线索 ⑥ 只触及权威标签，未触及事件模型本身。
- **权威之外无有效性维度。** 记忆线评审 R2 已指出：处理等级、是否当前有效、证据是否支持结论须分别判断，confirmed 的结论也会过时、被撤回。v2 的三级只有等级，没有争议/过时/撤回的表达位置；`confirmed/` 是目录，一条被推翻的结论在 append-only 结构里如何标记，全文未提。阶段二真实数据进来之前须有最小答案（哪怕只是一个状态字段）。

Git 作短期基座＋退出信号（§4.4）判断成立；但信号中"单次检索超过 2–3 秒"没有定义检索负载口径，不可测，实施时须补一句以何种查询为准。

### 5. 五阶段：顺序成立，阶段二藏着未声明的前置

骨架→记忆→拉模式→宰相→按需，依赖方向正确，"每停一步系统可用"是好纪律。两个问题：

- **阶段二依赖尚未存在的契约。** 阶段二要做"事件入库＋provenance"，而 provenance 信封与权威词表正是 `contracts/` 预定收录、至今"待两线共同定稿"的条目（contracts/README）。v2 §6.2 自行给了一个三要素的非正式版本，与契约区将来定稿的信封若不一致，又是一次数据迁移。阶段二的前置应显式写明：一页契约先行。
- **维护件在落地时丢失。** 联合评审 §五把系统收敛为四件，第 4 件是 maintenance 脚本（备份、条数核对、失败告警），理由是采收 E1"永不信自报成功"。v2 的阶段表与验收里没有任何维护件的位置——阶段一到四无一步交付它，§九第 6 条只有一次性的还原演练。评审结论落进蓝图时被漏掉一件，且无人察觉，这正是需要在冻结前补回的。

### 6. 验收标准：证据观正确，用例全是晴天

§九"不接受模型自报、必须有产物与 commit"的证据标准，是 Hermes 落盘误报病灶的正确解药，应保留。但六条用例全部是正常路径：升级报告 §五为 v1 写过 12 条用例（重复投递、结果未知、旧结果迟到、取消后复活、恢复时已清除内容再导入等），v2 一条未继承。至少三条应补入：同一任务重复投递的去重实证（第 3 条只写了结论"不重复执行"，正文却没有任何去重机制——任务 id 幂等、领取语义都未定义，验收无从下手）；claimed 过期后任务被回收再领；换宰相发生在任务执行中途时的归属。此外任务文件同时用目录位置（inbox/claimed/done）和 `status` 字段表达状态（§4.3），双份表示迟早漂移，须定一处为准——建议以目录为准、字段删去或注明只读镜像。

## 二、老邪六条线索逐条裁定

**① 名册缺现行协调面、两套账本风险——成立（但责任归属与老邪所指不同）。**
现行 Muse 协调面（侧聊、目标与跟踪、定时任务、审批卡流）确实不在盘点名册内，也不在 v2 的入口与名册模型里；账本分片导致状态误判有 2026-10 月底的实证教训，老邪引用的因果链属实。但须纠正一点：盘点不是疏漏——其开篇即声明范围是"本机能装的 CLI 的可驱动性"，Muse 协调面不在该范围内是范围问题不是错误。缺口在 v2：它定义了用户入口（Web/Telegram/手机/语音），却没有一句现行协调面与新账本的关系——哪些流量从此进 tasks 账本、哪些留在现行面、过渡期谁是唯一账本。**建议**：冻结前在蓝图补一段定位（一页以内）：现行协调面为宰相府的第一个用户入口通道，任务一旦进入 v2 流程即以 Git 账本为唯一记录，现行面不再另记该任务状态。此条采纳老邪的建议方向。

**② 任务字段缺 budget/access、执行器动作门未继承 dsh 裁定——部分成立；其中"未继承裁定"的指控不成立，须公开纠正。**
字段一半：任务文件加 `budget` 与 `access`（或并为 E13 的 scope/access/budget 三要素）有依据——采收 E13 明列三要素与逐任务成本账本，Grok Bot"无产品级消费上限"是盘点与蓝图共载的硬伤，长时拉任务无预算字段确属空白。此半成立。
指控一半不成立：**dsh 的现行裁定不是"四类不可逆动作审批门"。** `dsh-deployment-verdict.md` §5 是用户 2026-10-29 的正式裁定：对外发送类**接受全开无审批、不设门禁**，原"保留审批"口径明文作废；GitHub 写入以**行为规则**落实，且明文裁定"**不建凭单等结构性授权机制**"（理由：分支 hook 已拦直推主干、残余风险可回滚、复杂化不划算）。升级报告 §一亦把"对用户所派任务的渠道发送不新增门禁、不新建凭单式授权机制"列为继续有效的用户裁定。老邪把部署简报的初始判据当作现行裁定、指控 v2 未予继承，是把已被用户亲手拆掉的门又装了回来——v2 不设执行器审批门，恰与现行裁定一致。至于"发信须用户看过原文并点头"：那是用户与老邪之间、以用户本人名义对外发信的协作铁律，与 dsh 裁定的"用户所派任务的渠道发送"是两个范围，前者继续有效，但不能扩张为全舰队执行器的结构性门禁。**建议**：蓝图补一句与现行裁定的对齐声明——"不可逆动作的约束沿用 dsh §5 裁定形态：行为规则＋分支纪律＋事后统计，不设结构性审批门；以用户名义对外发信不在此列，仍须看原文点头。"任务字段加 budget/access，但理由是 E13 与成本可见性，不是"继承审批门"。

**③ 记忆仓单写入者与拉模式矛盾、应拆 tasks 仓——成立。**
文本矛盾属实：§4.2 写共享记忆仓"单写入者策略"，却从未定义写入者是谁；§4.3 tasks 位置"同仓或独立仓"悬而未决；阶段三让 Grok Bot 克隆私密仓取活——若 tasks 与 events 同仓，克隆即带走全部事件历史，而 Grok Bot 云电脑"不构成安全边界"是其官方文档明载、盘点与蓝图共同确认的事实（盘点 §2.5、v2 §三）。暴露面与写权限两个问题都真实。拆 tasks 独立仓是成立的解法，本评审采纳；等效替代（记忆仓只读范围令牌＋tasks 独立仓）亦可，但"拉模式 worker 不接触记忆仓全量"应写成阶段三的硬约束。仅一处保留：老邪称多一仓"每周管理成本约等于零"略乐观——多一仓即多一份备份与镜像对象（蓝图附 2 已有 VPS 每日镜像安排），成本小但非零，按判据如实记为"每周数分钟级"更稳妥。

**④ claimed 缺过期回收——成立。**
§4.3 claimed 只记 owner 与截止，到期处理全文无字。v1 工作记忆层弃锁的原文理由（"Agent 会 stall/crash，锁会被死 Agent 永远占住"，v1 工作记忆层一节）对文件式领取同样成立；升级报告 R3 的"先确认旧执行停止"管的是有人主持的交接，管不到领取者失联。老邪的补法（维护 cron 扫回 inbox＋handoff 注明失联未核）成本一行、与 R3 相容，采纳。附带指出：此规则依赖维护件存在——而维护件恰在 v2 落地时丢失（见 §一.5），两处须一起补。

**⑤ done 引用须可核验、维护脚本抽查存在性——部分成立（问题比老邪所述更大，不更小）。**
方向与依据成立：§6.2 已要求引用"可回查"，§九已立证据标准；把 `artifacts` 在 done 时设为必填、维护环节抽查引用存在性，是把既有原则落到可执行，采纳。但老邪的事实陈述有误：他说"四件套中的 maintenance 脚本只核对条数"——maintenance 脚本是联合评审 §五的第 4 件，**根本没有进入 v2 正文**，阶段表与验收中均无此件。所以缺口不是"脚本能力不足"，是"脚本不存在于蓝图"。裁定：意见的建议部分成立，问题定性修正为"维护件落地丢失，须整体补回蓝图（备份、条数核对、引用存在性抽查、失败告警四项一并写入阶段表）"。

**⑥ 壳路线文本矛盾＋权威词表映射——成立，两半都成立，且第二半应升级表述。**
第一半：联合评审 §七已定案第 1 条"壳自建首选"，其"仍待确认"第 1 条与 v2 附 1、§5.3 又建议"先用 WorkBuddy 验证／现成实现"，文本冲突属实；且如 §一.3 所述，还叠着铁律二与 WorkBuddy 当壳的结构张力，冻结时须一句话钉死三者关系（自建为定局、WorkBuddy 为有期限的验证脚手架、其含模型一事是已知例外）。第二半：三级（v2）与四级（记忆线 v0.2 约定 6）的映射确实未定，而 contracts 的权威词表本就"待两线共同定稿"——注意这不是哪一线单方面能定的事，按宪章须走 contracts 且留痕。老邪"vendor 是来源轴、raw 是加工轴、一份厂商导出原样存档同时占两格"的分析准确，且与记忆线评审 R2"raw 是载体标记、不得因导入取得事实权威"的释义正好互补，两份意见应在契约里合并成一张映射表。老邪建议"列为阶段二前置"，采纳并升级：不只是词表，**provenance 信封＋词表映射＋事件模型归属（见 §一.4）三者同属一页契约，应整体列为阶段二的开工门**。

## 三、全部现有材料共同遗漏的问题

以下七条，联合评审、升级报告、家底盘点、老邪意见均未提出：

1. **名册字段表在落地时丢失。** 联合评审 §2.3 给过完整的 `agents.yaml` 字段表（invoke/caps/resume/limits/notes），并强调"能力声明不是文档装饰，宰相派活前必须看它"。v2 正文只有选人矩阵（§5.3），名册的字段结构一字未落。没有 caps/resume/limits，宰相决策（阶段四）就没有可依据的输入格式，矩阵只是一张人事表。须在冻结时把字段表补回蓝图或立为名册文件规范。

2. **入口白名单在落地时丢失。** 联合评审 §四裁定"跨入口身份体系保持现状白名单"，dsh 侧亦有 Telegram 唯一用户白名单的现行事实（verdict §3.3）。v2 的任务入口含 Telegram（§4.3 `from` 字段）与多终端，却未写任何入口准入约束。任务入口即行动入口，无白名单的账本等于谁能发消息谁能派活。补一句即可，但不能不补。

3. **事件写入的身份与 git 作者的映射未定义。** §6.2 要求每条记"谁（厂商、agent、模型）"，但 Git 侧能自动给的只有机器的 git 凭据与 commit 作者；同一台机器上跑两个 agent（盘点已载：用户在 Grok Bot 云电脑上驱动 Codex）时，commit 作者无法区分执笔 agent。provenance 的第一要素在 Git 基座上的落法（事件内自报身份字段＋commit 作者双记、或每 agent 独立凭据）全文未定，阶段二开工即撞。

4. **凭据误入事件库的清除通道不存在。** 事件库 append-only 且进 git 历史：任一 agent 把令牌、密钥误写进会话或产物、被按 `vendor` 原样归档后，git 历史不可静默改写（改写与"只增不改＋审计"直接冲突），蓝图无任何脱敏/清除程序。升级报告 R7 的"可清除"是对 v1 数据层说的，老邪判其"随硬件线推迟合理"——本评审不同意：事件库是 v2 阶段二的产物、不是硬件线，清除程序至少要有最小版（发现即冻结该仓分发、轮换凭据、以新仓重建并留处置记录）。此条与老邪意见明确冲突，记录在案。

5. **宰相读记忆的范围未定。** 联合评审 §2.2 的工作流写宰相读"相关记忆摘要"，v2 §5.1 只说宰相"读任务与名册"。宰相能读到哪一级记忆（vendor 原文？仅 confirmed？摘要由谁生成）关系到黑箱路由与信息最小化，也关系到 Codex 自带记忆"只当缓存、不参与晋升"这条盘点风险（§2.1 风险 1）在 v2 中的落点——v2 全文未提各 agent 原生记忆与共享记忆的权威关系，阶段二"换 agent 接手验证"时必然撞上（接手者读的是共享事件还是前任的原生会话，结论完全不同）。

6. **阶段二与记忆线阶段二的工期耦合无人声明。** 记忆线阶段二有硬里程碑（厚管线 Chat 最小闭环），其事件模型、存储与 v2 阶段二的事件入库是同一片地。两份蓝图的阶段表各写各的，没有一处写明：v2 阶段二的事件库是否就是记忆线统一事件模型的第一个消费者，还是先行自建、将来再并。若各建各的，铁律四在跨线层面即被破坏（见 §一.4）。这不是文档洁癖：contracts 至今未定稿，正是两线在用阶段表互相等待而无人点名。

7. **宪章与蓝图的冻结状态倒挂。** 根 `AGENTS.md` 已在"文档角色"中宣布 v2 为"整体线当前唯一执行蓝图"、当前阶段一节亦然，而 v2 自身状态仍是"定稿草案，待用户裁定后冻结"。执行依据的效力不应先于裁定生效；本次冻结裁定作出后此倒挂自动消除，但若用户裁定暂不冻结，须同步把宪章表述降回"待冻结草案"，否则后来者会按已生效蓝图行事。
