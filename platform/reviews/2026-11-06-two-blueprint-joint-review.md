v1 的前提错误，用户五项纠正已推翻其骨架。逐条后果：

| 用户纠正 | v1 错在哪 | v2 怎么改 |
|---|---|---|
| ① 数据主权是远期蓝图，现阶段先管好各厂商 agent、降管理成本 | v1 把主权当唯一判据，凡不符即砍 | 重定卖点：**跨厂商 agent 治理**；主权降为长期积累，判据换成「是否降低管理成本」 |

因此 v1 的三处结论作废或收窄：**§1.1 OpenBot 四道硬门槛**（三条降级）、**砍 provenance 与四档权威**（收回）、**五件清单**（改四件）。逐处标注于下文。**v1 仍成立的判断**（不 fork、只落配置与插件层、砍厚薄双管线、砍实验室级信赖门、砍交接状态机与五段状态）继续有效。

## 结论

**一、系统定位重新落定：这是一套「跨厂商 Agent 组织治理层」，不是数据主权平台的早期版本，也不是某个 agent 应用的外挂。**

现阶段要解决的三件事，按优先级：多厂商 agent 的**统一调用**（不破权限墙）、**协作与交接**（谁做什么、上一任做了什么）、**共享记忆**（换个 agent 还认识你和你的活）。数据主权是这三件事正常运转若干年后自然长出来的资产，不是前置条件。

**二、因此不存在「核心 agent」，也不该存在「核心执行器本体」。** 唯一稳定的东西必须是**不属于任何厂商的一个薄壳**：它自己不含模型特权、不持有 agent 身份，只做派活、记账、传记忆。宰相席位是配置里的一个指针，随时换人。

**三、DSH 的角色下降一格：从「执行器本体」变为「一个 adapter ＋ 默认宰相候选」。** MIT、自托管、插件化、有 `acp`／`headless`／`sdk` 多个可编程 profile（采收 B3），使它成为最容易驱动、最容易替换的候选——但**它就是候选人之一**，与其他厂商的 CLI 平权。

**四、真正要建的只剩四件，且其中两件在源头是同一个东西。** 详见第五节。记忆的原始事件库，就是未来的数据资产，不要建两份。

**五、既有四份评审稿的过度工程化结论大部分维持，但有一项要收回**：provenance 信封在多厂商治理下是刚需，不是官僚开销（见第四节 ①）。

## 一、系统定位重写

### 1.1 三层价值，分时间尺度

| 尺度 | 是什么 | 判据 |
|---|---|---|
| **现在** | 把你手上所有厂商的 agent（含已付费订阅）收进一个调度面，统一派活、统一记账、统一记忆 | 每周省下多少手工搬运？换来多少「不用重复解释」？ |
| **中期** | 多 agent 协作：分工、交接、复核；宰相席位可换 | 一件活能不能被拆给最合适的那家做完并接得上 |
| **长期** | 数据主权资产：你与所有 agent 的全部交互，带完整来源，存在你手里，可迁移、可定价、可授权 | 这份资产离开任何一家厂商仍然完整 |

**关键**：长期资产不是中期之后再动工的新项目，而是**现在这条记忆链正常运转的副产品**。所以 1.5 说「记忆原始库＝未来数据资产」不是修辞，是工程上的合并。

### 1.2 宰相席位制（用户纠正③的工程化）

**规则**：任何时刻有且只有一个「当前宰相」，由配置里的一个指针决定；宰相的职责是**产出派活决策**，不是获得特权。

- **席位不属于任何厂商**。壳（调度层）是常设的，宰相是变量。
- **换人成本＝改一行配置**（`chief: codex` → `chief: gemini`）。不迁移数据、不重装、不改代码。
- **宰相能做与不能做**：能看任务、看 agent 名册与能力声明、读记忆；不能给自己或他人扩权、不能绕过权限墙、不能改壳的配置。
- **选谁当宰相**：由用户按各家当前表现决定；壳可以按任务类型给建议（例如「代码类任务建议 Claude/Codex，检索类建议 X」），但建议不自动生效。
- **为什么必须这样**：任何把某家 agent 写成「本体」的方案，都会在半年内被它自己的模型换代或产品转向绑死。这一点用户判断正确，且比多数架构文档清醒。

**首任宰相：Codex CLI，理由是实测而非偏好。** 家底盘查（[独立文档](2026-11-06-agent-fleet-inventory.md)）结论：Codex 是当前唯一同时具备「非交互执行（`exec`）＋ 结构化输出（`--json` JSONL / `--output-schema`）＋ 会话续跑（`resume`）＋ 常驻 daemon（`app-server`）」四项的执行器。用 JSON Schema 约束路由决策输出这一项，把「宰相」从模糊的模型判断变成可校验的结构化调用——这是选它的决定性理由，不是它模型最强。

**首任不是终身。** 席位制的意义在于：Codex 退位只需改 `chief:` 一行。而它与 PAT 记忆的关系必须提前划清——Codex 自带 `memories/`、`sessions/` 体系，**只当上下文缓存，不参与记忆晋升**，否则就是评审稿反复警告的「第二套权威」。

### 1.3 连接策略：双模——推与拉（2026-11-06 二次修正）

**用户质问推翻了本节的初版：** 「为什么不能用 grokbot 在他的云电脑上安装其他 agent 的 cli 来解决统一操作问题？我目前就试过在他的云电脑上去驱动 codex。」

**我错在哪**：我只找**入站的门**（能不能从外部调它），从未问**它能不能自己出来取活**。Grok Bot 的云电脑有 **terminal、持久文件系统、可安装任意软件**，routines 支持按计划／事件／webhook 触发——**它不需要门，它能走出来**。用户已经实测过在它上面驱动 Codex，这不是设想。

**这不是绕过权限墙，这是用厂商给的东西。** 恰恰是最合规的一路：对端用自己的账号读你的仓库、提交结果，全程在厂商认可的连接形态内，协调面**不需要暴露任何端口**。比打洞进 `:1340` 干净得多、持久得多。

于是连接策略从「四层单模」修正为**双模**：

| | **推（Push）** | **拉（Pull）** |
|---|---|---|
| 谁发起 | 壳 → 执行器 | 执行器 → 协调面 |
| 适用 | 机器可达（本机、自租 VPS、可 SSH） | 机器不可达（厂商云电脑、墙后） |
| 手段 | 子进程 CLI、ACP stdio、本地 HTTP | 定时/事件/webhook 触发 → 取任务 → 执行 → 回写 |
| 依赖 | 壳能连到那台机器 | 只要对端能 git pull/push |
| 典型 | Codex、DSH、Grok Build | **Grok Bot**、Muse 云、任何封闭云 agent |

统一的方式：两模共用同一个任务账本与结果格式，执行器在名册里声明 `mode: push | pull`。

**四层手段作为「推」模式内部的分级仍有效**（子进程 CLI 优先 → ACP/MCP → 本地 HTTP → SDK）。

**红线不变，但范围要精确**：不逆向私有协议、不伪造浏览器会话、不抓包重放、不代持凭据、**不依赖未文档化接口**。Grok Bot 的 `:1340` 仍不用——因为它是未文档化的内部网关；但「在它的云电脑上装 CLI」用的是它公开提供的 terminal，性质完全不同。

**代价要提前认**：每个 adapter 的能力受那家所赐。实测已把差距摊开（详见[家底盘查](2026-11-06-agent-fleet-inventory.md)）：Codex 四项全通；DSH 待测；WorkBuddy 有内置 CLI 未上 PATH；Muse 的 SDK 方向相反；**Grok Bot 有 terminal 与 routines 但没有入站 API**——它天生就是拉模式的一端。

**Grok Bot 专属三条硬伤**（官方文档明载，知情使用）：
1. 一个账号的**所有 Bot 共用一台云电脑**，文件／浏览器会话／凭据互通，官方明写「独立 Bot 不构成安全边界」→ **不放长期凭据，用短时令牌**。
2. 模型自动路由、不可选、无产品级消费上限、beta 无 SLA → **不跑不可中断的关键路径**。
3. 属厂商云，随时可能改版 → adapter 必须**可降级**。

### 1.4 记忆落点：Git 短期基座，云端服务为长期（2026-11-06 用户裁定）

用户已定：**记忆库目前落在 GitHub 仓，分项目仓、llm-wiki 仓，可再建一个私密的共享记忆仓；必要时也可在自己租赁的 VPS 上建；短期用 Git 最方便最快，长期需要更快更安全、更符合总体要求的云端方案——即本项目中另一份蓝图研究的对象。**

**这个裁定的价值在于它消掉了原本的一个过度设计。** 我先前把记忆面当成要新建的东西，实际你已经在用 Git 承载记忆：项目仓、`llm-wiki` 仓。再建一个私密共享记忆仓，协调面就现成了。

Git 恰好满足这套系统的大部分需求，这不是将就：

| 需求 | Git 天然给的 |
|---|---|
| 多机器多厂商读写 | 每台机器每个 agent 都有自己的 git 凭据 |
| 不开端口 | 全是出站连接 |
| 只增不改 | commit 本身即 append-only |
| provenance（谁／何时／经何通道） | 作者、时间、commit hash、分支 |
| 任务领取不冲突 | push 竞态＝乐观并发，失败者重试即得 |
| 审计与可迁移 | `git log`；本来就是文件 |

**关键设计：接口与后端分离。** 协调面读写抽象为「追加一条事件／查一个任务」，底层是 `backend: git | service`。换云端服务时接口不变——**两份蓝图因此不是两条路，是同一条路的两个站点**。这也让「另一份蓝图的云端方案」有了明确的位置：它是本蓝图的第五阶段，不是竞争方案。

**迁移信号先定，免到时候凭感觉**：单次检索超 2–3 秒、clone 变慢、并发写冲突每天多次、需要语义检索——任一出现即上云端服务。

### 1.5 记忆与数据资产：核心，且同源（用户纠正④）

全案最要紧的一处简化：

**记忆的原始事件库，就是未来的数据资产。不要建两个东西。**

- **今天**它的身份是「共享记忆的真相源」——所有 agent 的交互、工具调用、结论，带来源落盘，供检索、供换 agent 后接着干。
- **将来**它的身份是「数据主权资产」——同一份东西，加了确权、授权、定价之后就是资产。
- **反过来说**：若为「记忆」建一套、为「资产」再建一套，两者必然分叉，且分叉处必然是失去来源信息的那一侧。

所以：**一个 append-only 事件库 ＋ 一套 provenance ＋ 一个检索面**，同时服务当下与长远。这也是第四节要收回「砍 provenance」那条结论的原因。

**必须记的三样（缺一样，未来资产就不成立）**：

1. 谁说的（厂商 / agent 身份 / 模型）——多厂商场景下这是第一性信息
2. 什么时候、经由什么通道（CLI 调用 / MCP / 导入）
3. 它依据什么（原始引用，可回查）

## 二、架构：薄壳 ＋ 全员 provider

```
用户（Web / Telegram / 手机 / 语音）
        │
        ▼
┌───────────────────────────────────────────────┐
│ 宰相府（壳，不含模型特权、不属于任何厂商）      │
│  派活决策 ← 当前宰相（可变指针）               │
│  任务账本  │  名册与能力声明  │  记忆客户端     │
└───────────────────────────────────────────────┘
        │  CLI 子进程 / ACP / 本地 HTTP
        ▼
┌────────┬────────┬────────┬────────┬───────────┐
│ Claude │ Codex  │ Gemini │ DSH    │ 其他/自建 │
│ CLI    │ CLI    │ CLI    │ acp    │           │
└────────┴────────┴────────┴────────┴───────────┘
        │ 各自登录态、各自权限墙，互不代持
        ▼
   共享记忆（append-only 事件库 + provenance + 检索）
        │
        └──→ 未来：数据主权资产
```

### 2.1 为什么壳不能是某个 agent

用户纠正③已给出答案，这里补工程理由：**如果壳是一个 agent，它就必须有一个模型、一个 prompt、一套工具权限——这三样全都属于某一家**，于是「换核心」就变成「迁移整个系统」。壳一旦不含模型，换宰相就真的只是改一行。

**壳的最小职责只有四件**：把请求变成任务、按宰相决策派给某个 adapter、把结果与动作记进账本和记忆、把结果送到人面前。够用即止。

### 2.2 宰相怎么工作（且不加管理成本）

```
1. 用户提请求 → 壳建任务（id / 来源 / 目标）
2. 壳向宰相提供：任务文本 + 名册与能力声明 + 相关记忆摘要（不是全文）
3. 宰相返回派活决策：{agent, 子任务, 依据}      ← 只出决策，不出权限
4. 壳调该 agent 的 adapter 执行，产物按引用回传
5. 全程入账本与记忆；结果送达用户
```

**降成本的三条硬规矩**：

- **确定性优先**：用户显式指定（`--by codex`）、回复某条任务消息、单 agent 足以完成时，**不经过宰相**。只有真歧义才叫模型判断（与整体线升级稿 R2 同向）。
- **宰相只做路由**，不做执行、不复述任务全文给用户、不产生额外对话轮。路由结果是一段短 JSON，不是一篇分析。
- **宰相可自荐换人**：任务类型与名册能力不匹配时给一句建议，但必须用户点头。

### 2.3 名册与能力声明（adapter 契约）

一个 `agents.yaml`，每家一段。这是整个系统唯一需要随厂商变化的文件。

| 字段 | 说明 |
|---|---|
| `name` / `vendor` / `model` | 身份三元组，写进每条记忆的 provenance |
| `invoke` | 如何起（命令、模式、超时） |
| `caps` | 能力声明：headless / 续会话 / 结构化输出 / 工具调用 / 图像 / 附件 |
| `resume` | 能否接着上次干（原生 session id，还是只能重述上下文） |
| `limits` | 额度与计费口径，用于派活时避坑 |
| `notes` | 权限墙备注：这家什么不能做，换什么手段达成（不是破墙） |

**能力声明不是文档装饰**：宰相派活前必须看它。给一个不能续会话的 agent 派长任务，等于让下一任从头再来。

### 2.4 DSH 的角色（v1 结论收窄）

v1 说「DSH 是执行器本体、不是可换件」，现在改为：

- **DSH 是一个 adapter，与其余厂商平权。** 通过它的 `acp` / `headless` / `sdk` profile 被壳驱动。
- **它是最好的默认宰相候选**，理由：MIT、自托管、无供应商额度墙、插件化、可编程 profile 最全（采收 B1/B2/B3）。**不是因为它强，是因为它最不给你添麻烦。**
- **v1 仍然成立的那句**：不 fork。但理由变了——不是「因为它该当本体」，而是「它只是候选人之一，为候选人 fork 源码毫无道理」。
- **两个已知短板要记**：`0.2.1-rc.4` 且官方明言会有破坏性变更；与别家 agent 的互操作要靠 ACP，而 ACP 覆盖不全（采收 B21）。

## 三、OpenBot 重新评估（v1 结论部分收回）

v1 列了四道硬门槛否决它当底座。按用户纠正①②重审，**其中三条要么失效要么降级**，仅剩一条支撑「不当壳」，但理由换了。

| v1 的门槛 | 重审结论 |
|---|---|
| PolyForm Noncommercial 许可 | **降级**。个人非商业使用是被允许的。真问题只剩两条：不能并入未来 Apache-2.0 公开仓；用它代码做的改造不能对外分发。v1 把它列为首要否决，是我把「主权是唯一卖点」这个错前提带进了许可判断——认错 |
| `danger-full-access` ＋ 从不询问 | **降级为知情项**。这是它的产品取舍，个人自用可接受。v1 说「用自己的论点反着实现」过重了 |
| 桌面优先 ＋ Electron on server | **保留但降级**。它确实支持无头 VPS，只是重；你的主战场是调度面，不是桌面 |
| 状态落在它的私有 SQLite schema | **保留，且升为唯一支撑理由**。见下 |

**幸存的那条，换了说法**：用户纠正②说得很清楚——**治理本身就是这套系统的卖点**。那么「治理状态归谁所有」就不是实现细节，而是产品本体。把任务账本、agent 名册、记忆索引放进一个非开源产品的私有表结构，等于把卖点寄存在别人家里。**同时它还自行下载并钉版 provider CLI**（README 原文「prefers its managed CLI」），连你手上各家 agent 的版本都由它决定。

所以结论改成：**OpenBot 是这套架构最好的教科书，不是最好的房子。**

它的三样东西必须抄，而且要抄准：

1. **provider 接入清单**：十余家 CLI 的具体驱动方式——Codex App Server 走 stdio JSONL、Claude Agent SDK 走 stream JSON、Hermes 走 ACP。这份知识是各家 CLI 差异的硬积累，比任何文档都值钱（采收 B21 记的就是它）。
2. **凭据态度**：用各家 CLI 自己的登录，不复制、不代持、不落日志。这正是用户纠正⑤要的形态。
3. **原生 session id 只作私密恢复句柄**：换底座时对话连续，但恢复句柄不进业务逻辑。这个分寸拿捏得对。

**能用的边界**：它当前许可非自由，所以**只读设计、不搬代码**；若将来真要复用实现，先核对所选版本的许可范围（≤0.1.11 是 Apache-2.0）。采收 C9 的判断同样适用——借鉴设计与接口形态，不复制实现。

## 四、过度工程化重新甄别

判据换成用户纠正①的那句：**这东西加不增加管理成本？** 每件都要回答「每周花我多少分钟」。

**我上一轮砍错、本次收回的一条**：

**① provenance 信封 —— 从「砍」改回「立」为刚需。**
v1 把它归入「给多人追责准备的多余开销」。错。**多厂商治理下它是第一性信息**：同一件事，是 Claude 说的还是 Gemini 说的？是它读到的还是它猜的？换宰相后新宰相凭什么相信这条记忆？没有 provenance，共享记忆在有 3 个以上 agent 时会退化成一锅来源不明的粥。用户纠正④把记忆定为核心，provenance 就是核心里的骨架。

**② 权威档位 —— 从「两级」调回「三级」，并按多厂商现实重命名。**

| 档 | 含义 | 谁给的 |
|---|---|---|
| `vendor` | 厂商侧产出：会话、导出包、模型回答 | 厂商（未经你确认） |
| `inferred` | 本系统机器提炼：摘要、合并、推断 | 我们自己的加工 |
| `confirmed` | 你确认过的结论 | 人 |

v1 砍成两级是把 `vendor` 与 `inferred` 混为一谈——而这两者可信度**根本不同**：一个是「别家模型说过的话」，一个是「我们自己推的」。合成一级等于放弃分辨来源，正好废掉记忆的核心价值。四档（raw/inferred/curated/approved）确实过细，三级够。

**继续砍、维持 v1 判断的**：

| 条目 | 处置 | 一句话理由 |
|---|---|---|
| 厚/薄双管线 ＋ 对冲一二三四 | **砍薄管线** | 蓝图自称「薄只是厚的前置过滤，不是平行系统」；不是平行系统就别先建两套再防打架 |
| 候选门「校准概率＋阈值」 | **降为人工审核清单** | 你自己在未决项里写「小模型概率可信度未验证」；没把握的不进正文 |
| 六件治理组件 | **留 provenance ＋ 一个 cron** | 衰减、检索轨迹、镜像校验是多人多租户的活 |
| git 镜像导出器 ＋ 完整性校验 | **换成一条备份命令** | 原始会话本来就在磁盘上；缺备份不缺导出器 |
| 实验室级信赖门（同来源/同截面/同 reader/同预算/分功能记录） | **砍成 20–30 题自测集** | 个人语料撑不起统计显著性 |
| JS/SQL 可编程查询面 | **降为 grep ＋ SQLite 只读** | 原则留，执行面砍 |
| 评测常设对照臂 ＋ 证据链题 | **推迟** | 现在没有对照组要打 |
| 交接状态机（已完成/未完成/外部影响/可复核产物/待决事项） | **砍成 `handoff` 一段文本** | 跨 agent 交接要留痕，但留痕不必是状态机。写清「做到哪、产物在哪、下任注意什么」即可 |
| 五段状态 ＋ 幂等键 | **砍成三态** received / done / delivered | 工单系统 vs 派活 |
| 跨入口身份体系 | **保持现状白名单** | 你就是唯一用户 |
| 独立看门狗 Agent（能在线改提示词） | **砍成 cron ＋ 日志检查** | 采收 E15 自己也写了权限面与治理闸有张力 |
| 投机执行 / 后台主动性 | **推迟** | 先有稳定单任务流 |
| 工作记忆独立服务 ＋ thread-keeper 候选 | **砍，并入任务账本 ＋ 记忆库** | 三个名字（工作记忆/持久任务记录/快层）指向同一需求，三套设计是分叉源头 |
| 边缘层独立成层、e-ink 终端、MQTT 桥 | **全部推迟为开放选项** | 用户纠正⑤：硬件「不成为阻碍」而非「不碰」。手机为默认终端，其余只做补充入口（见第八节），因此不需要独立的边缘层立项 |
| 四类契约各成一份文档 | **合成一页** | 一个人不需要四份对接契约 |

## 五、目标形态：四件

| # | 件 | 职责 | 为什么不可省 |
|---|---|---|---|
| 1 | **宰相府（壳）** | 任务账本、名册与能力声明、派活（确定性优先＋宰相决策）、结果送达 | 系统的本体；不属于任何厂商，这是「无核心」的唯一实现方式 |
| 2 | **共享记忆** | append-only 事件库 ＋ provenance ＋ 检索；同时是未来数据资产的种子 | 用户纠正④定为核心关键；换 agent 不重来靠它 |
| 3 | **adapters** | 每家一个：CLI 调用、能力声明、resume、额度 | 连接层；只增不改，加一家不动壳 |
| 4 | **maintenance 脚本** | 备份、条数核对、失败告警 | 采收 E1：永不信自报成功。成本极低，收益最大 |

**明确不建**（现阶段）：数据定价授权、Hy 作为必选底座、独立工作记忆服务、看门狗 Agent、四份独立契约、边缘层立项。

**不建 ≠ 不接**：MQTT 桥、e-ink、设备采集这一组**不是「不做」，是「不成为阻碍」**——手机即默认终端，其余终端随时可接，接的时候不改壳。做法见第八节。这是用户纠正⑤的原意，与 v1 的「全部砍掉」有实质区别。

**共享记忆的后端起步**：文件 ＋ SQLite FTS 跑通即可，Hy 作为**可选第二后端**。理由不变（原始记录与账本没跑通就上 Hy 等于给不存在的系统装涡轮），但理由现在更强：多厂商场景下 `vendor` 来源必须精确可查，而 Hy 的 raw 是会裁剪的副本（记忆线评审 R1 已查实），不能当真相源。

## 八、硬件：开放接入，不做前置（用户纠正⑤的工程化）

用户原话：**「硬件作为开放选项，不是现阶段不碰，而是不成为阻碍，随时可以接入，可以把手机当做默认的硬件终端，其他终端只是手机的补充入口，接入的是 vps 和云电脑上的某个 agent」**。

这句话按工程翻译，有四条硬约束：

1. **手机是第一终端，不是过渡品。** 它有摄像头、麦克风、屏幕、常驻网络、成熟的通知系统——采集与显示的物理条件本来就齐。此前蓝图把它当「借屏」的临时件，是低估了它。
2. **其他终端只做补充入口，不各自成套。** e-ink、ESP32、手表、车机，都只补手机缺的那一项（常亮、盲操、免手持），**不各自建一条采集链路**。这直接砍掉了 v1 里「边缘层独立成层」的必要性。
3. **终端接的是 VPS／云电脑上的 agent，不是终端里的 agent。** 终端只做 I/O，智能在远端。这正是用户第 5 条「不破权限墙、用天然允许的连接形态」在硬件侧的同一句话。
4. **所以硬件接入的接口只有一个：消息与文件的收发面。** 手机端能发消息、能收结果、能传文件，就已经是最小可用终端。ESP32 那一套等真要「常亮+盲操」时再接，接的时候也不改壳。

**因此「不成为阻碍」的具体含义**：adapter 抽象里，「终端」与「agent」是两个独立维度——终端决定**输入输出长什么样**，agent 决定**谁来干活**。手机今天就能当终端，因为它走的是 message/file 接口；换成 ESP32 只是换一个说同样接口的客户端。**这个抽象现在定下来，硬件就永远不构成返工风险。**

**唯一要现在留的口子**：消息里带得动「附件引用」（不塞二进制本体）。这是手机与未来任何终端都能满足的最小约定，也是数据层不被终端绑架的前提。参考采收 C8 的 manifest 形态（owner / recipients / size / SHA-256），不要发明新的。
