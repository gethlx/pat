# PAT 个人 Agent 治理架构 v2

> 状态：**定稿，首版实施基线**（2026-11-07 经用户裁定冻结）
> 维护线：整体线（共享记忆为本项目子项目，区在 memory/，要求见 §十一）
> 最后更新：2026-11-07
> 摘要：把系统定位收正为「跨厂商 Agent 组织治理」——协调面（调度＋记忆治理）、全员 provider 双模接入（推/拉）、Git 作短期协调与记忆基座、宰相席位可换（机制＋当前推荐顺位＋选择决策规则，不预设人选）、终端以手机为首；共享记忆为本项目子项目；数据主权为长期副产品。

## 这份蓝图解决什么

手上有多家的 agent：Codex、DSH、WorkBuddy、Grok Bot、Muse，各自的机器有的在本机、有的在自租 VPS、有的在厂商云上。现在的问题是：

- 每家的活要分别去开、分别去记，**换个 agent 就要重新解释一遍你是谁、在做什么**
- 哪家擅长什么、上次谁做的、做到哪一步——全靠脑子记
- 想让它仨协作，得手工当人肉总线

**本蓝图只解决这一件事：把散在各家的 agent 收成一个能统一派活、统一记账、共享记忆的治理面——只治理经协调面进入的活。** 治理负担不得长期高于它节省的整理成本（见 §十一.9）。

（取舍：「收成一个」不是覆盖你和某家的直接对话；不经协调面的活不入账，避免同一件事两处记账。第一版就会有壳、账本和归并，不是零成本，所以管理成本对齐 §十一.9 的可计量标准，而不是口号。）

数据主权（确权、定价、授权）是这套系统正常运转若干年后自然长出的资产，**不是前置条件，也不驱动当前设计**。但它要求现在的记忆必须以「带完整来源、可迁移、存在自己手里」的形态积累——见 §6。

## 一、五条设计铁律

1. **不设永久核心 agent。** 任何时刻只有一个「当前宰相」产出派活决策，席位是配置里的一个指针，换人只改一行。**席位不属于任何厂商。**
2. **壳不做 Agent 的事。** 壳可以调用模型，但只能当辅助工具用：有界的加工步骤（提炼、归类、合并、校验），由壳的确定性逻辑调用，输入输出明确，不持任务、不自主决策。把模型当 Agent 用——在壳内自主定目标、接任务、作派活与执行决策——禁止；那是坐席宰相与被派活的 agent 的事。共享记忆治理属"工具"范围。所用模型可替换，全部状态沉淀在自有仓内，换模型不迁系统。
3. **不突破权限墙。** 只在厂商天然允许的形态内调用：官方 CLI、ACP/MCP、本地 HTTP、以及**由对端自己发起的拉取**。不逆向私有协议、不伪造会话、不代持凭据、不依赖未文档化接口。
4. **记忆与数据资产同源。** 只建一份 append-only 事件库，带 provenance。今天它是记忆的真相源，将来它就是资产本体。不建两份。任务账本是该事件库的当前视图，不是第二份真相源。记忆治理（提炼、晋升、整理）是本项目内建职能，与调度同属协调面，不设并行线；详细设计在子项目层展开，框架要求见 §十一。
5. **硬件不构成阻碍。** 手机是默认终端；其余终端随时可接，接入时不改壳。终端与 agent 是两个独立维度。

## 二、架构：三面 + 双模

```
                          用户
              Web / Telegram / 手机 / 语音
                            │
                            ▼
        ┌───────────────────────────────────────────┐
        │  协调面（你的；调度＋记忆治理）              │
        │  任务账本 · 名册 · 派活 · 送达 · 记忆治理     │
        │        当前宰相 = 一个可换的指针            │
        └───────────────────────────────────────────┘
                    │                   ▲
        推（Push）  │                   │  拉（Pull）
        壳调它      │                   │  它来取
                    ▼                   │
        ┌──────────────────┐   ┌────────┴──────────┐
        │ 可到达的执行器     │   │ 不可到达的执行器    │
        │ 本机 Codex         │   │ Grok Bot 云电脑     │
        │ 自租 VPS 上的 DSH  │   │ 厂商云 agent        │
        │ 任何能 SSH 的机器   │   │ 任何你打不进去的机器 │
        └──────────────────┘   └───────────────────┘
                    │                   │
                    └─────────┬─────────┘
                              ▼
        ┌───────────────────────────────────────────┐
        │  记忆面（你的，短期 Git / 长期云端服务）    │
        │  事件库 + provenance + 检索                 │
        │  今天：换 agent 不重来                       │
        │  将来：数据主权资产                          │
        └───────────────────────────────────────────┘
```

注：Muse（Meta）不在执行器列——其开放接口方向是终端面，见 §5.3 与 §七。

**为什么必须有「拉」这一模。** 我上一版把 Grok Bot 判为「有算力没门」，错在只找**入站的门**。它的云电脑有 terminal、有持久文件系统、能装任何 CLI——**它不需要门，它能自己走出来取活**。你在它的云电脑上驱动 Codex 已经证明了这条路。这不是绕过权限墙，这是用厂商给的东西。

## 三、双模连接：推与拉

| | **推（Push）** | **拉（Pull）** |
|---|---|---|
| 谁发起 | 壳 → 执行器 | 执行器 → 协调面 |
| 适用 | 机器可达：本机、自租 VPS、能 SSH 的机器 | 机器不可达：厂商云电脑、权限墙后面 |
| 手段 | 子进程调 CLI（`codex exec`、`dsh headless`）；ACP stdio；本地 HTTP | 对端定时/事件/webhook 触发 → 从协调面取任务 → 执行 → 回写结果 |
| 依赖 | 壳能连到那台机器 | 对端能 git pull / git push；写回使用只覆盖任务账本的短时限权令牌，不使用账号级长期凭据 |
| 典型 | Codex、DSH、Grok Build | **Grok Bot**、Muse 云、任何封闭云 agent |

**关键性质**：拉模式下，协调面**不需要暴露任何端口**。对端用厂商认可的出站连接取任务、提交结果。这比打洞进 `:1340` 干净得多，也持久得多。

**统一的方式**：两种模式共用同一个任务账本与同一套结果格式。执行器只声明自己用哪种模式（名册里的 `mode: push | pull`），壳按声明调度。

**Grok Bot 的三种用法**（按可靠度排序）：

1. **Pull worker（推荐）**：在它的云电脑上装好 CLI，跑一个取任务的循环（或挂一个 routine/webhook 触发）。它自己拉活、干活、推结果。**这是把「配置最高的 VPS」真正用起来的方式。** 阶段三的落地约束见 §八：独立 worktree、只覆盖任务账本的短时令牌、全机只允许一个领取进程。
2. **长时执行体**：把耗时长的任务（批量研究、通宵跑批、定期巡检）交给它，因为它 24/7 在跑，不占你的机器。
3. **宰相候选（不推荐）**：它的模型自动路由、不可选、不可观测，且无稳定 API。让它当宰相等于把路由决策交给一个你看不见的黑箱。

**注意三条它的硬伤**（官方文档明载，必须知情）：
- 一个账号的**所有 Bot 共用一台云电脑**，文件、浏览器会话、登录凭据互通；官方明写「独立 Bot 不构成安全边界」。→ **不要在它的云电脑上放长期凭据**，用短时令牌。
- 模型自动路由、不可选、无产品级消费上限、beta 无 SLA。→ **不让它跑不可中断的关键路径**。
- 属厂商云，随时可能改版。→ 它的 adapter 必须是**可降级**的。

## 四、协调面：Git 作短期基座

### 4.1 为什么是 Git

你的记忆已经在 GitHub 上分三个仓：项目仓、`llm-wiki` 仓，再加一个私密的共享记忆仓。**继续用 Git 做协调面，是当前成本最低且刚好够用的方案**，理由不是将就：

| 需求 | Git 天然给的东西 |
|---|---|
| 多机器、多厂商都能读写 | 每台机器、每个 agent 都有自己的 git 凭据 |
| 不需要开端口 | 全是出站连接 |
| 只增不改 | commit 本身就是 append-only |
| provenance（谁、何时、经什么通道） | 作者、时间、commit hash、分支 |
| 任务领取 | 同一仓库同一分支上领取必须串行；不支持同一任务双派 |
| 审计 | `git log` |
| 可迁移、可备份 | 本来就是文件 |

**领取冲突怎么处理。** 同一任务只派给一家，执行器在确认自己的领取记录已生效于远端后才开工。非快进拒绝时，只在专用且无未保存工作的领取副本上执行 `git fetch` 与 `git reset --hard`，重读 `tasks/inbox/` 后再决定是否领取。禁止对领取提交做 rebase 或 merge。推送结果未知时先读回远端，确认归属后再决定下一步。

（取舍：rebase 领取提交会在同路径 add/add 冲突上把两边文件拼进工作区，不是「重试即得」。串行领取加失败后硬复位，比假装乐观并发更便宜、也更不容易把 inbox 领乱。）

**一句话：你已经有的东西，正好满足这套系统 80% 的需求。** 另建数据库是给自己找活。

### 4.2 仓的划分

| 仓 | 内容 | 可见性 |
|---|---|---|
| 现有项目仓（本仓） | 设计、代码、文档 | 私密（永不整体公开） |
| 现有 `llm-wiki` 仓 | 知识层（经人确认的高可信知识） | 独立仓，多 agent 共治 |
| **新建：共享记忆仓** | 事件库、任务账本、经验候选 | **私密**（GitHub 私密仓，现阶段单点；不设常驻镜像，阶段里程碑时归档完整克隆一份）；阶段一同仓起步，凭据最小权限；事件 JSONL 只由壳单一追加写入（归并），执行器不得直写——并发追加同一文件必冲突；禁止对该仓 `main` force-push |
| 将来：云端记忆服务 | 同一接口的快速实现 | 自租 VPS 或自建 |

阶段三拉模式写回之前，评估是否把任务账本拆成独立仓。

（取舍：GitHub 权限是仓级的。事件与任务同仓起步，管理成本最低；若不拆，拉工人的写凭证也能改事件库。所以同仓可以先跑，拆仓作为拉模式写回前的评估项，而不是阶段一就多仓。）

### 4.3 目录约定（第一版）

仓根直接是下列目录，不再套一层 `memory/`（避免与本项目 `platform` 仓里的 `memory/` 区重名）：

```
events/                 append-only 事件，按日期分文件（JSONL）；只由壳追加
├── 2026-11-06.jsonl
proposals/              经验候选，待人确认
├── 2026-11-06-*.md
confirmed/              你确认过的结论
index/                  检索索引（可再生，可丢弃）
tasks/                  任务账本（阶段一同仓；是否独立见 §4.2）
├── inbox/              待领
├── claimed/            已领（含 owner 与 deadline）
└── done/               已完成（含结果引用）
```

空的 `inbox/`、`claimed/`、`done/`、`proposals/`、`confirmed/`、`index/` 提交 `.gitkeep`，保证目录可克隆。禁止对记忆仓与任务仓的 `main` 做 force-push。

**任务文件字段**（够用即止，九个；当前状态以所在目录为准，不另设可写的 `status`）：

```json
{ "id": "t-20261106-001", "from": "telegram", "source_ref": "tg:chat:msg",
  "goal": "…", "owner": null, "mode": "pull", "deadline": null,
  "artifacts": [], "handoff": "" }
```

- `source_ref` 是来源侧唯一键（例如一条 Telegram 消息的稳定 id）。同一 `source_ref` 再投进来：不新增任务、不第二次执行，账本仍只一条；壳可在事件里记一条「重复投递已忽略」。
- `deadline` 是提醒复核的时点。逾期由维护脚本告警，任务保留在 `claimed/`。由用户确认旧执行已停止，并核对已有产物与外部动作后，再补记完成或释放回 `inbox/`。结果仍不明时保持待核，避免重复执行。
- 当前状态看文件在 `inbox/`、`claimed/` 还是 `done/`，不以文件内字段覆盖目录。
- 阶段一用命令行指定执行器时，该指定可不入库；在多于一个拉工人之前，补 `assignee` / `agent` 字段。

（取舍：目录表示任务当前状态，来源侧 ID 用于去重，`deadline` 用于触发人工复核。阶段一命令行指定执行器可直接由脚本处理。）

`handoff` 是一段自由文本：做到哪、产物在哪、下任注意什么。**不搞状态机。**

任务创建、领取、完成、释放等影响账本的变更都由壳追加对应事件，记录变更后的任务内容和所在目录。阶段一同仓时，事件和 `tasks/` 的对应变更写入同一个 Git 提交。按事件顺序即可重建 `tasks/`。阶段三若拆仓，先定清壳如何归并执行器回写并验证重建，再开放写回。

（取舍：这才能落实「一份真相源」。目录搬家是方便人眼和脚本，不是第二份账。）

**范围注记**：本账本只记经协调面派发的任务；其他渠道（如与某个 agent 的直接对话）产生的任务不入此账，避免同一件事两处记账。

第一版用户用脚本命令发任务、在仓内（`tasks/` 与事件）看结果。与现有日常入口的划界就是上面这条范围：只有交到协调面的活才被治理；直接对话可以继续，只是不入账、也不承诺换人接手不丢上下文。

### 4.4 什么时候换掉 Git

**信号先定，别到时候凭感觉**：

- 单次检索超过 2–3 秒，或仓大到 clone 变慢 → 上云端服务
- 多 agent 并发写入频繁冲突（每天多次） → 上云端服务
- 需要语义检索而不只是关键词 → 上云端服务

**换的时候接口不变**：协调面读写的抽象是「追加一条事件 / 查一个任务」，底层是 git 还是云端服务由配置决定（`backend: git | service`）。这正好接上本项目共享记忆子项目的云端方案——**它不是另一条路，是同一条路的下一站**。

## 五、宰相席位制

### 5.1 规则

- 一个指针：`chief: <agent-id>`（取值来自名册；当前在册示例：codex / dsh / grok-build。grokbot 为禁用项——黑箱路由，不合 §5.3 判据②）
- 宰相只做三件事：读任务与名册、给出派活决策（哪个 agent、什么子任务）、标记歧义需你定夺
- **不能**：扩权、改配置、绕过权限墙、替你做审批
- 换人＝改一行配置。不迁数据、不重装不改代码
- **确定性优先**：你显式指定（`--by codex`）、回复某条任务消息、只有一个 agent 能胜任时，**不经过宰相**。省一次模型调用，也省一次不确定性
- **决策入账**：宰相的每次派活决策（§5.2 的 JSON）随对应任务一并入账本，可查、可复盘
- **运行中不可用**：当前指针无响应、输出不合 schema 或额度耗尽时，回退到推荐顺位二；第二顺位也不可用则停摆待人，不得自行任命第三人

（取舍：顺位表的作用就是降级；蓝图不得自行任命。停摆比临时选一个未评过的 agent 更安全。）

### 5.2 派活决策的输出形态

用 JSON Schema 约束，输出是一段可校验的短结构，不是一篇分析：

```json
{ "agent": "codex", "subtasks": ["…"], "reason": "…", "need_human": false }
```

Codex 的 `--output-schema` 让这件事当场可做，这是它排在当前推荐顺位一的决定性理由。

### 5.3 名册、当前推荐顺位与选择决策规则

| 候选 | 可驱动性 | 适合 | 不适合 | 接入与定位 |
|---|---|---|---|---|
| **Codex CLI** | 实测全通：`exec`／`--json`／`--output-schema`／`resume`／`app-server` | 结构化决策、代码类执行 | 长期宿主（额度、厂商改版） | 推模式；宰相候选（顺位一）＋主力执行器 |
| **DSH** | 自有 VPS、MIT、`acp`／`headless`／`sdk`（本机侧三项待补测） | 长期宿主、数据不出门 | 冲锋（0.2.1-rc.4，会破坏性变更） | 推模式；宰相候选（顺位二）＋长期宿主 |
| **WorkBuddy** | 已装，内置 `@genie/agent-cli`（未上 PATH、未文档化） | 多模型人工入口（日常使用） | 当壳（自带模型、接口未文档化）；当被派活方 | 不进架构组件（壳为自建脚本，见 §八） |
| **Grok Bot** | 云电脑有 terminal，可装 CLI；routines 可定时/webhook | **拉模式 worker**、长时任务 | 当宰相（黑箱路由） | 拉模式执行工；不入宰相顺位 |
| Grok Build | 官方 CLI，待装实测 | 补 xAI 侧能力 | — | 推模式；实测后按决策规则定顺位 |
| Muse | Gadgets SDK 方向相反 | **硬件终端面** | 派活对象 | 终端接口，非执行器 |

**名册字段**（`agents.yaml`，宰相派活前必读）：`invoke`（如何起：命令／模式／超时）、`caps`（能力声明）、`resume`（能否续会话及方式）、`limits`（额度与计费口径）、`mode`（push／pull）、`notes`（风险与备注）。

**当前推荐顺位**（基于 2026-11-06 家底盘点，标注日期、随复测修订；**推荐不是任命**）：① Codex——四件套（非交互／结构化输出／续会话／常驻）唯一实测全通；② DSH——归属自有，本机侧可驱动性补测后确认；③ Grok Build——未实测，暂不入序。不入顺位：Grok Bot（可观测性判据出局）、WorkBuddy（非候选）、Muse（终端面）。

**选择决策规则**：

- **决定权**：指针由用户设定与变更；蓝图与任何 agent 不得自行任命，顺位只是建议。
- **判据**（按序）：①可驱动性——非交互调用、结构化输出、续会话，缺一不可；②可观测性——决策输出可校验，黑箱直接出局；③稳定性与额度；④同厂知情——宰相与主力执行器同为一家时须在册明示（不禁止，但要知情）；⑤历史表现——派活准确率、schema 合规率，阶段四有数据后启用。
- **顺位的作用**：用户未指定时取第一顺位为默认；用户指定者优先。
- **重评触发**：新 agent 入册、在任者连续失败或额度耗尽、家底复测结论变化——任一发生即重排顺位并记日期。换人仍是改一行配置。

**Codex 同时担任顺位一候选与主力执行器时的降级**（判据④已要求知情）：它作为执行器不可用或额度耗尽时，进行中任务不改 `owner`，新任务按名册能力改派；若它同时还是当前指针，指针改到顺位二。

（取舍：进行中的活换 owner 会造成两家同时写；指针可以立刻换，因为宰相只出决策、不持任务。）

## 六、记忆面：核心，且是资产的种子

### 6.1 来源、加工与人工确认

| 档 | 含义 | 谁给的 | 例子 |
|---|---|---|---|
| `vendor` | 厂商侧产出 | 厂商，未经你确认 | Grok Bot 说了什么、Codex 的会话、导出包 |
| `inferred` | 本系统机器提炼 | 我们自己的加工 | 摘要、跨源合并、经验候选 |
| `confirmed` | 你确认过的结论 | 人 | 进 `confirmed/` 或 `llm-wiki` |

`vendor` 标记来源，`inferred` 标记加工性质，二者都可以出现在同一条记录的证据链上。判断结论时回查来源与证据。人工确认绑定具体内容版本，内容含义变更后须重新确认。纠正或撤回时保留记录，并在召回时标明旧结论已失效。阶段二前在契约一页中写清这三类标记与子项目词表的对应关系。

### 6.2 每条必须记的三样

1. **谁**：厂商、agent 身份、模型
2. **何时、经何通道**：时间戳、push/pull、CLI/MCP/导入
3. **依据什么**：原始引用（可回查的 commit 或资产 ID）

缺任何一样，将来那部分就不构成资产。

### 6.3 与知识层的边界

- **经验**（本系统沉淀）→ 候选池 → 你确认 → 进 `llm-wiki` inbox
- **知识**（`llm-wiki`）→ 最高权威，按它自己的规则治理
- **单向**：经验可晋升为知识；知识不回流成经验
- 机器提炼永远不能冒充知识呈现

各执行器自带的记忆/会话体系只作其自身的上下文缓存，不参与本系统的权威与晋升；换 agent 接手时以事件库与任务账本为准，不以任何一家的私有会话为准。

### 6.4 凭据安全（三档，含非目标）

- **默认开、平时无感**：事件归并写入时过一道凭据扫描（仅扫已知格式，规则集借成熟开源项目维护）；命中内容进隔离区并提示用户一键处置（脱敏入库／误报放行／丢弃）。
- **文档原则**：给 agent 的凭据尽量限权、短时（§三对 Grok Bot 的短时令牌纪律，全舰队同理）；王冠级凭据（如全账号令牌）单独列名，永不进入任务材料。
- **处置一页**：发现泄露——先轮换作废，再冻结该仓分发、按处置记录处理历史，并留一条处置记录。删文件不是解药，轮换才是。
- **非目标**：不做审批流、不做加密事件库、不做审计后台。个人项目的防护以"平时零打扰、命中一次点击、出事读一页"为度。

## 七、终端：手机优先，其余开放

- **手机是默认终端**：它有摄像头、麦克风、屏幕、常驻网络、成熟通知——采集与显示的条件本就齐。它不是过渡品。
- **其他终端只补一项**：e-ink 补常亮、ESP32 补盲操、车机补免手持。**不各自建采集链路。**
- **终端接的是远端 agent，不是终端里的 agent。** 终端只做 I/O，智能在 VPS／云电脑上。
- **硬件接入的接口只有一个**：消息 + 文件的收发面。消息里用**附件引用**而非二进制本体（owner／recipients／size／SHA-256 四字段，借采收 C8 的 manifest 形态）。

第一个手机可达入口挂在阶段二完成标志，用 Telegram，沿用现有用户白名单。阶段一用脚本命令发任务和查看结果。

（取舍：这样阶段一保持「一条命令」骨架，又避免手机在阶段表里缺席、被做成过渡品。）

**这样定的好处**：换终端只换一个说同样接口的客户端，**硬件永远不构成返工**。Muse 的 Gadgets SDK 正好在这层有用——让 Muse 的生态硬件成为显示与输入的补充面。

## 八、分阶段

| 阶段 | 做什么 | 完成标志 | 不做什么 |
|---|---|---|---|
| **一　骨架** | 建共享记忆仓（仓根见 §4.3）与 `tasks/`；自建脚本壳最小版（参考 OpenBot 等项目的设计，代码自写）；跑通单向派活；维护脚本负责备份、失败与逾期告警；锁定 §十一的框架要求 | ①一条命令派活给指定执行器，任务与结果落仓可查；②同一 `source_ref` 重投只执行一次，逾期未回报的任务保留在 `claimed/` 等待人工核对；③从远端或里程碑归档恢复到临时副本，仅凭事件重建一条任务，核对状态、来源、归属和结果引用；④§十一框架要求已锁定为进入阶段二的前置 | 不建数据库、不建服务、不做语义检索 |
| **二　记忆** | 事件入库（壳归并）+ provenance + 凭据扫描 + 关键词检索；换 agent 接手验证；接上第一个手机可达入口（Telegram） | 一家做完的活，换一家接手能读到上一任做了什么（隔离自带记忆后仍成立）；抽查三条事件的原始引用可回查；一条任务能从 Telegram 进入协调面，并在手机上看到结果落账 | 不上 Hy、不做向量检索 |
| **三　拉模式** | 在 Grok Bot 云电脑上用独立 worktree 跑取任务循环；另做只覆盖任务账本的短时限权令牌（不能沿用附录验通时的账号级长期凭据）；全机只允许一个领取进程；写回前评估是否把任务账本拆成独立仓 | 一个任务被 Grok Bot 自己领走、做完、推回结果 | 不碰它的 `:1340`、不放长期凭据、不对 `main` force-push |
| **四　宰相** | 路由决策 + 换人演练 + 运行中不可用时的降级（回退顺位二，再不可用则停摆待人） | 一个未经用户指定执行器的任务，宰相输出通过 §5.2 的 JSON Schema，`agent` 取自名册且不是禁用项；换指针只改 `chief:` 一行、不改代码，改后仍能达到与阶段一第①条相同的观察点 | 不做多级委派、不做自动重试链 |
| **五　按需** | 终端扩展（e-ink／ESP32）、云端记忆服务、数据资产业务 | 有真实痛点才启动 | 不预建 |

（取舍：§十一是后补的框架约束。把它锁在阶段一出口、从阶段二完成标志拿掉「治理子项目首批里程碑」，阶段二才关得上门——阶段一锁定的是要求，不是把治理能力做完。）

**每个阶段只依赖前一个阶段的产物，任何一步停下来，系统都是可用的。**

第一版用户怎么用：用脚本命令发任务、在仓内看结果。只治理经协调面进入的活；与某家 agent 的直接对话不入账，除非用户把它交给协调面。

## 九、验收（六条，够了）

1. 一条命令派活给指定 agent，任务与结果可查（对应阶段一①）
2. 换用另一家的 agent 接手，能读到上一任做了什么（记忆有效；对应阶段二）
3. 以 `source_ref` 识别同一来源投递，重复投递只保留一条任务且只执行一次。模拟已执行但逾期未回报，确认告警后任务仍在 `claimed/`，人工核对前保持原归属（对应阶段一②）
4. Grok Bot 自己领走一个任务并推回结果（拉模式有效；对应阶段三）
5. 换宰相指针只改 `chief:` 一行、不改代码；改后仍能达到与第 1 条相同的观察点（一条命令派活，任务与结果落在仓里，`git log` 可查）。自动派的观察点见阶段四完成标志：任务未经用户指定执行器，宰相输出通过 JSON Schema，`agent` 取自名册且非禁用项（对应阶段四）
6. 从任务账本所在仓的远端或已写明的里程碑归档恢复到临时副本。忽略现成的 `tasks/`，只从事件重建一条任务，核对任务标识、状态、来源、归属及结果引用（对应阶段一③）

**不接受的证据**：模型自己说「完成了」。必须有产物、有 commit、有可核对的落盘。

## 十一、对共享记忆子项目的要求

本节是框架层要求：只定子项目设计必须满足的边界与判据，不预写其内部设计。子项目设计若与本节冲突，以本节为准回炉，防止自行跑偏。本节由阶段一锁定，作为进入阶段二的前置；不在阶段二完成标志里验收「首批里程碑」。

1. **一份真相源**：与任务账本同源的 append-only 事件库，原始事件为唯一真相源。一切机器提炼产物与 `tasks/` 目录均为可重建的视图。影响账本的变更按 §4.3 落事件。
2. **provenance 完备**：每条必记谁、何时、经何通道、依据什么原始引用，缺一不入库。来源、加工和人工确认按 §6.1 解释，跨体系标签映射在 contracts 定稿。
3. **分层与单向晋升**：经验层与知识层（`llm-wiki`）分治；晋升必经"候选 → 用户确认"，机器提炼权威封顶 `inferred`，不得冒充知识、不得自动晋升。
4. **治理归壳**：治理作业（提炼、整理、冲突标记、晋升候选生成）的触发与承载属协调面职能；子项目须为每项作业写明触发方式、输入输出与人工确认点，治理能力不得做成任一 agent 的私有能力——换 agent 不丢治理。
5. **模型只当工具**：治理用模型遵守铁律二——有界加工、无状态、可替换；不得以治理之名在壳内行 Agent 之实。
6. **安全三档**：落实 §6.4（扫描默认开、凭据降价值、轮换优先处置），不另设企业级机制。
7. **开放与可迁移**：数据以开放格式存自有仓；厂商记忆只作输入源，本系统为 system of record；不锁定任何厂商的记忆服务或私有格式。
8. **信赖门**：任何提炼/加工能力转入默认启用前，须在对应指标上对照原始基线（Raw 基线）证明收益；无对照证明，不转默认。
9. **成本可计量**：治理作业的运行成本与人工确认负担须可计量并定期复核；治理总负担不得长期高于它节省的人工整理成本——高了先砍作业，不砍记录。
10. **慢层先行**：知识层接入先行，经验层快能力观察推进；事件模型字段以 contracts 定稿为准，不得自定并行格式。子项目交付节奏在子项目层自定，不得与 §八互相指认关门条件。

（取舍：原先「子项目里程碑对接阶段二、阶段二再验收首批里程碑」是循环引用，阶段二关不上门。阶段一锁定要求，子项目自己排里程碑。）
