## 3. 知情项（用户定向变更与判据不一致，须用户确认接受）

1. **对外发送类与判据不一致**：简报判据为该类保留审批；实际落实中，Telegram 已是可用的外发路径且 bash 可向任意端点发送数据，在"普通联网全开"（同为用户要求）的前提下无法按语义拦截。现状是**该类全开无审批**，不是"审批保留"。执行方如实申报、未伪造拦截，处置正确；但此口径与已裁定判据冲突，须用户明示接受为知情缺口后方生效。补偿口径：已配置的外发通道仅指向用户本人白名单会话；"向陌生端点外传数据"列为 20 任务观察窗零容忍计数，出现 1 次即按事件复盘。该类永不毕业的裁定不变。
2. **GitHub 凭据为全账号 OAuth**（用户 2026-10-29 定向变更，取代简报的单仓 fine-grained PAT）：scopes 为 repo/workflow/read:org/gist。root 管理的 Git hook 只守 git 推送路径（仅 `dsh/*`、拒非快进，已实测）；API 路径不经过 hook，且凭据文件与 dsh 同系统账户、对其自身可读——即仓库范围对 dsh 本身不构成硬隔离，靠纪律与事后可撤销（撤销 gh 授权＋删凭据文件）兜底。此风险执行方已明示，用户接受后按此运行。
3. **Telegram 为社区插件**（`@xmanrui/dsh-im@5.7.0`，非官方组织出品，超出简报"可信插件优先"的口径）：缓释措施齐备——独立 profile canary 兼容检查、钉死版本、唯一用户白名单、群聊关闭、安装前回滚副本在案。供应链风险在册，后续升级该插件须先过 canary 复测。
4. **非阻塞缺口两项**：主备模型无自动 fallback（手工切换已验可用）；Telegram 入站派活链（用户发消息→模型回复→长任务进度/停止/文件交付）未验——按执行方建议，由用户首次真实派活时顺带验收，在此之前"可用"范围为 Web/API 派活与已验的出站投递。
