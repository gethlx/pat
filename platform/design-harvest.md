# PAT 设计采收册

> **用途**：本册是长期跟进文档——汇总本轮（及后续每轮）调研中值得 PAT 吸收的**设计、机制与教训**，供升级与迭代时逐条回看。选型结论本身不在本册（另有记录），本册只收**可迁移的设计**：换了本体、进了下一阶段，这些条目依然有效。
> **维护约定**：新调研有新收获，直接往对应分组末尾追加新条目（编号顺延），不改旧条目；条目被实际采用或证伪后，在其"跟进触发"后补一行状态注记。分组按**适用位置**划分：阶段一可借用／阶段二自研吸收／共享记忆线参考／固件与设备层参考／横切原则与反面教训。
> **编纂日期**：2026-10-21。来源为本轮 PAT 选型全程调研的已核查结论（成品路六家、框架/观察路六家、生态旁线多项）。每条字段固定：设计／原项目运作／对 PAT 的价值／适用位置／跟进触发。

## 一、阶段一可借用（Hermes 接入期，配置级或薄桥即可用）

### A1. Runs API：审批是一等公民
- **设计**：异步 run 生命周期 API 中，approval（批准）、steer（中途纠偏）、stop（终止）是与"创建 run"同级的一等操作，而不是藏在某个参数里。
- **原项目运作**：Hermes 的 `POST /v1/runs` 建 run，之后经 `/approval`、`/steer`、`/stop` 子端点操控，事件经 SSE `/events` 流回；服务端持有会话状态。
- **对 PAT 的价值**：PAT 输出层 Tier 2 的审批回流（批准/驳回/干预）需要正是这组语义——阶段一的接入契约可以照这个形状定，不用自己发明。
- **适用位置**：阶段一接入时借用（Agent 层 ↔ 输出层审批回流）。
- **跟进触发**：Hermes 冒烟与接入设计时，作为审批契约的基准形状。

### A2. 设备专用 Webhook route + deliver_only 直投递
- **设计**：入站 Webhook 按 route 分发：每 route 独立 HMAC secret、prompt 模板渲染、声明式过滤、事件合并（coalesce）；`deliver_only` 模式跳过 LLM、把内容直投递到目标渠道。
- **原项目运作**：Hermes `POST /webhooks/<route>` 触发一次 run；限流 30 次/分/route、body 上限 1MB、delivery ID 幂等 1 小时；V2 签名带时间戳防重放。
- **对 PAT 的价值**：桥→Agent 的入口设计清单已经现成；低价值设备事件走 deliver_only 不烧 LLM 额度；幂等与限流口径可直接抄进 PAT 自己的 webhook 面规范。
- **适用位置**：阶段一接入时借用（薄桥 → Agent 层入口）。
- **跟进触发**：薄桥搭建时。

### A3. 出站生命周期 Webhook（事件靠推，不靠轮询）
- **设计**：Agent 把 session/turn/tool 等生命周期事件以 HMAC 签名主动推送到外部 HTTP 端点。
- **原项目运作**：Hermes `hooks.outbound`（config.yaml 配置），CLI 与 Gateway 均可发出。
- **对 PAT 的价值**：桥/网关靠推送拿到 run 完成事件再回注设备下行 topic，省掉轮询与长连接；也是 PAT 事件层的一个现成事件源。
- **适用位置**：阶段一接入时借用（Agent 层 → 桥/事件层）。
- **跟进触发**：桥需要结果回注时；事件目录与 payload 形状需先补查一页文档或冒烟确认（本轮未逐项核）。

### A4. 记忆治理配置组合拳（上线前基线）
- **设计**：把自带写入者的每个入口都配上治理：写入审批门 ×2、自维护作业关停、记忆权威让给官方插件槽、可选云组件全关。
- **原项目运作**：Hermes 配置级即可完成：`skills.write_approval` 与 `memory.write_approval` 打开、curator 关、background_review 关、MemoryProvider 插件位（单槽）由 PAT 占、Portal Tool Gateway 与 Honcho 等可选云组件默认关。
- **对 PAT 的价值**：阶段一"记忆不垄断"铁律的落地清单，全部零改源码；且每一项都对应一桩已实证的事故（见 E2、E3）。
- **适用位置**：阶段一接入时借用（Agent 层治理基线）。
- **跟进触发**：Hermes 部署第一天，先于任何真实数据接入。

### A5. 升级纪律：快照 + 自动回滚 + 只跟 stable
- **设计**：升级命令自带升级前快照与失败自动回滚；发行通道分层，默认跟 stable 通道。
- **原项目运作**：Hermes `hermes update` 带快照/回滚，v0.21.7 起默认 stable 通道；但 stable 通道也有 update 探测超时失败的实录，故仍须手动触发。
- **对 PAT 的价值**：常驻节点的升级不裸奔——PAT 运维 runbook 直接采用"有快照才升、只手动升"。
- **适用位置**：阶段一接入时借用（运维面）。
- **跟进触发**：运维手册编写时；每次升级前复查。

### A6. 版本与暴露面基线钉子
- **设计**：把"最低安全版本 + 网络暴露面收口"做成部署检查单的硬项。
- **原项目运作**：Hermes 的 Dashboard 预授权洞（含会话接管）已修于 v0.21.6；API Server 默认绑 127.0.0.1、Bearer key 必填；CVE-2026-71963（GitSpawn）修复状态各源不一、须按版本自查。
- **对 PAT 的价值**：阶段一部署清单直接引用：版本 ≥v0.21.6、Dashboard/API 不裸奔公网、需远程时反代加鉴权。
- **适用位置**：阶段一接入时借用（部署检查单）。
- **跟进触发**：部署时；此后每次大版本升级后复查 CVE 状态。

### A7. 桥的 Hermes 侧配置清单
- **设计**：设备接入只开最小配置面：Webhook 总开关 + 设备专用 route（独立 secret、窄 prompt 模板、限定 toolsets）；API Server 只绑内网、key 仅供桥调用。
- **原项目运作**：均为 Hermes 官方配置项，无改源码；设备事件的信任面被关进单 route 的窄 toolset 笼子里。
- **对 PAT 的价值**：ESP32 接入工单可直接抄；与 D2 的桥拓扑互为表里（拓扑在 D2、配置面在此）。
- **适用位置**：阶段一接入时借用（桥 ↔ Agent 层）。
- **跟进触发**：ESP32/薄桥接入时。

---

### A8. 变更收据：Agent 改动留收据、且只改被指定的那一处
- **设计**：Agent 的每次编辑是范围明确的局部操作——只改任务指定的对象，不连带重算或重渲染其他部分；完成后回报一张"变更收据"，逐项列明改了什么。
- **原项目运作**：BaoCut（AI 视频剪辑产品，JimLiu/baocut，2026-10-23 收录）——用户改一句字幕、换一个镜头，Agent 只动那一处并报告 receipt，其余时间线内容不被重渲染。
- **对 PAT 的价值**：比"降级留痕"更进一步的操作审计形态：桥与数据层将来接受 Agent 写入/修改时，应把"收据"作为回执契约的一部分（改了哪些对象、前后状态、未触碰范围），与审批中继天然配套。
- **适用位置**：阶段一接入期（桥的操作回执、审批中继）。
- **跟进触发**：薄桥/审批中继设计成文时。

## 二、阶段二自研吸收（选底座与自研时的架构级参照）

### B1. 一切皆插件——包括 agent 循环与记忆
- **设计**：没有特权核心：agent 循环、模型适配器、工具注册表、会话存储、界面全部是挂在内核上的可替换插件。
- **原项目运作**：dsh 基于 Cordis 内核，官方架构文档明言"every part of the product is a plugin"，连 agent loop 本身也是。
- **对 PAT 的价值**：与 PAT 的 adapter/契约哲学全场最同构——"私有实现可换、契约不变"被推到极致的参照实现；自研底座的架构纲领候选。
- **适用位置**：阶段二自研吸收（Agent 层整体架构）。
- **跟进触发**：阶段二选底座后、自研架构设计时，第一份要重读的条目。
- **状态注记（2026-10-24）**：dsh 经用户裁定正式升入阶段二底座现行名单（与 LangGraph、Microsoft Agent Framework、Agno 并列）；周观察（pat-phase2-watch）已改版为名单内成熟度跟踪。

### B2. 记忆外置 MCP 插槽（官方有意不内建长期记忆）
- **设计**：本体只做会话日志与上下文管理，长期记忆被有意做成一个外置插槽：经 MCP client 挂第三方记忆 server。
- **原项目运作**：dsh 用户指南专设一页"Connect a third-party memory MCP server"，附 Memorix 等参考配置且默认关闭；本体持久化只有 append-only 会话日志 + compaction。
- **对 PAT 的价值**：PAT 共享记忆层本就是 MCP server 形态——这个插槽与它是原生对接；"记忆不垄断"在 dsh 这里不是治理出来的，是架构上根本不存在垄断。
- **适用位置**：阶段二自研吸收 × 共享记忆线交汇处。
- **跟进触发**：阶段二底座与共享记忆层做对接设计时；也是 dsh 周观察的关键触发项之一（若它日后内建记忆，本条价值与它的定位都要重评）。
- **状态注记（2026-10-24）**：dsh 经用户裁定正式升入阶段二底座现行名单（与 LangGraph、Microsoft Agent Framework、Agno 并列）；周观察（pat-phase2-watch）已改版为名单内成熟度跟踪。

### B3. profile/bundle 拼装：一套底座、多种出厂形态
- **设计**：同一底座以 profile 拼装出不同运行形态：常驻服务、一次性执行、SDK 服务、协议服务、极简模式。
- **原项目运作**：dsh 的 `web`（常驻 + UI）、`headless`（跑完退出）、`sdk`（JSON-RPC over stdio）、`acp`（ACP stdio）、`sdk-minimal` 五种 profile；其自家 benchmark 成绩即用 minimal 模式跑出（同时是官方参考 harness）。
- **对 PAT 的价值**：阶段二自研时"同一节点、多种在场形态"（VPS 常驻/临时任务/被别的 agent 驱动）的拼装方式参照。
- **适用位置**：阶段二自研吸收（Agent 层形态设计）。
- **跟进触发**：阶段二形态设计时。

### B4. 模型即插件 + 三协议自定义端点
- **设计**：模型层是可换插件；自定义 provider 以三套协议（OpenAI Chat Completions / OpenAI Responses / Anthropic Messages）接入任意兼容端点、中转与自托管。
- **原项目运作**：dsh 内置 provider 目录含 Anthropic、OpenAI、Moonshot、ZAI 等，会话级选模型；社区甚至有把订阅制产品当 provider 的插件。
- **对 PAT 的价值**：模型面解耦的参考实现；"只绑 DeepSeek"的印象已被实查证伪——多厂商舰队的前提（模型可替换）在这里是默认态。
- **适用位置**：阶段二自研吸收（模型层）。
- **跟进触发**：阶段二模型层设计时。

### B5. Durable checkpoint：长工作流的状态持久化
- **设计**：图/工作流的执行状态以检查点持久化，进程中断后可从检查点恢复，长时挂起（如等审批 24 小时）不丢状态。
- **原项目运作**：LangGraph 的 durable checkpoint 是其常驻生产实证最厚的能力；本方阶段一冒烟考题（带审批挂起 24h、期间 kill 进程、恢复后继续、不用云厂商托管后端）本质就是在考这项语义。
- **对 PAT 的价值**：PAT 的审批回流与长任务天然需要这种语义；无论阶段二选谁，checkpoint 语义都是验收项。
- **适用位置**：阶段二自研吸收（工作流/执行层）。
- **跟进触发**：阶段二工作流引擎选型时；任何候选底座先过冒烟考题再谈其他。

### B6. Durable execution 作为独立拼图（不要指望框架自带）
- **设计**：持久化执行（重试、定时、长任务编排、故障恢复）从 agent 框架里拆出来，作为独立一层单独选型。
- **原项目运作**：Trigger.dev、Hatchet、DBOS、Conductor、Temporal 构成这一整类；选库型 agent 本体时，它们是必查的拼图而非可选项。
- **对 PAT 的价值**：防止阶段二出现"框架选好了才发现没有 durability"的结构性缺口；与 B5 是同一问题的两种解法（一体内建 vs 独立成层），选型时对照评估。
- **适用位置**：阶段二自研吸收（执行层）。
- **跟进触发**：阶段二底座确定后立即评估，不许拖到集成期。

### B7. 框架 + 常驻运行时一体
- **设计**：框架不止是库，自带常驻运行时（AgentOS），部署形态 out-of-box。
- **原项目运作**：Agno 以"框架 + AgentOS 运行时一体、DeepSeek 原生"在框架路线中成色突出。
- **对 PAT 的价值**：阶段二底座形态偏好参照：优先"框架带运行时"，少一层自搭常驻壳的工作与风险。
- **适用位置**：阶段二自研吸收（底座形态偏好）。
- **跟进触发**：阶段二底座名单复评时作为形态维度计入。

### B8. MAF 的未决问题：durable scheduler 能否非 Azure 自托管
- **设计**：（跟进型条目）大厂框架的托管组件与自托管边界，决定它能否进 PAT 的主权拓扑。
- **原项目运作**：Microsoft Agent Framework 是 AutoGen + Semantic Kernel 的官方继任者，已 GA + LTS；但其 Durable Task Scheduler 能否在非 Azure 的 VPS 上自托管，本轮未证实——这是它最大的未知数。
- **对 PAT 的价值**：这是 MAF 留在阶段二底座名单上的唯一结构性悬念；有答案（能/不能）都会改变名单排序。
- **适用位置**：阶段二自研吸收（底座名单维护）。
- **跟进触发**：周观察（pat-phase2-watch）持续盯；阶段二启动前必须先有实证结论。

### B9. Wasm 组件插件：能力沙箱化的扩展模型
- **设计**：扩展以 Wasm 组件形式运行，能力受沙箱约束，与宿主进程隔离。
- **原项目运作**：ZeroClaw 的扩展体系已是 Wasm 组件插件；与之对照，Hermes 官方明示其插件是进程内运行、"不是沙箱"。
- **对 PAT 的价值**：阶段二扩展架构的两条路线之对照样本：生态便利（进程内）vs 能力隔离（Wasm）；PAT 若开放第三方扩展，Wasm 路线是安全基线候选。
- **适用位置**：阶段二自研吸收（扩展/插件架构）。
- **跟进触发**：阶段二插件架构设计时，与 B1 的插件化纲领一起看。

### B10. 五层安全架构
- **设计**：安全分五层叠防：内核级沙箱、工具守卫规则引擎、文件守卫、技能扫描器（激活前扫 + 内容 hash 防偷换）、访问策略层。
- **原项目运作**：QwenPaw 的内核沙箱用 Seatbelt/Bubblewrap/Landlock/AppContainer 分平台实现；Tool Guard + File Guard + Skill Scanner + Access Policy 五层俱全；第三方实测埋 6 个攻击拦下 5 个；产品至今无公开 CVE。
- **对 PAT 的价值**：自研安全分层的最完整蓝图，尤其 Skill Scanner 的"内容 hash 防偷换"值得直接抄。注意只吸收设计、不吸收其默认值与未验项（其沙箱默认态等三处承重项无公开实证，见 E5/E6）。
- **适用位置**：阶段二自研吸收（安全架构）。
- **跟进触发**：阶段二安全设计时逐层对照。

### B11. 凭据加密金库 + 零遥测
- **设计**：凭据进 AES-256-GCM 加密金库；产品代码层面无遥测（经代码 grep 验证而非口头承诺）。
- **原项目运作**：IronClaw 的凭据金库与无遥测设计是其安全成色的核心；对照组是 Hermes 的明文 `.env`（0600 权限）+ 细粒度输出脱敏——两种取舍各有账。
- **对 PAT 的价值**："数据不出自己手"在凭据层的实现标杆；阶段二凭据设计按金库路线走，脱敏管线（B12）两者都要。
- **适用位置**：阶段二自研吸收（凭据与隐私层）。
- **跟进触发**：阶段二凭据/隐私设计时。

### B12. 技能供应链治理 + Hardline 黑名单 + 三道脱敏
- **设计**：三组可拆开抄的细节：①技能安装强制隔离扫描 + 信任分级 + hash 锁定；②命令审批有 Hardline 黑名单，连 `--yolo` 都越不过，无人值守默认 deny、超时 fail-closed；③输出脱敏三道（工具输出、子进程 env、MCP 报错）。
- **原项目运作**：均为 Hermes 的已实现机制且官方文档诚实标注边界；其技能生态至今无已知恶意技能事件。
- **对 PAT 的价值**：阶段二自研网关/底座的安全细节清单；其中审批与脱敏部分阶段一在 Hermes 上直接受益、自建桥/网关时同样适用。
- **适用位置**：阶段二自研吸收（安全细节）；部分阶段一即受益。
- **跟进触发**：阶段二安全设计时；阶段一自建桥/网关时先抄②③。

### B13. 多 Pipeline 网关 + 按工具访问策略
- **设计**：平台即网关：多条 Pipeline 并行路由不同入口与下游；MCP 工具按单个工具粒度设访问策略。
- **原项目运作**：LangBot 以多 Pipeline + 15+ IM 入口见长，原生把 Dify/Coze/n8n 等当作下游 agent 接入——它治理的是"入口与路由"，不是 agent 本体；其 MCP 管理面有按工具的访问策略。
- **对 PAT 的价值**：多 Agent 舰队的入口网关形态参照：入口统一、路由分流、工具治理细到单个工具——阶段二做舰队网关时比"每个 agent 各连各的渠道"更合 PAT 的分层。
- **适用位置**：阶段二自研吸收（网关/入口层）。
- **跟进触发**：阶段二舰队网关与多入口设计时。

### B14. PPC 优化循环：借方法不借工具
- **设计**：Harness² 的价值不在工具本体，而在其 prompt/policy 优化循环方法——框架无关，可移植到任何已选底座上做系统化调优。
- **原项目运作**：本方对 Harness² 的裁定即"借方法不借工具"：它不构成选型变量，但构成选型之后的方法论资产。
- **对 PAT 的价值**：防止"调优 = 换工具"的反复横跳；底座定下来后，用同一套优化循环持续压榨，而不是再起一轮选型。
- **适用位置**：阶段二自研吸收（方法论）。
- **跟进触发**：任一底座选定并跑稳之后，调优阶段开启时。

### B15. 沙箱/部署运行时独立成层（证据薄，先占位）
- **设计**：把 sandbox 与部署运行时做成独立层，与 agent 框架解耦。
- **原项目运作**：AgentScope Runtime 属此形态（QwenPaw 的同门生态）；本方对 AgentScope 本体的认知仅到扫荡级，本条证据级别低。
- **对 PAT 的价值**：阶段二分层时多一个选项：运行时/沙箱独立成层，与 B6（durable execution 独立层）合看，构成"执行面三拆"（框架/持久化/沙箱）的讨论框架。
- **适用位置**：阶段二自研吸收（分层架构）。
- **跟进触发**：阶段二架构分层讨论时；引用前须先补一轮深查，不许凭本条直接决策。

### B16. 垂直产品验证：本体自有 + Agent 引擎插件化（ACP driver）
- **设计**：产品本体（领域数据模型 + 工具管线 + 本地 Runtime）自有且完整；智能层不自研，接现成 Agent 引擎——以统一驱动（ACP，Agent Client Protocol）接入多个引擎、引擎可替换；能力（转写/配音/生图等）与模型供应商解耦，按能力选本地或云端实现。
- **原项目运作**：BaoCut 的 Agent 功能依赖外接引擎（Claude Code、Codex 已端到端验证，Copilot/OpenCode 等经同一 driver 插入）；离开任何单一引擎，本体仍是完整可用的剪辑产品。它还把领域核心反过来以 MCP 服务 + skill 双形态暴露给任意外部 Agent，两条路径工具名一致。
- **对 PAT 的价值**：PAT 核心命题（采集/数据自有、Agent 层可换）在消费级垂直产品上的已发布实证——"本体不绑 Agent"是可行的产品结构而非洁癖；其"按能力解耦供应商"的粒度比"按产品选模型"更细，桥的能力声明可借此粒度；MCP + skill 双形态同目录暴露，是数据层 MCP 化的现成参照。
- **适用位置**：阶段二自研架构参照（Agent 层接入面）；桥能力声明粒度参照。
- **跟进触发**：阶段二底座设计或桥能力声明细化时。

### B17. 人机共编同一事务系统：同一命令网关、同一撤销栈
- **设计**：人与 Agent 在同一编辑面工作时，走同一个 command gateway、同一种事务、同一个 undo 栈；Agent 的每次改动都是可撤销事务，用户随时接管、随时回滚，不存在"Agent 专用通道"。
- **原项目运作**：BaoCut 中用户拖动片段与 Agent 改写字幕进入同一事务与撤销系统；其工程 bundle 含全部文档与资产版本（可迁移再编辑），但不含完整事务/撤销历史——可移植性与历史完整性之间的取舍被明确写出。
- **对 PAT 的价值**：为 E3"版本快照可回滚"提供进阶形态：写入治理的终局不是"留个快照"，而是"写入即事务、可回滚、可接管"。PAT 工作记忆层与 Tier2 审批/共编面可按此目标立标；其 bundle 的取舍（版本随行、历史不随行）亦是经验资产迁移时的现成参照。
- **适用位置**：阶段二自研（工作记忆层、输出/审批层）；共享记忆线资产迁移参照。
- **跟进触发**：工作记忆层或共编面设计时。

### B18. 工程即唯一真相源：派生物一律从属
- **设计**：全部工作成果（转写、字幕、翻译、配音、章节、动效）只住在一个可编辑工程对象里；一切文件形态（SRT/MP4/音频/文本）都是该工程的导出，永不反向成为真相；工程以版本化 bundle 形式整体迁移。
- **原项目运作**：BaoCut 的"The video is the source of truth"——修正一处后重新导出，源头永远只有一个。
- **对 PAT 的价值**：与数据层"只增不改、开放格式"同构的另一形态印证：主权资产必须有单一规范源，派生视图/导出物可再生、不回写。此条的价值不在新意，在"有人在真实产品里靠它吃饭"的外部实证。
- **适用位置**：数据层设计自检（既有原则的对照标尺）。
- **跟进触发**：数据层成文设计时对照。

### B19. 双层架构：常驻 Router 分派 + Worker 隔离执行，订阅直通绕过中转
- **设计**：把"维护全局连续性"与"高并发执行"拆成两层：常驻 Router 只承接全部入口的人类交互、任务分派与全局记忆，不直接执行具体任务（可配轻量模型、可不配执行工具）；Worker 上下文彼此隔离、各管一个任务、只向 Router 汇报，由 Router 统一对外回复。任务分派后，同一话题（Thread）的后续事件由程序直通已订阅的 Worker，不再经 Router 转发（订阅为多对多：一个 Thread 可被多个 Worker 订阅，冲突靠共同事件流自发现）；Router 只处理未订阅新事件的冷启动与跨任务协调。事件进入先过两级过滤：程序规则（来源/范围/白名单）走快路径筛噪，余下候选才交模型做语义判断。Router 单会话靠"推理期间积压的事件在下一轮合并注入"的批处理摊薄单个决定的成本。
- **原项目运作**：DeepSeek Harness 团队《Super-agent 设计探索》（2026-10-31，理念文，内部实例已持续运行、参与问题复现修复与代码审查响应）。其消融实验（合成负载，约 300 条消息、约 20 条真实请求）显示双层架构完成时间显著优于单会话加子代理工具方案（后者在中性提示下多次运行从不委派、长尾严重）；去掉直通则完成时间不变，但 Router 决定数与读缓存 token 明显上升——直通省的是中转开销，不是速度。
- **对 PAT 的价值**：多任务并行时"单会话互相阻塞、上下文混杂"是迟早撞上的墙，此条给出系统层解法而非提示词解法——分派者不下场、后续事件不绕中转。订阅直通与 PAT 的 MQTT 主题订阅天然同构；两级过滤即触发策略的"确定性前置 + 语义兜底"，与触发判断尽量下沉的既定原则一致。
- **适用位置**：阶段二自研吸收（多任务 Agent 运行时的会话组织与事件路由）。
- **跟进触发**：阶段二底座定版后做多任务运行时设计时；或任一在用 Agent 出现多任务串行阻塞/上下文混杂的实证时。

### B20. 计算、状态与环境三分离：云端无状态循环 + 端侧无状态执行端
- **设计**：分两步拆开计算、状态、环境在单机上的绑定：先把推进 Agent 循环的计算放进云端无状态容器、会话状态存入数据库，容器可替换可扩展、连续性由存储保障；再把执行环境留在原地——端侧只部署一个不保存会话状态的轻量执行端，负责执行命令与返回结果，环境本体（含未提交修改、私有凭据、内网依赖、专用工具链）不复制、不上云。Agent 可跨多台接入设备切换环境，并能等间歇在线的设备重新上线后，自动续办需要在该设备上执行的任务。
- **原项目运作**：同文第五节，明言与 Anthropic 的"脑手分离"（harness 无状态、会话日志存于 harness 之外）一致，区别在场景：首先接入的是用户日常使用、可能间歇在线的个人机器（自带机器接入），其次才是云端沙箱。文末自列开放问题：云端循环一旦被攻破，将牵连其接入的全部端侧设备；凭据须做到"可用但不进入模型上下文"，机制未解。
- **对 PAT 的价值**：与 PAT 蓝图几乎逐项同构——自有层不动、Agent 层可替换、端侧执行要薄、私有面止于桥；此条是同一思想在"云端 Agent + 用户设备"场景的官方级表述，可作阶段二拓扑设计的互证与术语对齐。其自曝的安全开放问题（云端失陷的爆炸半径、凭据不可见使用）正是 PAT 做跨设备拓扑时必须先答的题。
- **适用位置**：阶段二自研吸收（部署拓扑）；与蓝图分层原则互证。
- **跟进触发**：阶段二部署拓扑设计时；PAT 出现"接入用户自有设备"类形态立项时。

### B21. ACP 接入实证：标准协议 + 原生协议双轨的 adapter 层
- **设计**：Agent 接入不押单一协议：能走标准协议 ACP（Agent Client Protocol）的走 ACP，厂商有更深原生接口的走原生协议（Codex App Server 的 stdio JSONL、Claude Agent SDK 的 stream JSON）；每个 agent 是底座 CLI 的一个持久会话，登录态与会话状态留在各 CLI 自有目录，运行时只做会话托管、队列与协作，不接管凭据。自定义 ACP agent 与 OpenAI 兼容端点同为一等接入形态，本地模型服务（Ollama、LM Studio）自动探测。
- **原项目运作**：OpenBot（nightly-labs/openbot，维护主体 Synthetify Labs，2026-08 建仓，核查时 v0.60.0/2026-11-03）：接入 Codex、Claude、Grok、OpenCode、Gemini、Cursor、Cline、Kimi、Devin、Hermes 十余种底座，provider CLI 由应用统一下载、钉版至全机共享目录；上下文按 agent 监测、超限前自动压缩；agent 切换底座时本地对话保持连续，provider 原生 session id 只作私密恢复句柄。
- **对 PAT 的价值**：B16"Agent 引擎插件化（ACP driver）"的规模化实证——双轨而非单轨是现实解：标准协议保下限（可替换性），原生协议保上限（深度能力）。PAT 蓝图 adapter 模式"私有协议止于桥、层间全开放"得到产品级验证；"凭据留底座自有目录、运行时不接管"与本方凭据纪律同向。
- **适用位置**：阶段二自研吸收（Agent 层接入与 adapter 设计）。
- **跟进触发**：阶段二做 Agent 接入层设计时；评估任一新 agent 底座的接入成本时。

### B22. SQLite 命令日志 + 读投影：本地状态核心的事件溯源形态
- **设计**：本地状态不直存当前快照，而以只增的命令日志为唯一真相源，读路径走由日志派生的投影（agents、conversations、provider 会话绑定、queues、reactions、附件索引同库）；消息队列 FIFO，支持 pause/resume/cancel，崩溃后凭日志恢复；旧格式数据迁移时原样留备份，不覆盖不删除。
- **原项目运作**：同上（OpenBot）：Electron userData/openbot.db 即其命令日志与投影库；其前身 bots.json / mailbox.json 在迁 SQLite 时原样存入 legacy-backup-v1。
- **对 PAT 的价值**：PAT 数据层"只增不改"原则在运行时状态层的对应形态——不只是采集数据只增，运行状态同样以日志为源、投影为读。C4 工作记忆层（指针 + TTL）解决"共享什么"，此条解决"本地状态如何不丢、不乱、可恢复"，两者配套；迁移留原样备份的做法可直接借。
- **适用位置**：阶段二自研吸收（运行时状态与持久化）；工作记忆层实现参照。
- **跟进触发**：阶段二运行时或工作记忆层做存储设计时。

### B23. 频道协作治理原语：单一任务所有者 + 显式委派 + 可转交
- **设计**：多 agent 协作不靠自由聊天，而以频道为单位组织：每个共享频道任一时刻只有一个 task owner 对外担责；委派必须显式发生；控制集固定为 Stop、Resume、Reassign、Archive、Restore——转交是一个有状态机的动作（Reassign），不是一句"@你来"。协作痕迹全部留在共享历史里可回溯。外部消息渠道（Slack、Discord、Telegram、WhatsApp）另设 Orchestrator agent 做提及路由与分发，是同一治理在外部渠道的延伸。
- **原项目运作**：同上（OpenBot 共享桌面频道与消息桥）；远程访问走 WebRTC 点对点加密（RPC + 事件 + 二进制文件），官方账号服务只管登录、信令与隧道配置，且账号 API、信令、TURN 均可自托管。
- **对 PAT 的价值**：与 Grok Bot 团队"不同分工 bot 按职责讨论与决策"（Lingxi Li 实践）是同一问题的两个解法——一个是 xAI 内部实践，一个是开源产品化。舰队规模化后"谁在担这个任务、转交过没有"不能靠聊天记录猜，此条给出最小原语集：所有权单点、委派显式、转交留痕。
- **适用位置**：阶段二自研吸收（多 agent 协作运行时与任务治理）。
- **跟进触发**：PAT 做跨 agent 常态协作编排设计时；与 B19（Router/Worker 双层）合读。

### B24. 派活失败语义：失败达限转 blocked、配额中断 fallback＋退避重排
- **设计**：调度器对执行失败分型处理，不一律重试：spawn 连续失败达阈值，任务转 BLOCKED 并进入恢复回路；配额耗尽类中断走后端 fallback 链，退避后重新入队；任务间依赖未满足时由依赖门拦截、不派发。
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/dispatcher.ts` 的派活回路，配合 `merge-gate.ts` 的 `evaluateDeps`、`backend-fallback.ts`、`interruption.ts`；并行上限可配（默认 8），每任务一个独立 git worktree。
- **对 PAT 的价值**：PAT 蓝图只定了派活的正常路径，失败语义尚是空白；此条给出最小完备集——失败计数熔断、配额型中断的降级链、依赖门。翻译到 Git 账本语义，即 claimed 任务的失败回收与重派规则，与受派评审曾指出的"claimed 无过期回收"缺口正对。
- **适用位置**：阶段二自研吸收（调度与派活设计）；阶段四宰相派活规则细化。
- **跟进触发**：阶段一壳脚本写派活逻辑时先行参照；阶段四设计 claimed 回收与重派时必读。
- **状态注记**：观察中——来源仓 2026-11-06 才公开、公开史只有一次灌入式发布，无迭代记录可验；本条只作设计实证采收，不作可靠性背书，待其出现版本节奏与 issue 处置记录后复检。

### B25. secrets 自加载三规则：环境优先、缺失自禁用、日志只记键名
- **设计**：组件自读本地 secrets 文件的三条纪律：①已设环境变量优先于文件值；②文件或键缺失时，依赖该秘密的功能自动禁用，而非报错崩溃；③日志只记键名、永不记值。秘密存于专门分区，并排除在一切导出、打包之外。
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/secrets.ts` 与 `SECURITY.md`——daemon 自持 Telegram token、远程访问主密钥、推送私钥；各 agent CLI 用用户自身登录态，产品不代持厂商凭据。（注：其 HOST_MODE 允许 agent 继承用户真实环境运行，姿态比 PAT 宽；本条只取 secrets 加载纪律，不取环境继承。）
- **对 PAT 的价值**：与蓝图 §6.4 凭据三档"默认开、平时无感"同向的细颗粒实现规则：壳组件读凭据时"缺失即降级、日志脱敏、导出排除"可直接落为壳的实现约定，零用户摩擦。
- **适用位置**：阶段二自研吸收（壳的凭据处理细则）；与蓝图 §6.4 三档配套。
- **跟进触发**：壳第一版写凭据读取与日志模块时。
- **状态注记**：观察中（同 B24 注记）。

## 三、共享记忆线参考（多 Agent 共享记忆项目的设计资产）

### C1. 经验→资产编译 + 确权四件套
- **设计**：把 agent 的经验编译成可流通的资产（Gene＝策略、Capsule＝已验证修复），并配齐确权四件套：SHA-256 内容寻址、DID 身份、审计链、lineage 血统追踪；验证者质押可罚没。
- **原项目运作**：EvoMap/Evolver 是目前完成度最高的已实现样本：经验经其协议编译为资产、在 Hub 上按声誉（GDI）与积分（Credit）流通、被其他 agent"继承"。
- **对 PAT 的价值**：共享记忆线迟早要回答"经验如何资产化、如何确权、如何跨 agent 流通"——这是现成的设计参照系。只借资产与确权设计，**不采纳**其 Hub 中心化路径（服务端不开源、默认同步与默认公开发布与主权姿态相冲，见 E6）。
- **适用位置**：共享记忆线参考（经验层资产化设计）。
- **跟进触发**：共享记忆线做经验资产化/确权设计时，第一份要重读的条目。

### C2. Markdown 文件即记忆真相源
- **设计**：长期记忆以 Markdown 文件为真相源（而非数据库内部状态），可审计、可迁移、可 diff、可手工修订。
- **原项目运作**：QwenPaw 的 ReMe 记忆即文件真相源，其记忆形态在全场最合 PAT 的文件哲学。
- **对 PAT 的价值**：PAT 的知识层（LLM Wiki）已经是 MD 仓库形态；经验层若同形，整条记忆线的可审计性与可迁移性统一——换任何 agent 本体，记忆资产不被锁死。
- **适用位置**：共享记忆线参考（存储形态）。
- **跟进触发**：共享记忆线定存储形态时；与 B2（MCP 插槽是接口、文件是形态）配套看。

### C3. Dream 式记忆固化作业
- **设计**：周期性的离线记忆固化/策展作业：把当日散记索引化、重写摘要层，让"记了但搜不到"变成"睡醒就可召回"。
- **原项目运作**：nanobot 的 Dream 机制（且关停干净，是它的加分项）；QwenPaw ReMe 的 Auto-Dream 是同类设计（夜间重写 digest/ 节点）——但其静默失败实锤（见 E1）说明这类作业必须外挂看门狗。
- **对 PAT 的价值**：共享记忆线的召回质量靠的不是写入瞬间，而是固化作业；这是记忆系统从"存得下"到"找得回"的关键一环。
- **适用位置**：共享记忆线参考（策展/固化作业）。
- **跟进触发**：记忆线设计策展作业时；落地时必须与 E1（看门狗）、E3（审批+快照）捆绑实施，不许单独上线。

### C4. 工作记忆层独立薄层：指针 + TTL + 任务作用域
- **设计**：共享上下文不进数据层，另设一层薄的工作记忆：只存指针不存本体、条目带 TTL、按任务作用域隔离、乐观并发。
- **原项目运作**：本方在蓝图修订中已定此分层（工作记忆层与"只增不改"的数据层严格分离）；thread-keeper 是该层的候选实现（尚未启用，待与其他 Agent 联合评估）。
- **对 PAT 的价值**：多 Agent 协作的临时上下文若直接写进资产库，会污染长期数据；这一层是"舰队协作"与"数据主权"之间的隔离带。
- **适用位置**：共享记忆线参考 × PAT 数据层/工作记忆层。
- **跟进触发**：启用工作记忆层候选评估时；阶段二多 Agent 协作设计时。

### C5. 原生记忆共存：周期性批量导出 → ETL 导入
- **设计**：不与各厂商 agent 的原生记忆争权威，用周期性批量导出 → 导入自有共享层的慢同步（ETL）模式实现共存。
- **原项目运作**：四家 web 端均可批量导出会话（ChatGPT 数据导出 ZIP、Claude 导出、Gemini 走 Takeout、Grok 导出，均为结构化 JSON）；共享记忆线已拍板底座（Hy-Memory/MemHub）的十种工具历史导入 + 本地统一召回正是这一形态的产品化。
- **对 PAT 的价值**：用户在各厂商 agent 里沉淀的历史不必抛弃、也不必实时同步；慢层先用起来，快层实时同步是全赛道空白、已转入长期观察——这是被验证过的取舍，不是将就。
- **适用位置**：共享记忆线参考（导入通道）。
- **跟进触发**：共享记忆线做四家导出 ETL 导入器时。

### C6. 知识层双准入治理：人荐机整 / 机稿人批
- **设计**：知识入库两条通道都过人：①人推荐、机器整理；②机器起草、人审批。写入侧实行角色制：同一时刻单一写入者、文件锁、一次一篇一提交；其余参与者经 inbox/ 投稿。
- **原项目运作**：本方 LLM Wiki（gethlx/llm-wiki）的现行治理（WIKI_RULES），已实证跑通；被明确豁免的只有"无主动收录、纯人触发"的工具型 skill。
- **对 PAT 的价值**：共享层最大的长期风险是污染而非缺量；这套治理是记忆线"高可信"底线的现成模板，可直接移植到经验层晋升知识层的通道设计。
- **适用位置**：共享记忆线参考（写入治理）。
- **跟进触发**：共享记忆线定写入/晋升治理时。

### C7. 上下文即缓存：内联/溢出 + 引用图链式召回
- **设计**：把上下文窗口当缓存管理：高频、近期大概率用到的信息直接内联进窗口，超预算或低频信息只在窗口内留引用与摘要、全文留在窗口外按需读取——从最少信息（ID + 摘要）起步，按局部性逐步内联时空相邻的内容，超长则截断并保留续读入口。系统对象（事件、话题、会话）统一赋唯一 ID 并在注入时内联关联对象的 ID，底层构成一张引用图；每次召回的结果本身同样遵循内联/溢出、并内联下一跳的 ID，模型得以顺着引用多跳按需展开上下文（链式召回）。
- **原项目运作**：同文第三节，服务于 Router 层在长期运行、任务历史累积之后，仍能跨信道找回旧任务的上下文。作者自承其主要解决近期任务与会话历史的按需检索；跨月级的长程记忆仍是扩展瓶颈，未解。
- **对 PAT 的价值**：与 C4 工作记忆层"只存指针 + 按需展开"是同一思想的上下文工程版本，且给出了可落地的注入纪律（起始最小集、局部性内联顺序、截断 + 续读入口、ID 引用图）。共享记忆线的检索面可直接对照：记忆对象赋 ID、索引内联摘要与关联 ID、详情按需多跳取回——正是本方"索引→详情"链的产品化形态。
- **适用位置**：共享记忆线参考（检索与上下文注入）；亦适用于工作记忆层实现。
- **跟进触发**：共享记忆线设计检索/注入机制时；工作记忆层从设计走向实现时。

### C8. 受管文件传递 manifest：产物传递的来源信封雏形
- **设计**：agent 间传文件不裸传：每次传递生成 manifest，记 ownership、recipients、size、SHA-256；文件落共享区专用 Transfers 目录；删除某 agent 时，其独占的传递物随之清理、仍被其他 agent 使用的保留——传递物的生命周期按"谁还在用"管理，而非"谁创建"。附件面另有能力协商：接收端须先 advertise 能力位（media/mp4/zip/svg-attachments），发送方才发对应类型。
- **原项目运作**：OpenBot（同 B21），`~/OpenBot/Shared/Transfers/*.openbot-transfer.json`；每 agent 独立工作区目录（~/OpenBot/Agents/<agent-id>）+ 共享区（~/OpenBot/Shared）的布局亦是同一来源。
- **对 PAT 的价值**：contracts/ 互通契约里"来源信封"（来源 / 时间 / 权威等级 / 原始引用）的产物层雏形：先有可校验的传递收据（hash + 归属 + 接收者），再谈知识层 provenance。能力协商位的做法值得契约区借鉴——接收方先声明能收什么，发送方再发。
- **适用位置**：共享记忆线参考（产物/文件互通契约）；contracts/ 设计参照。
- **跟进触发**：contracts/ 做文件/产物交换格式设计时；与 C1（确权四件套）合读。

### C9. Agent 导出格式：人格 + 记忆的可移植包（Grok Bot → OpenBot 实证）
- **设计**：agent 的可移植单位不是聊天记录，而是蒸馏包：name、instructions、avatar、skills、routines、memories——历史对话不整包搬运，由导出侧 agent 把重要事实提炼为 memories 条目随包迁移；导入侧落入新平台的工作区与记忆，agent 在新底座上以同一人格与记忆续跑。导出格式以 skill 文件形式公开，导出 agent 本身是一个可分发的 skill。
- **原项目运作**：xAI 官方提供 Grok Bot 导出 agent（入口见 OpenBot README "Import agents from Grok Bot"节的 x.ai/bot 链接），格式规格在 OpenBot 仓 resources/agent-import/grok-bot/SKILL.md；任一服务器成员可导入（≤100 MB，接管的服务器经加密 host 连接传输，本机导入不上传）。
- **对 PAT 的价值**：C5"原生记忆共存：导出 → ETL 导入"的厂商级实证，且给出关键取舍——迁移的是蒸馏后的记忆而非原始历史。这与 Raw-RAG 实证（原始证据不可替代、提炼有损）正好构成一对张力：平台迁移场景下蒸馏包是现行唯一可行解，但蒸馏即有损；PAT 共享记忆层"原始事件为真相源"的原则在迁移格式设计时须显式处理这层有损。此格式亦是"不忠诚于单一 agent"从口号变工程的现成样本。
- **适用位置**：共享记忆线参考（记忆可移植性与迁移格式）；阶段二底座可替换性评估参照。
- **跟进触发**：共享记忆线做导入/导出或跨底座迁移设计时；与 C5、Raw-RAG 结论合读。

### C10. 复现计数晋升提案：达阈值才提案、只提案不决策
- **设计**：经验事实先以 raw 状态积累；周期批处理按内容哈希统计同一事实在多少次任务中复现，达阈值才生成晋升提案；提案以带哈希标记的块追加写入 proposals 文件（幂等去重）并通知用户；提案不自动生效，用户确认后才进入正式规则/指令文件。
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/memory-promote.ts`（文件头自述 "PROPOSES (does not decide)"）——扫描各 agent 的 learnings、按哈希计数复现，提案写入项目 `proposals.md`（含 hash/kind/count/agent 标记），用户经 API 确认后才进 `instructions.md`/`decisions.md`；该功能默认关闭。
- **对 PAT 的价值**：蓝图 §十一.3 定了"晋升必经候选→用户确认"，但候选如何产生尚无机制；复现计数是现成的候选生成判据——单次出现不提案、反复出现才值得占用户注意力。提案载体是带标记的 md 文件块，与 PAT 的 Git 基座及账本仓 proposals 约定天然契合，可直接移植形态（代码自写）。
- **适用位置**：共享记忆子项目参考（治理层晋升候选生成）；蓝图 §十一.3/.4 的机制落点。
- **跟进触发**：子项目设计晋升通道时首选参照；与 C6（知识层双准入治理）合读。
- **状态注记**：观察中——来源仓 2026-11-06 才公开、公开史只有一次灌入式发布，无迭代记录可验；本条只作设计实证采收，不作可靠性背书，待其出现版本节奏与 issue 处置记录后复检。

### C11. 来源系统盖章：保留前缀只有治理通道能写
- **设计**：记忆条目的来源标记不采信写入者自报：特定来源前缀（如 `plugin:<id>`）为系统保留字，只有治理/系统通道能盖此章；外部提交若在来源字段伪造保留前缀，直接拒绝写入。
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/memory-rule-origin.ts`——规则来源以保留前缀标记并设校验，外部 payload 伪造来源会被拒。
- **对 PAT 的价值**：PAT 的 provenance 三要素（谁、何时、经何通道）若靠执行器自报，天然可伪造；此条把"来源由归并方盖章、自报不算数"落成一条可执行的写入纪律，正好补上蓝图 §十一.2"provenance 完备"缺的防伪一环，且实现成本极低（写入点一次校验）。
- **适用位置**：共享记忆子项目参考（事件归并写入纪律）；contracts 的 provenance 信封设计参照。
- **跟进触发**：contracts 定 provenance 信封、或壳归并逻辑写来源字段时。
- **状态注记**：观察中（同 C10 注记）。

### C12. 治理调用防回路隔离：治理用模型不建任务、不写事件、不走总线
- **设计**：治理环节调用模型做提炼、整理时，使用一次性的受限调用通道：不创建任务、不发事件、不经调度总线、不进账本——治理自身的活动不产生新的待治理材料，杜绝治理回路自我繁殖。
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/memory-capture.ts` 的 oneShot 调用约束——一次性提示调用明确不建 mission、不发事件、不走总线（源文件注释自述其防回路意图）。
- **对 PAT 的价值**：铁律二"模型当工具"的落地细则之一：壳以工具方式调用模型时，最容易出的事故就是治理动作被账本当作新任务/新事件再处理一遍。此条为"工具式调用"划了现成的隔离清单，可直接写进壳与治理作业的设计约束。
- **适用位置**：共享记忆子项目参考（治理层实现约束）；蓝图铁律二的实施注脚。
- **跟进触发**：子项目或壳实现任一治理作业（提炼、整理、晋升候选）时。
- **状态注记**：观察中（同 C10 注记）。

### C13. 任务终局事实捕获：廉价模型一次性抽取三类事实
- **设计**：每个任务结束时，用廉价模型对会话记录做一次性抽取，只收三类事实——decision（已定决策）、pitfall（踩过的坑）、preference（用户偏好）；以内容哈希去重后、以 raw 状态入学习库；设触发门槛（用户对话轮数下限、跳过归档/批处理型任务），功能默认关闭、显式开启。
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/memory-capture.ts`——mission 结束时以 Haiku 级模型抽取，sha1 哈希去重，入 learnings 表（raw 状态）；要求 ≥3 轮用户对话，跳过归档型 mission；默认关。
- **对 PAT 的价值**：治理的第一道提炼作业长什么样，此条给了一个克制的原型：抽取类别收敛为三类、去重靠哈希、门槛防噪、默认关防失控。与蓝图 §十一.8 信赖门配套——此类捕获转入默认启用前，须对照 Raw 基线证明收益。
- **适用位置**：共享记忆子项目参考（治理层提炼作业原型）；经验层候选生成的前置环节。
- **跟进触发**：子项目设计提炼作业时；与 C10（晋升提案）串读为完整链路。

### C14. 治理决策审计留痕：supersede 非破坏＋可回滚
- **设计**：治理动作（新增、合并、取代、否决）逐条记入审计日志；规则被新规则取代时，旧条目标记 superseded 而非删除，历史可回溯、决策可回滚；人只收周期摘要（digest），保留事后否决权。（本条只借留痕与非破坏，不借其自动生效。）
- **原项目运作**：Timon（ai-timon/timon，AGPL-3.0，2026-11-06 首个公开版本 v0.1.7；多厂商编码 Agent 编排产品——daemon 拆活派给用户已登录的各家 CLI、异模型评审后合并）：`orchestrator/src/memory-synthesize.ts`——夜间整理作业以强模型对规则语料做 new/merge/supersede/reject 决策，每条记 `memory_audit`，被取代规则非破坏保留；注：其默认开启、全自动生效的做法与 PAT"晋升须用户确认"口径冲突，不在采收范围。
- **对 PAT 的价值**：PAT 事件层本身 append-only，但治理作业对提炼层的修改若不留痕，提炼层就成为不可审计的黑箱；此条给出治理层的留痕形态——审计日志＋非破坏取代，与事件层的只增原则同构。
- **适用位置**：共享记忆子项目参考（治理层审计设计）。
- **跟进触发**：子项目设计任一自动/半自动治理作业时必读；与蓝图 §十一.9（治理成本可计量）配套。

## 四、固件与设备层参考（采集层、触发、终端形态）

### D1. 触发级联：L2 召回 → L3 精确
- **设计**：触发分档级联：低功耗常开的 L2 状态机做粗筛（高召回），命中的才唤醒 L3 端侧模型做精确判定；再往上 L4 才是 agent 策略下发。
- **原项目运作**：本方 ESP32 触发五档（L0–L4）调研的收敛结论：L2 状态机、L3 模型接入、L4 策略协议均须自写固件；现成 SDK（如 Muse Gadgets SDK）只解决"连上云端 agent 玩"，不解决触发编排。
- **对 PAT 的价值**：采集终端的功耗与误报率都由这一级联决定，是固件设计的第一性决策；"触发策略本身也是资产"（策略下沉端侧、云端只做下发与事后分析）。
- **适用位置**：固件与设备层参考（采集层触发）。
- **跟进触发**：ESP32 固件设计启动时。

### D2. MQTT + 薄桥拓扑：私有协议终止于桥
- **设计**：固件只说 MQTT（设备最自然、最低功耗的协议）；目标 agent 的私有面（Webhook 签名规则、Runs API 形状）只活在一个常驻薄桥里：桥做 topic↔HTTP 翻译与结果回注，broker 的 QoS/持久会话兜住设备休眠。
- **原项目运作**：本方为 Hermes 接入核查后的推荐路径（见 A7 配置清单）。对照实证：连"原生 MQTT"的 QwenPaw 也只认单 topic 对 + 纯文本/JSON text 载荷——结构化事件总线在任何现成产品上都得自建桥与 schema，"原生支持"不等于"不用桥"。
- **对 PAT 的价值**：换 agent 只换桥的下游，固件与 broker 拓扑不动——adapter 模式在设备侧的原样落地；这条是阶段一拓扑的既定形状，写进册子防迭代时被"直连更省事"带偏（直连 Runs API 只许作单设备临时验证，见 D2 跟进触发）。
- **适用位置**：固件与设备层参考 × 阶段一拓扑。
- **跟进触发**：ESP32 接入 Agent 层时按此拓扑施工；若有人提议固件直连某 agent 私有 API，先回看本条。

### D3. 事件订阅 + 冷却防抖（Home Assistant 模式）
- **设计**：设备状态变化经订阅过滤后才唤醒 agent：watch 名单（域/实体）做白名单、每实体冷却时间防抖；agent 回复以持久通知呈现，并可反向调用服务控制设备。
- **原项目运作**：Hermes 的官方 HA 插件：gateway 经 WebSocket 订阅 HA `state_changed`，按 watch_domains/watch_entities 过滤 + 每实体默认 30s 冷却后转发给 agent；工具侧有 ha_call_service 等反控能力；默认无过滤则什么都不转发。
- **对 PAT 的价值**：现成的"设备事件 → 唤醒"通道与防抖设计；家里已跑 HA 时阶段一可零自研借用。代价要记清：设备契约被 HA 的实体模型接管——借用的是通道，不是契约主权。
- **适用位置**：固件与设备层参考（事件通道）；HA 在场时阶段一可借用。
- **跟进触发**：设备事件通道设计时；决定是否引入 HA 时对照本条代价项。

### D4. 设备交互形态：配对码、动作即工具、TTS 回放
- **设计**：随身终端的交互三件套：配对码完成设备与 agent 的绑定；设备动作以 agent 工具的形式暴露（agent 能"操作设备"）；回复以 TTS 在设备端回放。
- **原项目运作**：社区项目 hermes-gadget-sdk（ESP32-S3 固件 + Hermes 插件 + 自研 WebSocket 协议，非官方、自称实验性）已把这套形态跑通，证明产品形态成立。
- **对 PAT 的价值**：输出层 Tier 1（随身 glanceable 终端）的 UX 参照——借交互形态，不借其"插件 + 私有协议"路线（私有协议扩散正是 adapter 原则要防的，见 D2）。
- **适用位置**：固件与设备层参考（输出层 Tier 1 终端）。
- **跟进触发**：Tier 1 终端 UX 设计时。

### D5. ESP32-S3 视频现实路线（硬件硬约束）
- **设计**：（约束记录）S3 无 H.264 硬编码，视频现实路线是 MJPEG；带 H.264 硬编的 P4 不在 Muse Gadgets SDK 支持表内；S3 只有 BLE、无经典蓝牙。
- **原项目运作**：本方 ESP32 选型核查的实证结论，曾纠正过一次"拿过期产品目录下结论"的误判（见 E8）。
- **对 PAT 的价值**：板子选型与固件媒体管线的硬约束底稿——视频数据主权的第一性问题（采什么格式、什么码率、端侧能否编码）都从这里出发。
- **适用位置**：固件与设备层参考（采集层硬件）。
- **跟进触发**：摄像头板选型（要/不要摄像头、哪颗芯片）拍板时。

### D6. 出境网络：VPN 终结点放随身路由
- **设计**：采集终端的出境通道由随身路由做 VPN 终结点，终端只连路由，不各自处理 VPN。
- **原项目运作**：本方核查结论：手机热点共享 VPN 是系统级死路（iOS/Android 均绕过）；固件内跑 VPN 开发成本不可控、已否决；用户现有的 BE3600 随身路由即最小成本终结点。
- **对 PAT 的价值**：边缘层（data mule/网络中继）的既定形状，避免在固件或手机侧重走死路。
- **适用位置**：固件与设备层参考（边缘层）。
- **跟进触发**：采集终端联网方案定稿时。

## 五、横切原则与反面教训（不属于任何一层，属于所有层）

### E1. 静默失败是通病 → 外部看门狗 + 永不信自报成功
- **实证**：QwenPaw 的 Auto-Dream 静默失败 45+ 天、471 次报错、零告警；ReMe 出现假报 success、整晚工作成果静默丢失且永不重试；Hermes 亦有整合失败却记录 "completed" 的实锤。
- **原则**：任何后台/自治作业的"成功"必须由作业之外的独立信号验证——文件看门狗、心跳、结果抽查，三选一以上；系统自报成功不构成证据。
- **对 PAT 的价值**：阶段一的核心产出是可信的使用经验数据；一个会静默说谎的系统污染的不是功能，是经验本身。这条从第一天起适用于所有层。
- **适用位置**：横切（所有后台作业、固化作业、同步作业）。
- **跟进触发**：任何新作业/新同步上线前，先答"它的看门狗在哪"。

### E2. 一切自治循环设死预算
- **实证**：Hermes 的 Curator 死循环 20 小时、5,501 次调用、烧掉 353M tokens——根因是迭代上限被设成 9999 且全局兜底被拆掉。
- **原则**：自治循环（自维护、自动策展、后台复核、定时任务）必须有迭代/token/时长三重硬上限 + 全局熔断；上限只能由所有者改，下层配置无权单独放宽。
- **对 PAT 的价值**：自治是 PAT 的常态运行方式（夜间固化、周期复盘、舰队自维护），没有死预算的自治就是无上限的账单与污染源。
- **适用位置**：横切（所有自治组件）。
- **跟进触发**：引入任何自治组件时，先查它的上限配置面；查不到上限 = 不许上线。

### E3. 后台写入 = 审批门 + 版本快照 + 不静默跨机同步
- **实证**：Hermes 后台 review 把用户技能写成 0 字节、还同步到了其他机器；机器样板话被当作用户事实存入长期记忆。
- **原则**：自治写入（技能、记忆、策展资产）先过写入审批门；被写对象有版本快照可回滚；策展类资产跨机同步必须显式批准，默认不带。
- **对 PAT 的价值**：舰队是多机多 agent 的，单机的写入事故会被同步放大成全舰事故；审批门与快照是唯一的刹车。
- **适用位置**：横切（记忆线、技能系统、同步机制）。
- **跟进触发**：设计任何"后台自动写"功能时；A4 的配置组合拳就是本条在 Hermes 上的现成实现。

### E4. 契约只建在文档化面上
- **实证**：QwenPaw 的实际 HTTP API 面比文档宽得多，多出来的一大半是前端同源接口——无稳定性承诺、随版本漂移；其升级又是重装式，漂移成本更高。
- **原则**：PAT 的契约（对底座的依赖面）只允许引用文档化 + 可钉版本的接口；未文档化面如必须用，一律隔离在 adapter 内、做好随时弃用的准备。
- **对 PAT 的价值**：阶段一产出的是被验证的契约；在会漂移的面上沉淀契约，等于地基浇在沙上——这是 Hermes 在决赛中赢下的第一条，值得固化为通则。
- **适用位置**：横切（一切接入与集成）。
- **跟进触发**：每次接入设计评审时，逐个依赖面问"它文档化了吗"。

### E5. 安全设计必须与部署拓扑一起验
- **实证**：IronClaw 的安全策略主动封堵 localhost/IP 字面量 MCP 端点，与 PAT 默认内网拓扑正面相冲（其安全成色全场最硬，却因此只拿到 62 分适配度）；QwenPaw Console 鉴权默认关 + localhost 免鉴权，绑 0.0.0.0 或过反代即裸奔。
- **原则**：安全机制不是孤立属性——选型与冒烟时必须把 PAT 的真实拓扑（内网 MCP 端点、绑定地址、反代链）摆上台面与安全策略对撞验证；"安全"与"可用"在拓扑上打架时，两边都要让步方案，不许默认牺牲拓扑主权。
- **对 PAT 的价值**：防止"账面最安全、落地最别扭"的选型翻车重演；IronClaw 的教训是结构性而非质量性的，最容易在下一轮选型中被遗忘。
- **适用位置**：横切（选型冒烟、部署评审）。
- **跟进触发**：任何候选进入冒烟清单时，拓扑对撞列为必测项。

### E6. 默认值审计：外发、发布、权限三类默认值一律显式改
- **实证**：QwenPaw `init --defaults`（官方快速开始的用法）会自动接受遥测 opt-in，根除要靠环境变量 `QWENPAW_TELEMETRY_DISABLED=1`；LangBot 的 `enable_all_*` 系列默认全 true；EvoMap 的记忆图谱默认同步 Hub、进化成果默认自动公开发布。
- **原则**：接入任何产品先做一遍默认值清单：凡涉及数据外发、自动发布、权限放行、自动同步的默认值，逐项显式设定并留记录；"默认关"要验证、"默认开"要关掉或收窄。
- **对 PAT 的价值**：数据主权最常见的失守不是被攻破，是被默认值"顺手"送出去；这条审计是成本最低、收益最确定的接入动作。
- **适用位置**：横切（一切接入动作的第一步）。
- **跟进触发**：每个新产品/新组件接入时，先交默认值审计表再接真实数据。

### E7. 补丁层级：配置 ＞ 插件 ＞ 旁路 ＞ 源码
- **实证**：本轮适配度评估的定级口径即源于此——Hermes 以"配置 + 一条薄桥"跑通（92 分），而被迫源码级的两家（ZeroClaw、IronClaw）分数垫底；用户亦已拍板此优先级为接入总原则。
- **原则**：给成熟产品打补丁时按此顺序选层，越薄越优先；真正要沉淀的资产是契约与旁路层，不是本体代码——本体随时可换，补丁层级决定换本体的沉没成本。
- **对 PAT 的价值**：这是两阶段路线的操作守则：阶段一的全部接入动作都应落在此梯子的前三级；一旦某方案需要动源码，先停下来问是不是选错了本体。
- **适用位置**：横切（一切接入/改造决策）。
- **跟进触发**：每次接入方案评审时标注其补丁层级；出现"源码级"方案自动升级评审。

### E8. 成熟度多维加权：禁单一信号定性
- **实证**：dsh 曾仅凭 0.2.x 版本号被打入观察名单，经多维核查纠偏（其发布节奏、机构投入、npm 月下载 173 万均属顶格，结论是"更强的阶段二候选"）；反面同样成立——star 通胀严重（dsh 三周破 20 万 star 是名气数字）、微软出品的 AutoGen 照样归档停维。
- **原则**：候选评估固定四维加权：发布历史的长度与节奏 × 机构背书与持续投入 × 社区口碑一手实证 × 硬使用量（下载/拉取）；star 只作发现信号；版本号只看其发布史信息量。时效性信源（产品目录、价格、赛事日历）先看日期再下结论。
- **对 PAT 的价值**：选型判断的方法论底座；本轮至少三次误判（dsh 版本号、过期目录判五合一不存在、Letta 依据过期）都死在单一信号上。
- **适用位置**：横切（一切候选评估）。
- **跟进触发**：任何新候选进名单时，按四维出评估表，不许单维定性。

### E9. 失败模式"已知"优于表面"干净"
- **实证**：Hermes 的记忆事故全有尸检报告与 issue 编号，可逐条设防；QwenPaw 的记忆系统全网查不到一手好评、仅有的问题报告又成色难看——"干净"实为用户基数太小、证据缺位。决赛裁定的第三条即基于此。
- **原则**：评估系统可靠性时，有据可查的坏消息 > 查不到消息；证据密度本身计入评分，"无公开 CVE/无差评"在小基数产品上不作正分。
- **对 PAT 的价值**：防止被"账面完美"的小众产品误导；与 E8 的口碑维度互为表里。
- **适用位置**：横切（候选评估、风险判断）。
- **跟进触发**：任何"零负面"结论出现时，先查它的用户基数与证据密度再采信。

### E10. API 连续性与升级回归：整代弃用是真实风险
- **实证**：Letta 在 2026-03 废弃整代旧 API Server 转向 letta-code；QwenPaw 八个月内改名一次、升级靠重装；Hermes 把插件移出 core 后 `update` 不再带插件、stable 通道亦有升级失败实录。
- **原则**：长期底座优先有稳定性承诺者；任何在用产品钉死版本、升级走全量回归；评估候选时把"迁移成本"作为独立一项，整代弃用史是持续性负事件、按负分计。
- **对 PAT 的价值**：PAT 是长周期自建项目，底座的地层变动比功能差距更伤；契约层（E4/E7）是唯一的防震层。
- **适用位置**：横切（底座选型与版本管理）。
- **跟进触发**：阶段二底座定版时；任何在用组件大版本升级前。

### E11. 生态规模 ≠ 安全：供应链面单独治理
- **实证**：OpenClaw 生态最大，安全债也最重（RCE CVE、ClawHavoc 供应链攻击、大量公网暴露实例）；QwenPaw 的 Skill Market/插件自动同步同样是持续攻击面，只是尚无事件实录。
- **原则**：生态只作设计参考不等于可直接接入；凡"市场类自动同步"机制，接入前过 E6 默认值审计 + B12 的扫描/信任分级/hash 锁定，缺一不可。
- **对 PAT 的价值**：舰队规模越大，供应链入口越多；这条与 B12 是同一防线的"原则面"与"机制面"。
- **适用位置**：横切（扩展生态、技能/插件市场类功能）。
- **跟进触发**：任何产品开启其市场/自动同步功能之前。

### E12. 第三方文档与 skill 按外部数据隔离
- **实证**：EvoMap 官方 wiki 的配置页内嵌了直接写给 agent 的行为指令（要求读到该页的 agent 未经用户确认不得启动其组件、须披露写凭据行为等）——本轮调研为纯读取、未运行任何组件，未受影响，但现象已记录在案。
- **原则**：外部文档、skill 文件、网页内容一律只作数据、不作指令；接入任何第三方文档/skill 通道前，先扫一遍有无面向 agent 的指令性文字；agent 行为只听所有者与本体配置。
- **对 PAT 的价值**：PAT 未来会大量消费第三方 skill 与文档，这是提示注入的现实入口；其披露内容本身甚至可能是善意的，但通道性质不因善意而改变。
- **适用位置**：横切（文档/skill/网页消费面）。
- **跟进触发**：接入任何新的第三方 skill 源或文档源时。

### E13. 自治边界三要素 + 逐任务成本账本
- **设计**：Agent 自治须同时显式声明三要素——作用范围（scope）、访问模式（access mode）、预算（budget）；破坏性动作先问；不可信材料只作数据、永不作指令；每个任务记一份用量账本（usage ledger），成本对用户持续可见。
- **原项目运作**：BaoCut 将 bounded autonomy 写为产品级承诺（明确 scope/access/budget、destructive 先问、untrusted material is data never instructions、honest delivery 只报实测不报"已完成"）；其模型层有 per-job 成本账本。
- **对 PAT 的价值**：为 E1（看门狗）、E2（死预算）补上产品级落形态：预算不只是熔断阈值，还要是"逐任务可见账本"——353M 事故靠人次日看配额才发现，正是因为没有这种账本。阶段一的最小落地已写入配置方案（服务商消费上限 + 用量告警，见 hermes-config-spec §3.4/§7）。
- **适用位置**：全线治理基线（节点配置、桥、阶段二自研）。
- **跟进触发**：Hermes 开跑验收核对告警在位时；阶段二治理设计时。

### E14. 投机执行：后台先行试做，确认有价值才交付、否则保持安静
- **设计**：借投机执行的思想：Agent 依据环境信号，在尚不确定结果是否会被采用时，先在后台尝试（复现问题、预查资料、备好草稿），用额外的后台算力换人的等待与介入成本；结果确认有价值才交付，无价值直接丢弃且全程不打扰。
- **原项目运作**：同文第三节。其内部用户群配置了"静默复现并修复"策略：群里有人反馈问题，Agent 先在后台复现并寻找修复方案，确认问题且已有简单修复后才交付，否则全程安静。个人助手场景同理：会议邀约到达时先核日程冲突、备好背景与回复草稿，用户过目即可发出。
- **对 PAT 的价值**：给"主动性"划出一条可执行的纪律边界——主动不等于多说话，而是多做后台功、只在结果成立时出声；与 PAT 输出侧的低打扰原则、以及本方监控类任务"命中才报、无事安静"的口径完全同向。前置条件是算力预算与丢弃纪律，须与 E2（自治死预算）、E13（逐任务成本账本）配套。
- **适用位置**：横切原则（一切带主动性的 Agent 行为）；输出层打扰策略设计。
- **跟进触发**：为任一节点设计主动行为/环境监听策略时；输出侧打扰策略展开时。

### E15. Watchdog 外部控制回路：独立 Agent 会话判进展，而非探活
- **设计**：在主系统之外设一个独立的、具备完整工具能力的看门狗会话，由定时消息驱动，构成外部控制回路：除处理接口报错、状态恢复失败等基础设施故障外，核心职责是由模型判断各执行体是否有实质进展、方向是否偏离整体目标，异常时介入修复，外部偶发故障则持续复查直至恢复。维护者可用自然语言向其问诊，并让它在线修正主系统的行为（增删提示词、调整触发规则）。
- **原项目运作**：同文第六节。立论是：长期运行的 Agent 异常多非进程崩溃，而是模型陷入无效循环或偏离目标，传统存活探测对此无感，所以监控对象必须从"进程活着"升级为"任务在推进"。
- **对 PAT 的价值**：E1"外部看门狗 + 永不信自报成功"的落地形态参照——看门狗本身是一个能读现场、会判断、能动手的 Agent，而非脚本探针。对照本方实证：Hermes 验证中出现过落盘误报与长任务静默，正是"自报不可信、进展需外部判读"的实例。注意其权限面（能在线改主系统的提示词与规则）与治理闸存在张力，引入时必须与审批门配套设计，不可裸奔。
- **适用位置**：横切原则（一切长时自治运行）；阶段一节点的运维面亦可参照。
- **跟进触发**：任一 Agent 进入长期无人值守运行前；自治循环治理设计时（与 E1、E2、E13 合读）。
