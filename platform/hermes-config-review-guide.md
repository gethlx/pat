# Hermes 配置方案评审指引

> 状态：现行
> 维护线：整体线
> 最后更新：2026-10-22
> 摘要：给参与评审 Hermes 配置方案的智能体的接引文档：评审范围、必读材料与顺序、评审纪律、重点议题、意见格式与回流方式。

## 1. 你被请来做什么

评审 `platform/hermes-config-spec.md`（下称"方案"）——PAT 阶段一 VPS 云端节点（Hermes）的推荐配置方案。评审结论将汇总给仓库所有者（用户）裁定；方案在裁定前不执行。你的产物是一份**评审意见文档**（见 §6），不是对方案的直接修改。

## 2. 评审范围

**在范围内**：

- 方案中每项配置的正确性、完整性与内部一致性；
- 配置 ↔ 需求映射是否真实（有没有"纸面满足"：配置名义上存在、实际达不到需求）；
- 风险遗漏（安全、记忆治理、运维、数据主权四个维度）；
- 方案引用的事实依据是否成立（欢迎并鼓励去源头核查：上游仓库文档、issue、release notes）；
- 阶段边界是否干净（本阶段与接入期的事有没有混淆或遗漏）；
- §5 的重点议题（含未决取舍 A–D）。

**不在范围内**（已定案事项）：节点选型结论（Hermes 及替补顺位）、两条线节奏分工、许可证（Apache-2.0）、仓库公开策略、架构蓝图本身。对定案有异议的，走 §4 纪律 3 的「建议重议」通道。

## 3. 必读材料与顺序

1. `AGENTS.md`（仓库维护规范，尤其写入规则与架构铁律）——先知道这个仓库的规矩；
2. `platform/architecture-v1.md` 中与云端节点、数据层、协议与通道有关的节——需求的源头；
3. `platform/hermes-adjustments.md`——需求逐条核对与调整清单（方案的上一环：方案每项配置应能在此找到出处）；
4. `platform/hermes-config-spec.md`——被评审对象，全文；
5. 按需深入：`platform/design-harvest.md`（设计与反面教训的出处）、方案 §6 引用的上游 issue 与文档。

## 4. 评审纪律

1. **只读评审**：不直接修改方案及任何既有文档；你的意见只写入你自己的评审文档（§6）。
2. **意见必须可核查**：事实断言给出处（链接 / issue 号 / 文档节号）；推断标注为推断；不确定就明说不确定。
3. **定案重议须有硬证据**：与已定案事项冲突的意见单独标注「建议重议」，并附可复现的事实证据；仅凭偏好或口味的重议意见不进入汇总。
4. **只写有影响的事**：命名、行文、格式偏好不写；只写影响正确性、安全性、可执行性的问题。
5. **不替方案补执行细节**：方案层只到配置姿态与目标值；发现缺失时指出"缺什么、为什么重要"，不要直接写操作命令充数。

## 5. 重点议题（请逐项明确表态）

- **A 占槽节奏**：定调为"先以治理后原生记忆运行、共享记忆线就绪后再占 MemoryProvider 槽"。次序是否合理？有无更优安排？
- **B 凭据基线**：建议接受"密钥文件 0600 权限 + 整机磁盘加密"，密钥注入类改造放迭代期。对个人自用阶段是否足够？有无更轻、且不增加日常运维负担的替代？
- **C 审批长挂起**：方案不定纸面结论，以执行后冒烟实测裁定（判据：审批挂起数小时、期间重启进程、审批可恢复并走完）。判据是否充分？若冒烟不过，方案给出的兜底方向（分段 run + 状态存 PAT 侧）是否成立？
- **D 渠道分工**：本阶段零消息渠道（先 API/CLI 跑稳本体）。过于保守，还是正确？
- **桥约束六条**（方案 §3.6）：翻译桥的六条设计约束是否充分？有无缺失或多余？
- **设计理念五条**（方案 §2）：彼此有无冲突？有无未覆盖的面？

## 6. 意见格式与回流

- **文件位置**：`platform/reviews/YYYY-MM-DD-hermes-config-review-<评审方标识>.md`（评审方标识 = 你的产品/模型名小写 slug，如 `claude`、`gpt`、`gemini`、`deepseek`；日期为提交日）。
- **文档头部**：沿用仓库元信息格式（状态：已提交评审；维护线：评审方-<标识>；最后更新；摘要）。
- **正文结构**：
  1. 总体结论：通过 / 有条件通过 / 不通过（三选一）+ 一句话理由；
  2. 逐条意见：编号 | 位置（方案节号）| 类别（正确性 / 风险遗漏 / 事实错误 / 阶段边界 / 可执行性）| 严重度（阻断 / 重要 / 建议）| 意见 | 证据出处 | 建议改法；
  3. 重点议题表态：对 §5 每一项给出立场 + 一句话依据；
  4. 「建议重议」专节（没有则写"无"）。
- **提交方式**：在本仓以一次提交推送你的评审文档，提交信息格式 `[platform] 评审意见：<评审方标识> 对 Hermes 配置方案`；推送后读回验证，并告知用户或整体线（汇总方）。
- **汇总与关闭**：汇总方逐条给出采纳 / 不采纳及理由，经用户确认后由整体线修改方案文档并更新其状态。评审文档保留不删，作为决策记录存档。

## 7. 背景速览（三十秒版）

PAT = 个人数据主权架构：采集终端自有 → 数据层自有 → Agent 层可替换（蓝图见 `platform/architecture-v1.md`）。阶段一只做一件事：在 VPS 上把开源 Agent Hermes 以受控配置跑起来，用户本人先真实使用，沉淀可验证的契约与经验数据。红线是记忆治理与数据主权，功能完整让位于数据可信。方案里每项配置的"为什么"写在其 §2（理念）与 §6（依据）——请先读完再质疑，重复提出已答问题会浪费一轮评审。
